# 0914. Measurement of the client per mode of its use

## Status

Accepted

## Context

The desktop client is written in Rust with gpui so that it uses less memory and processor time than the chat clients that run in Electron. A statement of that kind needs measurements of the client as it is shipped, in the states in which people use it, by a method that also reads another application. The native targets of ADR 0902 measure other things: `frames` reads the graphics memory of two windows while pictures arrive, and `endurance` reads the growth of the readings over a long use. Both run two windows and, in `endurance`, a third person in the same process, so their absolute readings are not those of one client. `endurance` also measures the release profile with debug assertions, because the harness finds elements by the names that gpui keeps only with debug assertions; with debug assertions gpui does more work at each frame.

Limits per mode were considered and not chosen. A limit fails a change that adds memory for a reason, and it does not show where the memory goes. The work that keeps the client small is the analysis of what uses the memory and the processor in each mode and the correction of waste, with a measurement before and after each correction. The tests that fail on a defect stay: the growth bounds of `endurance` and the release of pictures in `frames`.

## Decision

- The test target `modes` of the client measures six modes: idle with one server and a text channel shown; the same channel while the wheel of the pointer moves the list up its history of 400 messages and back to its end; a voice call with one other person; the same call with the camera of the client and the camera of the other person; the same call while the client shares its screen and watches the share of the other person; a call with three other people who each send a camera, with the camera of the client.
- Each mode runs in a process of its own. The program starts itself once per mode with the name of the mode in a variable; the started process opens one native window on a new profile and brings it into the mode, and the first process collects the results and prints the table. A mode therefore starts from the state of a client that was just opened, and no mode carries the caches of an earlier one.
- The window is the only client in the process. The server of the tests runs in its own process. The other people of a call are processes of the test participant (`spikes/test-participant`): the test makes an account for each, asks the server for a place in the call with that account, and gives the token of the answer to the participant. A participant sends a camera at the size and rate of the camera of the client (1280 × 720 at 30 pictures a second, in the default simulcast layers of the SDK) and a share at the default settings of the share of the client (1920 × 1080 at 30 pictures a second).
- The window is driven through the state of the application (the selection of a channel, the entry into a call, the camera, the share, the watched share) and through events of the pointer. The wheel is turned over the bounds of the message list that the shell states (`Shell::feed_bounds`, with the feature `test-support`), so the program needs no names of elements. It refuses a build without optimization or with debug assertions: it measures the release profile as it is shipped.
- After the mode is reached, the window draws it for 20 seconds without a reading, then for 2 minutes with a reading every 5 seconds: `phys_footprint`, the graphics memory (the category "IOAccelerator (graphics)") and the pixel buffers of Core Video that the window draws as surfaces (the category "IOSurface", which the graphics memory does not include) with `footprint` (the method of ADR 0902), the bytes that the Rust allocations hold with the counting allocator `junto-alloc-count`, the processor time and the threads with `ps`, the open file descriptors. The result of a mode is the highest of each memory reading and of the threads, the processor share over the 2 minutes, and the share over the busiest interval of 5 seconds, in percent of one core. The program also counts the drawings of the window and states the processor time per drawing: its frame loop is paced by time and a native window waits for the display, so two runs of a mode in which the window draws at every frame can draw a different number of times.
- A mode fails when it was not reached or not held: the call is not connected, a camera or the watched share is not drawn, the wheel did not move the list away from its end and back, or a participant ended. The readings themselves fail nothing.
- `JUNTO_TEST_MODES_PROFILE` names a directory into which each mode writes, in the middle of its measured time, the regions of `footprint -v`, the summary of `vmmap`, a `sample` of the stacks of all threads over 5 seconds while the window draws, and the count of the Rust allocations.
- `tools/process_usage.py` reads another application from outside by the same method: every 5 seconds the `phys_footprint`, the graphics memory and the pixel buffers of each process whose executable is under a given path, their processor time and their threads, summed over the processes. An application in Electron runs in several processes; the sum is the memory that the system counts against the application.

- The bar of actions of a message (react, reply, thread, edit, delete) is built only for the message under the pointer. Before, every row of a message carried the bar, hidden until the pointer was over the row; gpui builds, lays out and hit-tests a hidden element at each frame and only does not paint it. The shell keeps the message under the pointer from the hover events of the rows and builds the bar for that message; a scroll of the list removes it, because gpui tells a row that the pointer is over it only at the next move of the pointer. The keyboard path to the same actions, the menu of a message, is unchanged (ADR 0702). The text mode measured 3.17 ms of processor time per drawing before and 2.69 ms after; the idle mode measured 31.8 MiB before and 27.2 MiB after. Test: `messages::only_the_message_under_the_pointer_has_the_bar_of_actions` in the window tests.

## Consequences

- The measurement of the emoji of the fonts at a start (ADR 0758) is measured with the target `emoji_fonts` of the client in a release build: the time of a start without a kept measurement and of a start with one, and the memory of the process. Its figures are in `docs/client-performance.md`.
- The table of the modes and its comparison with other clients are in `docs/client-performance.md`. A change that is meant to reduce the memory or the processor time of a mode is measured with this target before and after.
- The readings include the program that drives the window: its runtime with two worker threads for the accounts of the other people and the frames that it gives the window at the rate of a display. On the test platform of gpui the background tasks of gpui run on the thread of the windows, so their processor time is in the process as in the product, but on one thread.
- The camera of the client is the synthetic camera, which makes pictures of 640 × 360; a real camera gives 1280 × 720, so the camera modes measure less encoding than a real camera needs. The sound devices are the synthetic ones of the tests.
- The participants, the server and the media server run on the same machine. Their processor time is not in the readings, but they take cores; the target is run inside the machine lock of `tools/serial.sh` with no other test running.
