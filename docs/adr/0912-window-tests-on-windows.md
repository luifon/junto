# 0912. Window tests on Windows and their database

## Status

Accepted

The steps ran on the Windows machine of ADR 0905 on 2026-10-17: the 3 window tests without a database and the 97 with PostgreSQL pass (1 ignored). The two unit tests of `tools/windows` that had not run before failed there and were corrected: the version test read the PostgreSQL image from the workflow, where it no longer is (it is in `tools/ci/pins.sh`), and the test of a child that keeps the output of `pg_ctl` open left the child holding a file of the test's temporary folder, which Windows does not remove; the test now ends the child and waits for its end. The Windows window-test server has a safe standard-library file backend (ADR 0606); the Windows job includes the file, export and picture window tests. This backend is for tests only, not server deployment. Finished-recording fixtures still require FFmpeg and their /bin/sh transcription stand-in. Native verification of that backend is pending. The tests of `live::` need LiveKit and do not run on Windows.

## Context

The scope item "Client on Windows" requires that the client starts on Windows and that its window tests pass there. The check of the Windows package (ADR 0755) already starts the installed `junto.exe` with `--check-startup` and requires exit code 0 and the line `Junto first frame rendered`.

The window tests in `crates/client/tests/app` open the window code on the test platform of gpui, whose text system draws no glyphs; they need no display and no GPU. Most of them start the server binary of the workspace on a database of their own, from the PostgreSQL that `JUNTO_TEST_DATABASE_URL` names. On Linux, `tools/with-test-postgres.sh` starts that PostgreSQL as a Linux container. The Docker engine of a Windows runner runs Windows containers only, and service containers of GitHub Actions run on Linux runners only. The runner image `windows-2025` has a PostgreSQL installed, but its version is that of the image and changes when the image changes.

The Unix server opens and creates files through directory-relative descriptors and `O_NOFOLLOW`. The Windows window-test server checks components and pre-existing reparse points using safe standard-library file operations (`crates/server/src/recordings/files/windows.rs`, ADR 0606). Attachments, exports, backups and recordings use the file interface, but its production storage guarantees apply to Unix.

## Decision

- The Windows job gets its database from `tools/windows/with_test_postgres.py`. It downloads the PostgreSQL build for Windows of the version of `JUNTO_TEST_POSTGRES_IMAGE` (the ZIP of binaries from EnterpriseDB), checks its SHA-256 against the sum in the program, keeps the checked file in `~/.cache/junto-postgres` (on GitHub the job saves it in its cache in a step before the tests, so that a failed test does not lose the download; on the Windows machine of ADR 0905 it is in `postgres` of the CI directory, through `JUNTO_TEST_POSTGRES_DOWNLOADS`), and extracts only `bin`, `lib` and `share`. For each run it creates a new data directory with `initdb`, starts the server with `pg_ctl start -w` on the loopback address, at a free port, with the settings of `tools/with-test-postgres.sh`, runs the command with `JUNTO_TEST_DATABASE_URL`, and stops the server, also after a start that failed. The lanes of the Windows job start several servers at the same time (ADR 0905), and the port that one start chose is free only until another program binds it: a start whose log says that the server could not bind its port tries another free port, five ports at most; any other failure ends the start. Only the lines that the attempt itself wrote into the log count. A start that fails prints the output of `pg_ctl` and the log of the server. The output of `pg_ctl` goes into a file: on Windows the server keeps the output handles of `pg_ctl` while it runs, so a pipe would not reach its end until the server stops. `pg_ctl` removes the administrator rights from the token of the server, which the server requires on Windows.
- `tools/check-pins.sh` fails when the version of the program differs from the version of the CI image or when the program has no SHA-256. A unit test fails when its server settings differ from those of `tools/with-test-postgres.sh`.
- The Windows job runs the window tests in three steps after the package check: `updates::` without a database, the other applicable cases with the database, and the window tests of calls with the database and LiveKit. File uploads, downloads, pictures and exports use the standard-library Windows test store. The window tests of calls (`live::`, ignored in the plain run) run against the LiveKit release for Windows that `tools/with_native_livekit.py` starts (ADR 0905). The window tests of finished recordings and transcripts run as well, with no test left out by name: the job gives them the FFmpeg build for Windows of the version of the server image (`tools/with_native_ffmpeg.py`), and the stand-in of the transcription worker, a shell script, runs in the `sh` of Git for Windows, which is on the path of the job; the test passes the path of the script with `/`, and the script takes the last part of a path given with a backslash as well, since `basename` of that shell takes only `/`. The job also runs the native file-store unit tests, including no-clobber finalization and junction refusal.
- A program that the server or a test starts with an emptied environment (the server binary of the host-command tests, the setup tool of `setup_real`, FFmpeg and the transcription worker of the server) gets the variables of the system that a Windows process needs: `SystemRoot`, `windir`, `SystemDrive`, `TEMP` and `TMP` (`starter::system_environment`, empty on other systems). Without `SystemRoot` a Windows process cannot load the providers of its sockets, and the server binary could not reach PostgreSQL.
- The harness of the window tests sends the log of the client into the output of each test, at the level of `JUNTO_LOG_LEVEL` and `info` without it. The test runner prints that output for a test that fails, on every system.
- The account-switch file-dialog test runs its owner change and stale-dialog refusal on every system. Its final successful upload runs on both Unix and Windows, where the test server stores files.

## Consequences

- The tests on Windows use the PostgreSQL version of the tests on Linux. A change of the CI image needs a new ZIP with its sum.
- The first run of a new version downloads 340 MB; the next runs read the cache.
- No window test is left out on Windows by name; the job runs the tests of `updates::` without a database and every other one with it.
- The Windows backend is exercised by the same window assertions as the Unix backend, and by native file-contract, component and pre-existing-junction tests (ADR 0606).
- The Windows file backend uses only safe Rust and the standard library, with `forbid(unsafe_code)` in its module. It adds no crate or Windows API binding. The server retains its base lint configuration and its two pre-existing Windows modules for disk-space queries and parent-process monitoring.
- Protection against concurrent mutation of a held directory into a junction is a guarantee of the Unix descriptor-relative store. Standard-library Windows path operations do not provide that guarantee. The Windows server is limited to a test tree controlled by the window-test runner; it is not a supported deployment store.
