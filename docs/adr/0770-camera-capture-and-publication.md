# 0770. Camera capture and publication

## Status

Accepted

## Context

Voice calls and direct calls need camera pictures without coupling capture to the window. Permission, device disappearance and late completion of capture startup must not leave a camera running after the person stops it or leaves the call.

## Decision

- `CameraCapture` supplies permission state, a device list and a capture stream. Capture starts only after the camera action. The platform implementation may ask for permission then; reading permission or devices does not ask.
- The macOS implementation uses AVFoundation on a capture thread and delivers frames on a serial queue. The preferred capture preset is 1280 by 720; a device that does not support it uses 640 by 480 or 352 by 288, in that order. The selected dimensions accompany the stream. Publication is capped at 30 frames per second and 1.7 Mbit/s, with 360p at 500 kbit/s and 180p at 150 kbit/s as lower layers. The capture preset does not guarantee a particular hardware frame rate.
- The video data output requests the selected width and height together with its pixel format and aspect-preserving scaling; any unused area is black. A session preset alone does not enforce the dimensions after the output settings dictionary is replaced: native capture delivered 1920 by 1080 buffers while the stream declared 1280 by 720. The native test compares every delivered frame with the declared dimensions before accepting publication.
- The publication path and the receivers decode camera pictures with the limited-range 601 matrix. The YCbCr matrix attachment of each macOS camera buffer selects its source matrix: 601, 709, SMPTE 240M and the non-constant-luminance matrix of BT.2020 are used as tagged. A buffer without the attachment, or with another tag (including the deprecated P3 tags of Core Video, which ITU-T H.273 does not define as matrices), uses the rule of video decoders for untagged video: 601 up to a height of 576 lines, 709 above it. For the capture presets this gives 601 at 352 by 288 and 640 by 480, and 709 at 1280 by 720. Such a camera keeps working; when the rule does not match the camera's actual matrix, the colours are slightly wrong. Buffers in the 601 matrix keep the native path; buffers in another matrix are converted into owned 601 I420 planes before preview and publication, with the inverse source matrix and the forward 601 matrix and without clipping intermediate RGB values. Colour primaries and the transfer function are not converted. The output requests limited-range 420v buffers; a buffer of another pixel format ends capture as unsupported, because a full-range or RGB buffer would need another conversion. Synthetic pixel buffers with each tag, without a tag and with another pixel format test these rules without opening a device. The conversion adds a copy and matrix conversion per frame.
- The media connection owns capture and publication. A generation identifies each start. Stop and leave release capture; completion of an older start cannot publish a new camera. A connection loss keeps capture while publication is paused, for at most 30 seconds; then the camera ends. A new connection republishes the retained capture at a seat that the session admits, and the connection generation rejects a result from an older room (ADR 0794). A terminal call failure ends the engine and releases capture. Capture shutdown runs on the owning capture thread without blocking the media actor.
- Camera permission and the server's permission to publish a camera are independent of a microphone block. Meeting mode closes microphone publication under ADR 0510; it does not close camera publication.
- Permission refusal, system restriction, a missing device, interrupted capture, unavailable capture, a call that is not connected yet and server prohibition are distinct states. A start reads the camera permission once, on a blocking thread of the runtime, because the Linux camera opens each device node to read it. The person starts again after a failure. The notice of a failure has "Settings", which opens the settings of the application at "Voice and video", where the camera is chosen (ADR 0735), and "Dismiss". Test: `live::cameras` reads the choice of the camera after the press, in the main window and in the call window.
- Generated camera sources implement the same interface for tests. They never open a hardware camera or ask for permission.
- Windows uses Media Foundation device activation and an asynchronous source reader with its advanced video processing. Device identifiers are the symbolic links supplied by Media Foundation; an entry without a symbolic link cannot be chosen again and is left out, and an entry without a friendly name is named "Camera". Enumeration does not activate a source. The capture mode is chosen by the rule below among the native progressive NV12, I420/IYUV, YUY2 and MJPEG types that capture takes; a type that the reader refuses gives way to the next of the order. An MJPEG type is set as the native type of the source, and the reader decodes it to limited-range 601 NV12 of the same size and rate. Desktop camera privacy settings are read without a dialog; access denied during activation or reading is a permission failure. An invalidated device ends capture; preemption and a media-type change end it as interrupted.
- Windows also lists the video input devices of DirectShow (`camera::windows::direct_show`), because a camera that registers only a DirectShow source filter, such as a virtual camera, is not in the Media Foundation list. The list holds the Media Foundation cameras and then the DirectShow devices that are not among them: a DirectShow device whose device path has the device instance of a Media Foundation camera (the path without its interface class and reference string, compared without case, because the two interfaces list one device under different interface classes) is that camera and is listed once, with its Media Foundation identifier. A DirectShow device without a device path is named by the display name of its moniker, which names its registered filter and stays the same across sessions. A failure of the DirectShow list is logged and leaves the Media Foundation list. The two enumerations run on threads of their own (`camera::listing`). The list waits up to 10 seconds for the Media Foundation cameras, whose failure or absence fails the list, and up to 3 seconds from its start, and at least until the Media Foundation answer, for the DirectShow devices. A DirectShow enumeration that did not answer in that time, or that still runs from an earlier list, adds the devices of the last DirectShow enumeration that finished; no second one starts while one runs, so a DirectShow enumeration that does not end holds one thread. Reason: the client reads the camera list at each press on a device list, and before, one enumeration on one thread held the whole list up to 10 seconds and left one more thread at each read when DirectShow did not end. A start of a camera of the Media Foundation list does not enumerate DirectShow, for the same reason. A start of another camera enumerates DirectShow under the same rule (`listing::claimed`): while another enumeration runs, it starts none, finds no DirectShow device and ends as `DeviceGone`, with the reason in the log. A DirectShow device is captured through a filter graph of its source filter and a sink filter of Junto with one input pin, which accepts progressive NV12, I420/IYUV, YUY2 and UYVY pictures and RGB24, RGB32 and ARGB32 pictures, in the video formats `VIDEOINFOHEADER` and `VIDEOINFOHEADER2` (`camera::bitmap`). RGB rows run from the bottom of the picture for a positive height of the bitmap header and from the top for a negative one, and each RGB24 row is padded to four bytes, as the bitmaps of Windows are. Reason for UYVY and RGB: they are the other uncompressed formats that DirectShow sources offer, and the formats of NVIDIA Broadcast are not documented; a camera that offers only one of them did not start. The capture pin is the output pin of the capture category, or, for a source that states no category for its pins, as the virtual camera of OBS Studio 33 does, its first output pin with a stream configuration. The capture mode is chosen among the types of that pin (`IAMStreamConfig`, or the pin's own enumeration when the configuration states none) in the order of the rule below, with every uncompressed type before every MJPEG type (`format::uncompressed_first`). An uncompressed type is asked of the pin and then connected directly, and a pin that refuses the request can still take the type in the connection. An MJPEG type is asked of the pin and connected through the MJPEG decoder of DirectShow (`CLSID_MjpegDec`), which capture creates and adds to the graph at the first MJPEG type that a start tries and removes at the end: the capture pin is connected directly to the input pin of the decoder with the MJPEG type, and the output pin of the decoder directly to the sink without a type, so that the two pins agree on a type of the decoder that the sink takes. A type that does not connect gives way to the next of the order, and the pins of the attempt are disconnected. The size of an MJPEG type is that of its bitmap header, and the decoder gives pictures of that size. Reason for the decoder: a DirectShow-only device that offers only MJPEG, such as a capture device, did not start (`Unsupported`). Reason for the uncompressed types first: the decoder decodes each picture on the processor, and the uncompressed types are the path of the virtual cameras for which the DirectShow list exists; so in DirectShow, unlike Media Foundation, an uncompressed type at a smaller published size or a lower rate comes before an MJPEG type. Reason for the decoder of the system, created by its class, and two direct connections instead of the intelligent connection of `IGraphBuilder::Connect`: the intelligent connection can insert a decoder filter that another application registered, which then runs in the process of the client, and it chooses the types of the connections itself, so the log could not state them in advance. This path needs new unsafe calls, each a COM call in its own block in the module that already allows unsafe code: the creation of the decoder, its addition to the graph, the enumeration of its pins and of their directions (`find_pin`, which the search for the capture pin also uses), the request of the format, the two direct connections and the disconnection of each pin of a failed attempt. The sink keeps the graph that it joined and states it, because the graph connects only pins whose filter states the graph. The pin copies each picture and hands it to the capture thread, which keeps at most two; a picture that does not fit is dropped and counted as lost in the counts of the device check; the pacing, the conversion to I420, the stated size and rate and the errors are those of the Media Foundation path. A stated full range is refused, a stated matrix is kept, a removed device (`EC_DEVICE_LOST`) ends capture as gone, the end of the stream of the source (`EndOfStream` of the pin) as gone, as the end of stream of Media Foundation does, an aborted graph by the error of its event, a type change of the source and five seconds without a picture as interrupted. The pin records a type change and the end of the stream in flags that the capture thread reads before each wait, so neither is lost when the queue is full. A filter that did not join the graph is not removed from it at the end, so a start that fails reports no stop failure. Tests: `camera::listing::tests` (the merge, a failed and a slow DirectShow enumeration, a capture start while an enumeration runs, and a Media Foundation enumeration without an answer), `camera::bitmap::tests` (the layout of the DirectShow format blocks, the RGB row order and padding, the colour flags, the names of subtypes, the mode of an MJPEG type and the order of the types of a start), `camera::format::tests` (every uncompressed mode before every compressed mode) and `camera::windows::direct_show::tests` (the subtypes and modes of DirectShow types and the copy of a media type).
- A camera start on Windows that fails writes one log line, "the camera did not start", with the camera, the interface (Media Foundation or DirectShow), the step of the start that ran last, the types that the camera offered, the type that capture set, and the error; a capture that ends after its first picture writes "the camera capture ended". The offered types are the subtype, size and rate of each type of the capture pin of DirectShow or of each native type of Media Foundation, the latter after their count; a type that capture does not read is marked "(not read)" (`format::offered`). A subtype is named by its four-character code, by the name of an RGB subtype of DirectShow or Media Foundation, or by its identifier (`bitmap::subtype_name`). For DirectShow an MJPEG type that connected is stated with the type that the decoder gave the sink. Reason: a start that ended as `Unsupported` left no reason in the log, so a report could not tell a refused type from a refused connection; and a count of the native types of Media Foundation did not show which subtypes a camera offers that capture does not read. The description of a native type of Media Foundation reads its subtype, size and rate with the reads of `IMFMediaType` that the mode of a type already makes, in one new unsafe block.
- The capture mode on Windows and Linux (`format::order`). Capture takes a mode whose sides are even and at most 4096 pixels, with at most the pixels of 3840 by 2160 (`format::takes`). The published size of a mode is its own size when it fits inside 1280 by 720, and otherwise the largest size with its proportions and even sides that fits inside 1280 by 720 (`format::fit`): 1920 by 1080 gives 1280 by 720, 1440 by 1080 gives 960 by 720, 1080 by 1920 gives 404 by 720. The stream states the published size, and every picture has it. The order: the modes of at least 24 frames per second by published size, largest first; at one published size the smaller camera picture first, because a larger one costs a scale for each picture; then the highest rate at or below 30, else the lowest above 30, then a stated rate before an unstated one, then an uncompressed mode, because decoding costs processor time for each picture. When no mode reaches 24, the highest rate, then the larger published size. A mode without a stated rate counts as reaching 24. A start that the driver refuses for one mode tries the next. A common USB camera offers uncompressed YUY2 at 1280 by 720 only at 10 frames per second and MJPEG at 1280 by 720 at 30: the rule gives MJPEG at 1280 by 720 and 30 on Windows through Media Foundation, which is what macOS delivers, and YUY2 at 640 by 480 and 30 on Linux, which has no JPEG decoder. A larger picture at 10 frames per second was rejected because the motion of a person in it is visibly jerky; 24 is the lowest rate at which it is not. Reason for the sizes other than 1280 by 720, 640 by 480 and 352 by 288, which were the only sizes before: a virtual camera offers one size, the size that its own application sets. The virtual camera of OBS Studio offers NV12, I420 and YUY2 at the output size of OBS only; by default that is the base size (the primary screen in logical pixels, at most 1920 by 1080) scaled down until it has at most the pixels of 1280 by 720, so 1280 by 720 for a 1920 by 1080 screen, 1152 by 720 for 1920 by 1200 and 1092 by 614 for 1366 by 768, and OBS rounds the width to a multiple of 4 and the height to a multiple of 2; a person who streams often sets 1920 by 1080. NVIDIA Broadcast offers the size of its own camera setting. With the three sizes only, such a camera had no mode, and its start ended as `Unsupported` ("The camera cannot be used on this system.").
- Linux uses V4L2 rather than the camera portal. This gives the existing device-choice interface explicit camera identities and does not depend on a desktop portal camera backend or a session manager exposing camera nodes. Screen capture and sound still use PipeWire. Camera access requires read/write permission to the device nodes, including inside a sandbox; there is no portal fallback. A node is listed when it is a single-planar streaming capture device with a mode of NV12, I420 or YUY2 of a size that capture takes: capture enumerates the formats, frame sizes and frame intervals of the driver, so metadata nodes, output nodes, and nodes with only compressed, Bayer or other formats are not listed. The sizes that capture asks a driver for (`v4l2::sizes`) are each discrete frame size of the driver that capture takes (`format::takes`), and for a continuous or stepwise range the sizes 1280 by 720, 640 by 480 and 352 by 288 inside it and the largest size of the range when capture takes it (`format::PRESETS`, which the session presets of macOS also are). A driver without the enumeration of frame sizes is asked for the three sizes. The order of the modes, the published size and the scale of a larger picture are those of the rule below and of Windows. Reason: a v4l2loopback device of OBS Studio offers one discrete size, the output size of OBS, and with the three sizes only, such a device at another size was not listed. When the driver sets another size or pixel format, an interlaced field or a range other than limited, before any buffer is mapped, the start tries the next mode of the order. A device is identified by its canonical sysfs path; a selected device is resolved again at start and is never replaced by a different listed device. A node that the account may not open is not listed, because V4L2 states the kind of a node only after an open; when no node is a usable camera and at least one refused the open, the access state is restricted. Capture owns a nonblocking file descriptor, asks for four memory-mapped kernel buffers and accepts from one to 32, sets the chosen mode, and requests the frame interval of the mode when the driver supports frame-interval control, 30 frames per second for a mode without a stated rate. A refused frame-interval request leaves the rate to the driver; only a removed or busy device ends the start there. A buffer that the driver marks as damaged, or that holds less than a picture, is given back to the driver and skipped; a buffer outside the mapped ones ends capture as failed. Permission failures and device disappearance are distinct errors. Devices that expose only compressed formats or the multi-planar V4L2 API are unsupported.
- Both new backends validate dimensions, plane lengths and strides before copying, reject interlaced and explicitly full-range output, and deliver owned I420 planes. NV12 chroma is separated, I420 row padding is removed, and YUY2 and UYVY chroma is averaged over each pair of rows. RGB24 and RGB32 pictures of DirectShow are converted with the limited-range 601 matrix of the publication path, and the chroma of each block of two by two pixels is that of their average colour. A picture larger than its published size is converted at its own size and then scaled by the scaler of the call library (`I420Buffer::scale`), before the matrix normalization, which takes the matrix rule of the height of the camera picture. The operating-system matrix metadata selects the existing 601 normalization. V4L2 resolves a default encoding from the colorspace (`V4L2_MAP_YCBCR_ENC_DEFAULT`): sRGB, which uvcvideo reports, and the other colorspaces without their own encoding give 601, and Rec. 709 gives 709; the extended-gamut encodings xvYCC 601 and xvYCC 709 and sYCC use the matrix of their name. Missing metadata (a Windows type without a matrix, a V4L2 format without a colorspace) and unknown matrix metadata use the same height rule as macOS. Windows two-dimensional buffers are copied with their contiguous-copy API so GPU pitch is not mistaken for image width. No buffer is mirrored before publication.
- Native controls run on a capture thread. Startup succeeds only after a valid picture, and has a ten-second bound. Five seconds without a usable picture interrupts capture. Dropping a pending start or a running stream fences delivery immediately; native shutdown runs on the owning thread, whose wait for another sample is bounded to 100 milliseconds. A capture holds its device in the process until its native capture has closed: a new start of the same device waits for that within the start bound, because a driver refuses a second open while the first capture still closes (V4L2 answers busy to a quick stop and start). Callback objects retain no reader or source. An end notification is terminal.
- Delivery is limited to 30 pictures per second by the time stamps of the driver, or of arrival when the driver gives none, so that the jitter of the scheduler does not drop pictures. A camera whose average gap is at least that of 30.5 frames per second keeps every picture. A picture of a faster camera is taken when it is at its place, one interval of 30 per second after the place or the time of the last taken picture, whichever is later, so that the gaps stay even: 60 and 120 frames per second give 30, 59.94 gives 29.97, 50 gives 25, 45 gives 22.5, 36 gives 18 and 32 gives 16. Taking 30 of 50 or of 36 would need gaps that alternate between one and two source gaps. For a camera whose average gap is at most 0.525 of an interval, as at 60 frames per second, a picture up to a quarter interval, and less than half its own gap, before its place counts as at its place, so that the jitter of the camera does not move every taken picture by one gap.
- Ordinary tests exercise padded planes, 709 conversion, malformed lengths and sizes, YUY2 chroma, permission and device-loss error mapping, cancellation during startup and delivery after stop, the mode rule, pacing with jitter and at the common rates, the device claim, the V4L2 buffer, matrix, frame-size and interval decisions, Windows type choice and enumeration, and Linux capture against a V4L2 device in memory (ADR 0913). The explicit `camera-device` example lists without starting capture and captures only with `JUNTO_TEST_CAMERA_DEVICE=1`; it selects one listed device, rejects an absent choice, checks the size and the content of thirty pictures and the rate (ADR 0913), and on Windows also captures three virtual cameras, one of them through the MJPEG decoder and one that offers only 1920 by 1080. It requests no permission dialog. Without a camera, Linux capture is verified against the device in memory, also with one camera size of 1920 by 1080, 1092 by 614 and 1080 by 1920, and Windows capture against virtual cameras; neither verifies the drivers of real cameras, a v4l2loopback device, a DirectShow device that offers only MJPEG, or an unplug.
- The drawing window reports visible camera tiles and their pixel bounds, including interface and display scaling. Remote cameras that are not drawn are disabled; their converted pictures are released. The engine requests a layer for each visible tile and bounds conversion by that tile. The latest frame is retained for drawing. macOS uses one cached native video surface per frame; the fallback converts to BGRA. Only the local preview is mirrored. Published and remote pictures retain their source orientation.

## Consequences

The media engine has no dependency on the window toolkit. The main window or the detached window draws the call; the other releases its image references. Moving the call between windows never opens another capture. The explicit native tier verifies capture and publication with operator-managed permission (ADR 0913); generated-frame tests do not verify hardware behavior. Orientation against an assisted target and native client rendering still require separate verification.

Camera capture uses the common bounded worker supervisor (ADR 0706) on Linux, Windows and macOS. Cancellation fences delivery synchronously; neither stop nor Leave waits on a delivery mutex or joins native capture. AVFoundation stop and delegate-queue drain remain on their owning worker; camera startup has ten seconds to answer. Native shutdown errors, worker panics and cleanup deadlines produce a camera-specific notice retained by Calls after Leave, with the same generation-scoped dismissal as sharing. The camera delivery callback clones no source while holding a lock across a native `capture_frame` call. `camera::worker::tests::a_stalled_camera_delivery_does_not_hold_stop_or_its_cleanup_notice` holds a callback until after the cleanup deadline; `live::stopping::a_stalled_camera_reports_stop_failure_and_leave_still_works` checks both stop/notice/Leave and stop/Leave/notice through the window.

V4L2 close returns the result of stream-off, each mapping release and descriptor close to Rust, which logs every failure and records cleanup failure for the supervisor. Cleanup attempts all remaining operations after an error. The native C adapter test injects failures at all these operations, requires the stop acknowledgement to fail, and verifies that every mapped buffer and open descriptor was visited.

The Media Foundation reader is configured with `MF_SOURCE_READER_DISCONNECT_MEDIASOURCE_ON_SHUTDOWN`: the capture worker owns and checks shutdown instead of the reader performing it implicitly on release. A returned `MF_E_SHUTDOWN` confirms that the source is already closed and is logged separately; other shutdown errors remain failures. Microsoft documents the default [reader ownership](https://learn.microsoft.com/en-us/windows/win32/api/mfreadwrite/nf-mfreadwrite-mfcreatesourcereaderfrommediasource) and the [closed-source result](https://learn.microsoft.com/en-us/windows/win32/api/mfidl/nf-mfidl-imfmediasource-shutdown).

The final Media Foundation reader flush is checked by the same cleanup-result path as source and activation shutdown. An already-shut source is complete; every other flush failure is logged and retained in the stop result.
