# 0727. The GitHub release and the release notes

## Status

Accepted

Before the first release this record described a static release site that `packaging/site.py` wrote, with the update source in its directory `updates/`. The site was removed when the GitHub releases of the public repository became the update source and the download location (ADR 0724): a second host would have held the same files, and the client follows the layout of GitHub releases.

The unit tests of `packaging/test_release_assets.py` ran on Linux and on macOS; the tests of the test build (`--test`) ran on macOS. On 2026-11-03 `--test 4` ran on macOS on the retained files of 0.1.0: it wrote the eight files of the test build and a `SHA256SUMS` with the same lines as the `SHA256SUMS` of the published release `v0.1.0-test.4`. Not run: a publication to GitHub with the printed commands.

## Context

ADR 0724 makes the GitHub releases of `https://github.com/luifon/junto` the update source: the release of version V has the tag `v<V>` and holds the update files of every target, and the latest address serves the latest files of the newest release that is neither a draft nor a pre-release. The release commands write the files of one release into a new directory on each build system (`packaging/README.md`). A person who installs Junto for the first time needs the first-install files, their checksums, the steps of the first start of an application without a paid signature (ADR 0704), and the notes of the release. Before a release, the project gives test builds of the version to a small group, who install them by hand.

## Decision

- `packaging/release_assets.py <version> <release directory> <new output directory> [--notes <file>] [--test <n>]` collects the files of one release, or with `--test <n>` the files of test build `n` of the version. The release directory holds the files of the release from every system, as the release commands write them.
- The files of a release are the first-install files `Junto-<version>-macos-aarch64.dmg`, `Junto-<version>-macos-aarch64.zip`, `Junto-<version>-windows-x86_64-setup.exe`, `Junto-<version>-windows-x86_64.zip`, `Junto-<version>-x86_64.AppImage`, `junto-<version>-linux-x86_64.tar.gz` and `junto_<version>_amd64.deb`; the symbols file `Junto-<version>-windows-x86_64.pdb` (ADR 0755, ADR 0757); and for each of the four targets `macos-bundle-aarch64`, `linux-directory-x86_64`, `linux-appimage-x86_64` and `windows-directory-x86_64` the files `latest-<target>.json`, `release-<version>-<target>.json` and `junto-<version>-<target>.junto`. Every release holds the latest files of every target, because the latest address serves only the files of the newest release.
- A test build holds only the first-install files and the symbols file. It is installed by hand, and clients read update files only at the latest address and under the tag `v<version>` (ADR 0724), so update files under the tag of a test build would not be read. The update files of the version may be in the release directory of a test build; they are left out without a check, so one directory of a build serves both a test build and the later release of the same commit.
- The command stops with an error that names each file: on a missing file, an unknown file, a link or a directory, on a latest file whose signed release (payload and release signatures) differs from the release file of its target, and on release information whose payload names another version, target or archive name, or another size than the archive. With `--test` it stops on a missing first-install or symbols file, on an unknown file, and on a test number that is not a whole number from 1 without leading zeros; it does not check the update files. It does not verify signatures: the release commands and the package checks of ADR 0724, ADR 0754 and ADR 0755 do that before the files reach the directory.
- The output directory must not exist. The command copies every file byte for byte into a temporary directory beside it, writes `SHA256SUMS` in the format of `sha256sum`, sorted by file name, and renames the directory into place, so a failure leaves no output directory. `SHA256SUMS` lists every file except the latest files, which a freshness renewal replaces (ADR 0724); for a test build it lists every file. The command never writes into the release directory.
- The command prints every file with its size and the commands of the publication. A release has the tag `v<version>`, the only tag at which clients find the files of the version (ADR 0724), and the title "Junto <version>": `gh release create v<version> --draft --verify-tag` with every file, the title and the notes, then `gh release edit v<version> --draft=false --latest`. The files of a draft are not served, so the latest files become available together with every archive that they name.
- A test build has the lightweight tag `v<version>-test.<n>` on the release commit and the title "Junto <version> test <n>", the names of the earlier test builds. The command prints `git tag v<version>-test.<n> <release commit>`, which must be pushed before the draft is created because of `--verify-tag`, then `gh release create v<version>-test.<n> --draft --verify-tag` with every file, the title and the notes, and `gh release edit v<version>-test.<n> --draft=false --prerelease`. A test build is never edited into a release: the release of the same version is a new GitHub release of the tag `v<version>`, collected without `--test`.
- The command uploads nothing. The operator publishes; the output directory is kept as the retained files of the release, which the freshness renewal of ADR 0724 reads.
- The notes of each version are `docs/releases/<version>.md`, the text of the GitHub release. They name the server install document by its path in the repository. The notes of a test build are not tracked, so `--test` requires `--notes`; they have the sections Files, Install, Changes since test <n-1>, What this build does not do, and Known limits.
- The client shows the notes in the window. The build script of `junto-client` compiles every `docs/releases/<version>.md` of its commit into the program (`release_notes::ReleaseNotes`): the notes of a published version do not change, and the client shows them without the network and without a request to GitHub. So the release commit holds the notes of its version, as the release uses them. At each start the client compares its version with the version that started last, `last_build` in `settings.json` (ADR 0710), and stores its own. When the version that started last is older, the window shows once, at that start, the notes of every version after it up to its own, the newest first, in a dialog that scrolls and closes with Escape, its close button and "Close"; a person who updates over several versions reads each of them. A data directory without `last_build` that has a server book or a profile was used by 0.1.0, which did not store it: it gets the notes after 0.1.0. An empty data directory is a first install and shows none. Settings, About, has "What is new" with the notes of the version of the build, when the build has them; closing them returns to the settings. The notes are read as the composer reads a message (`compose::parse`: headings, lists, code blocks and inline code) and drawn as messages are. Tests: `release_notes::the_first_start_after_an_update_shows_its_notes_once`, `release_notes::an_update_over_several_versions_shows_the_notes_of_each_newest_first`, `release_notes::the_first_start_after_0_1_0_shows_the_notes_since_it`, `release_notes::settings_show_the_notes_of_this_version` (window, with notes of the tests), and the unit tests of `release_notes`, among them that the build carries the notes of 0.1.0. The other window tests give no notes, so that a data directory that they write shows none when the build carries the notes of a newer version.

## Consequences

- A release needs every first-install file, the symbols file and the update files of the four targets; a test build needs the first-install files and the symbols file. A new first-install file or a new target is a change of `release_assets.py` and of this record.
- The first-install steps and the checksum commands are in the notes of each release and in `docs/client-macos.md`, `docs/client-linux.md` and `docs/client-windows.md`, because GitHub shows the notes beside the files.
- Not checked: a publication to GitHub with these commands, and the page of a release on GitHub.
