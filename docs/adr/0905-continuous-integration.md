# 0905. Continuous integration workflow

## Status

Accepted

On macOS (ADR 0916) and on Windows (ADR 0912) the window tests of the client run against the PostgreSQL build of the system; the other tests that need PostgreSQL run on Linux only. The macOS job assembles the bundle of the client build of each commit and starts it until its first frame.

## Context

ADR 0902 decides that CI builds and tests on macOS, Windows and Linux for every commit, regenerates the API documentation and checks the licence of every dependency (ADR 0801, ADR 0202). The repository has a Rust workspace, the recording layout page with browser tests (ADR 0609), the transcription worker in Python (ADR 0610), and the container images and Compose files (ADR 0014, ADR 0015). The integration tests need a PostgreSQL that the test script starts in Docker (ADR 0904); the runners for macOS and Windows have no Docker for Linux containers. A workflow that names an action by a tag runs other code when the tag moves.

## Decision

- The steps of each job are one script under `tools/ci/`: `rust-linux.sh`, `rust-other-systems.sh` (macOS and Windows), `licences.sh`, `layout-page.sh`, `transcription-worker.sh` and `deployment.sh`. The images and tool versions of the jobs are in `tools/ci/pins.sh`. A runner only prepares the tools that a script needs and calls it, so that every runner runs the same steps.
- CI runs on a Linux host and on a Windows machine of the project over SSH and on a macOS machine (`tools/ci/ci.sh`); the GitHub workflow stays valid and calls the same scripts. See "Runners outside GitHub" below.
- One workflow, `.github/workflows/ci.yml`, runs for every push and for every pull request from another repository.
- Every action is named by its commit hash, with the version as a comment. Every container image that a job runs is named by its digest in `tools/ci/pins.sh`, which gives the two test scripts the PostgreSQL image and the LiveKit image of the deployment. The PostgreSQL build for macOS of the window tests (ADR 0916) is named there by its version and the SHA-256 of its ZIP. `tools/check-pins.sh` fails when an image there has no digest, when those two differ from the images of the deployment, when the PostgreSQL build for macOS has another version than the PostgreSQL image or no SHA-256, and when the Node, uv, Python or cargo-deny version of the workflow differs from `tools/ci/pins.sh`.
- A package that a step installs with `apt-get` is named with its version. `tools/check-pins.sh` fails for an `apt-get install` without a version in a workflow or in a script of `tools/ci/`. Not pinned: the programs of the runner image and the system packages that Playwright installs for its browser.
- The Rust steps of the Linux job run in the Linux build image of ADR 0750 (`tools/linux/Dockerfile`), through `tools/linux-container.sh`. The image is the one list of system packages for the local Linux checks and for CI: the libraries of the window, of sound and of screen capture, clang 22, which the call library needs (Ubuntu 24.04 has clang 20 at most, and ADR 0750 rejects the package repository of the LLVM project as a pinned source), PipeWire for the tests of sound, and `ffmpeg` for the tests of recordings. Its base image has a digest, and each package has a version from one dated Debian snapshot; `tools/check-pins.sh` checks both, and that its Rust version is the one of `rust-toolchain.toml`. Each command of the job gets its own PostgreSQL and LiveKit server in Docker; Cargo's registry and target directory stay in Docker volumes from one step to the next.
- The workflow has no permission by default. Each job gets `contents: read`. No job uses a secret, and the checkout keeps no credential.
- The runner images are named by version, not by `latest`.
- The Rust version is the one of `rust-toolchain.toml` (ADR 0014).

Jobs:

- Rust on Linux: the free disk space of the runner as in the deployment job, the build of the Linux image, then in it `cargo fmt --check`, `cargo clippy` of every target of the workspace with warnings as errors and with the bound on the stack of one function (ADR 0906), a workspace build that supplies the standalone server binary for the process tests, then the tests of the workspace with the private PostgreSQL of the container runner; in the image the container runner and packaging unit tests; in the image the check of the Linux packages (ADR 0754); then the generation of the API documents and the comparison with the committed files in the image, under the checkout owner.
- Rust on macOS and on Windows (`rust-other-systems.sh`): `cargo clippy` of every target of the workspace with warnings as errors, a build of every target of the workspace, and the tests of `junto-authz`, `junto-protocol`, the library and tools of `junto-client-core`, and the storage guard of the server library (`storage::`, whose reading of the free space differs between Unix and Windows, ADR 0605), which need no database. On macOS also the check of the condition waits (ADR 0786): `tools/check-condition-wait.sh` with the built client binary; and the unit tests of `junto-media`, which include those of the condition waits and the macOS-only tests of camera colour, camera capture settings and screen capture configuration. These tests open no device and request no permission. On macOS the signing, update and recovery checks of test bundles (ADR 0725, ADR 0726), and the first frame of the bundle of the client build: `packaging/bundle.py` assembles the debug programs `junto`, `junto-recover` and `junto-icon` into an unsigned `Junto.app` in the temporary directory of the job, and `packaging/check_start.py` starts its executable with an empty data directory, `--no-activate` and `--check-startup`, and requires exit code 0 and the line `Junto first frame rendered`; the window appears without taking the focus. On Windows every crate is built with the static C runtime (ADR 0753), and the check of the Windows package installs, starts, updates and rolls back the ZIP (ADR 0755). On both systems the window tests of the client, without and with the PostgreSQL build of the system (ADR 0916 on macOS, with the unit tests of `tools/with_native_postgres.py`; ADR 0912 on Windows). On Windows also the unit tests of `junto-media`, and the tests of the screen capture against the window of a fixture program (ADR 0706), whose window appears on the desktop of the account for a few seconds.
- Clippy runs in the job of each system, because Rust compiles the code under `cfg(windows)`, `cfg(unix)` or `cfg(target_os = "macos")` only on a system that matches, and the lints of code that is not compiled are not checked: the Linux job does not lint the Windows code and the macOS code, and a warning in either was found only in the build log of its own system. Each clippy step runs with `--keep-going`, so the log of one run shows the lints of every crate, also of the crates after the first crate with an error.
- Licences: `cargo deny check` with a stated version of the tool.
- Recording layout page: the locked packages without install scripts, the build, and the browser tests against a LiveKit server in Docker.
- Transcription worker: the locked packages with `uv`, `ruff`, `mypy`, and the unit tests.
- Images and deployment: the check of pinned versions, the linter for workflow files and the linter for shell scripts from pinned images, the rendered Compose files of every form, the builds of the server image and the link image, the test of the hand-over scripts, the tests of the recorder start script and of the entry, the start of the local form, which builds the worker image, a backup of a running server with a restore into an empty deployment (ADR 0902, ADR 0911), an upgrade from an earlier release with the way back (ADR 0911), and the start of the one-host form and of the two-host form on the runner. This job fetches the whole history, because the upgrade test reads the files of an earlier commit.

- The deployment job sets every Compose CPU limit variable from the processor count of the Docker host before starting any form. Deployment defaults stay unchanged; a recorder or worker default larger than the runner must not make container creation fail.

- `tools/serial.sh` uses `flock` where `lockf` does not exist, so that the scripts that call it run on Linux.

### Runners outside GitHub

GitHub Actions cannot be used for this project at present. CI runs on three machines of the project, started from a developer machine with `tools/ci/ci.sh`:

- **Linux host, over SSH.** `ci.sh run <commit>` pushes the commit to a bare repository on the host as the ref `refs/ci/<run>` and starts `tools/ci/run-jobs.sh` of that commit there with `setsid nohup`, so the run continues when the developer machine sleeps or the connection drops. Jobs: Rust on Linux, licences, the transcription worker, the recording layout page. The SSH alias and the CI directory of the host come from `JUNTO_CI_HOST` and `JUNTO_CI_DIR` in `.env.local`, which is not tracked.
- **macOS machine.** `ci.sh local <commit>` runs `run-jobs.sh` on the developer's Mac through `tools/serial.sh`. Jobs: Rust on macOS, and the images with the Compose deployment. The macOS job keeps the PostgreSQL download of ADR 0916 in `postgres` of the CI directory (`JUNTO_TEST_POSTGRES_DOWNLOADS`); the window of the bundle check appears on the desktop of the account until its first frame is drawn.
- **Windows machine, over SSH.** `ci.sh run <commit>` also sends the commit to a Windows 11 machine on the local network as a Git bundle with the ref `refs/ci/<run>`, together with the `run-jobs.sh` of the commit, and starts `run-jobs.sh` there in the Bash of Git for Windows. The machine keeps no repository: `run-jobs.sh` fetches the bundle into its clone and removes it. The run starts in the desktop session of the account through a scheduled task that `tools/windows/start-run.ps1` creates for that run; it is not a process of the SSH session, which Windows ends with the session, so the run continues when the developer machine sleeps or the connection drops. See "The desktop session of the Windows job" below. Job: `rust-windows`, which installs the Rust version of `rust-toolchain.toml` with rustup and runs `tools/ci/rust-other-systems.sh`: the job that GitHub ran on `windows-2025`, with the window tests and PostgreSQL of ADR 0912 and the check of the Windows package (ADR 0755). The SSH server of the machine starts commands in the shell of the account (Windows PowerShell); `ci.sh` sends every shell command on the standard input of the Bash of the setup, so no command passes through the quoting rules of PowerShell. The address comes from `JUNTO_CI_WINDOWS_HOST` and the CI directory from `JUNTO_CI_WINDOWS_DIR` (a folder such as `C:/junto-ci`); `JUNTO_CI_WINDOWS_USER` and `JUNTO_CI_WINDOWS_KEY` name the account and the private key when the SSH settings do not. All four are in `.env.local`.

`run-jobs.sh` fetches the objects of the commit into a bare repository of the run (`runs/<run>/commit.git`), with every reachable object copied, so the run does not depend on the source repository. Every run of a machine uses one checkout, `checkout` of the CI directory. After it has taken the run lock, the run fetches the commit with its history into that checkout, checks it out, and removes with `git clean -ffdx` every file that the commit does not hold, also those that an earlier run wrote; Git in a container reads only that repository. Only the locked part changes the checkout. Each Git step of the checkout reports its failure: the steps are joined with `&&`, because a shell runs a function in the condition of `if` without `set -e`, and an earlier version continued after a failed `git checkout`, so that its jobs tested the files of the earlier commit and the run recorded them for its own. Before the first job the runner checks that `HEAD` of the checkout is the commit of the run and that `git status --porcelain --ignored` shows nothing, and otherwise the run starts no job (`test_runner.py::CheckoutFailure`: an index that a power loss cut short, which makes `git checkout` fail while the last step succeeds, and a committed file whose content differs from what Git reads from it, a file with CR LF line ends that `.gitattributes` declares as text). Git compares the content of a file only when the time that its index records for the file is not older than the index itself, and otherwise trusts that time. The checkout records the time of each file that it writes, so the check found such a file only when the checkout wrote the file and the index within the same second; on the Linux host a checkout that crossed the start of a second passed the check (seen once in `rust-linux`). The runner therefore replaces the index with `git read-tree HEAD`, which records no times, before `git status`, so that Git compares the content of every tracked file in each run; the test dates the index one hour ahead before `git status`, as such a checkout leaves it. A run that was ended while Git wrote the checkout (a stop of Windows, which ends every process of the run, or a KILL) leaves the lock files of Git, such as `.git/index.lock`, and every later run would fail at the checkout. No other Git process uses the checkout while a run holds the run lock, so the locked part removes the lock files of `.git` before it writes, and when Git still fails it removes the checkout and creates it again (`test_runner.py::Recovery`, with a stale `index.lock` and with a damaged `HEAD`). It writes the files of the checkout only after it has taken the run lock; it takes the lock with `tools/serial.sh --inherited` and `tools/windows/lock.py` of the commit, which it reads from the repository of the run. The runs of a machine share the Cargo target directory, and Cargo treats a unit as up to date when its output is newer than its source files. A run that wrote its files and then waited for the lock while other runs built had files older than their output, so Cargo kept output compiled from other commits: on the Windows machine such a run printed a warning of a line that its commit had corrected, and the test of `junto-release` ran with the manifest directory of a removed checkout and failed. The files of a run that are written after the lock are newer than the output of every earlier run, because the lock is free only after every process of the earlier run has ended (below), and the containers of an earlier run that ended without its cleanup are removed before the files are written. Git rewrites only the files that differ from the commit of the earlier run, so Cargo rebuilds the units whose sources changed and keeps the others. The checkout has one path for every run because kept output holds the paths of the checkout that built it: `CARGO_MANIFEST_DIR` and `file!` are compiled into a binary. With a checkout per run, removed at the end of the run, a test binary that a later run of another commit kept named the checkout of an earlier run, which no longer existed, and the test of `junto-release` that reads its manifest directory failed on the macOS machine; with one path every compiled path names the current checkout. A checkout per run also gave every source file a new time in each run, so Cargo compiled every crate of the workspace again. The test is `test_runner.py::FixedCheckout`: two runs of two commits use the same path, keep the time of an unchanged file, rewrite a changed one, and do not see a file that the first run left. The clone has `core.autocrlf` off, because Git for Windows turns it on in its system settings, and the scripts and the files that tests compare must keep the line ends of the commit. It takes the run lock (one run at a time per machine: `tools/serial.sh --inherited`, on the Linux host and on the Windows machine with a lock file of the CI directory, on the macOS machine with the lock file of the other heavy commands of that machine, which `tools/serial.sh` names when `JUNTO_HEAVY_LOCK` is not set, or `JUNTO_CI_RUN_LOCK` for the tests of the runner; a `JUNTO_HEAVY_LOCK` of the caller is not used there, because two runs with two locks would write the one checkout at the same time. `--inherited` takes the lock with `tools/windows/lock.py` on every system. BSD `lockf`, which `tools/serial.sh` uses on macOS without that option, frees its lock when its direct child ends, while the processes that the child started can still run (checked on the macOS machine: `lockf -k L sh -c 'sleep 5 & exit 0'` frees `L` at once). `lock.py` and `lockf` take the same `flock` lock of the file, so the run and the other commands of the machine still exclude each other. The Bash of Git for Windows has neither `lockf` nor `flock`; there `tools/windows/lock.py` takes the lock with `LockFileEx`, which Windows releases when the process ends. On Windows `lock.py` starts a second copy of itself, the keeper, and returns its exit code. The keeper takes the lock and runs the run in a job object whose only handle it holds, with the limit `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. When the run ends, or when the first `lock.py` is ended from outside (the keeper waits for that process by its number and creation time), the keeper ends each process of the job through a handle of that process and waits until each handle is signalled, and only then exits and releases the lock; so the next run cannot run beside processes that are still ending, which can still hold files of the shared target directory. The count of active processes of a job and its message `JOB_OBJECT_MSG_ACTIVE_PROCESS_ZERO` do not show this: Windows removes a process from the count and from the process list of its job as soon as its end begins, before it has ended (measured on the Windows machine with a process whose end a debugger delays). The keeper reads the process list again until it is empty and every ended process has ended, so a process that an ending process started is ended as well. When processes remain 60 seconds after they were ended, the keeper writes their numbers to the error output (`runner.log` of the run) and keeps the lock until they end. When the keeper itself is ended from outside, the limit of the job ends the processes, and the lock is free while Windows ends them. On the other systems the command inherits the locked file, and the lock lasts until the last process that holds it has ended; a signal to `lock.py` while it waits for the lock ends it, and after the command has started the signal goes to the command), runs the jobs one after the other, and records each job in `runs/<run>/record.tsv`: commit, job, start and end in UTC, exit status, log file, seconds. `runs/<run>/current` names the running job; `runs/<run>/finished` holds the exit status of the run. At the end, also after a failure, it removes the repository of the run and every container and network whose name starts with `junto-ci-`.

**The processes of a job.** Each job runs through `tools/ci/group.py`, as a group of processes of its own: on Unix a session and process group, on Windows a job object named after the run and the job, which holds the child processes from their start. When the command of the job ends, `group.py` ends the processes of the group that remain, and waits until every one has ended; on Unix a process that has not ended 30 seconds after TERM receives KILL. When the run is ended by a signal, `run-jobs.sh` sends TERM to `group.py` (on Windows it ends the job object by its name with `group.py --end`, because a signal of the Bash of Git for Windows ends a native program at once), waits for it, and only then removes the containers of the run and checks the caches. The part of `run-jobs.sh` outside the lock waits for the lock program, which ends after the locked part, so the repository of the run stays until the locked part has ended, and `finished` is written once. On Unix a process that changes its process group (`setpgid`, as `Command::process_group` of Rust does, or a session of its own) leaves the group and is neither ended nor awaited; no job of macOS or Windows starts such a process (the server tests that start the transcription worker in a group of its own run in the Linux containers). The processes of a job hold the run lock: `lock.py` names its descriptor in `JUNTO_LOCK_FD`, and `group.py` passes it to the command, whose processes inherit it: the shells of the job, Cargo, rustc and the test programs. Two kinds do not hold it: a process that Python's `subprocess` starts, which closes the inherited descriptors (the packaging checks and the Python unit tests of the macOS job), holds it only through its Python parent; and a container of the deployment job is a process of the Docker daemon, which the runner removes with the sweep before the next checkout. So the lock lasts until the last process of the job has ended, also when the runner, `lock.py` and `group.py` are killed (the OOM killer, `pkill -9`), and also for a process that left the group; the cost is that such a process keeps the lock of the machine until it ends. A second signal while the runner cleans up, such as the INT that a terminal sends to every process of the foreground group, which reaches the locked part twice, is ignored, so the cleanup ends with the removal of the containers and the check of the caches. A run ended by a signal on Windows is ended by the keeper of `lock.py`, which ends every process before it releases the lock; the part outside the lock removes the repository of the run while the keeper ends them; the checkout is changed only by the next locked part. The tests are `tools/ci/test_group.py` and, for a run that is ended by TERM while a process of its job takes a second to end, `tools/ci/test_runner.py`; the Windows job object was checked on the Windows machine. `ci.sh status <run>` prints each job as passed, failed, running or waiting with its time, and copies the log of a failed job to `target/ci-logs/<run>/`. `ci.sh forget <run>` removes a run, its ref and a commit that no other ref keeps.

**A commit has passed CI** when each job of the list of each runner (Linux host, macOS machine, Windows machine) passed in the latest run of the commit on that runner that has the job (`ci.sh status <commit>` prints `passed`). Every run of a commit tests the same files, so a run of only the jobs that failed completes an earlier run; with the latest run of a machine alone, a commit whose jobs passed across two runs showed as incomplete, and the only way to complete it was a run of every job again. A failure of a later run of a job fails the commit also when an earlier run passed that job. A run that failed outside its jobs (before its first job, or with a status other than 0 when each of its jobs passed) fails each job that it decides. `ci.sh` writes the commit and the jobs of a run into its folder before it starts the runner, so a start that fails before the runner (a failed copy to the Windows machine, a locked screen) still names its jobs; a run whose jobs cannot be read has every job of its runner, so it is not passed and an earlier pass of the commit does not decide those jobs. A failed job keeps the verdict `failed` when another job has no run. Test: `tools/ci/test_ci.py::CommitStatus`.

**The Windows machine** is a Windows 11 machine that is also used interactively. `ci.sh setup-windows` copies `tools/windows/ci-setup.ps1` to it and runs it with Windows PowerShell 5.1; the script downloads each tool from its publisher at a pinned version, checks its SHA-256, and installs it below the CI directory. A tool whose installed version is the pinned one is left as it is; the version of rustup is read from rustup itself:

Python 3.12.10 is the last release of 3.12, the version of the Python image of `tools/ci/pins.sh`, with Windows binaries; later 3.12 releases are source only. The Build Tools are those of Visual Studio 2022 release 17.14; the build of every target, with the prebuilt WebRTC library of the call crate and the static C runtime of ADR 0753, passes with them. `tools/check-pins.sh` fails when a download of the script has no SHA-256. The Visual Studio installer places itself in `Program Files (x86)\Microsoft Visual Studio\Installer` and the Windows SDK in `Program Files (x86)\Windows Kits\10`, and registers the Build Tools instance; nothing else of the setup is outside the CI directory. rustup replaces itself with its latest release when it installs a toolchain, unless its self-update is off: the setup runs `rustup set auto-self-update disable` (stored in the `rustup` folder), and the job installs the Rust version with `--no-self-update`; `tools/check-pins.sh` fails without either. The script changes no system setting and no `PATH`, and does not restart Windows: when the Build Tools installer asks for a restart, the script ends with exit code 3 and does not restart Windows. The job sets its own `PATH` from these folders, the programs of Git for Windows and those of Windows, and the temporary folder `tmp` of the CI directory, which is emptied before and after the job; it uses no other program of the machine. Runs, logs and records are in `runs/` of the CI directory, as on the other runners.

**The desktop session of the Windows job.** The SSH server and the management service of Windows start their processes in session 0, whose window station is not interactive; gpui opens no window there (`cannot open windows while headless`), and the start check of the Windows package (ADR 0755) needs a window that draws its first frame. The window tests of ADR 0912 run on the test platform of gpui and need no session. Windows 11 has one interactive session at a time, so a CI account with a desktop of its own beside the desktop of the account that uses the machine is not possible. A run therefore starts in the desktop session of the account that `ci.sh` logs in with, which is that account: `tools/windows/start-run.ps1`, run elevated over SSH,

- refuses the start with exit code 2 and a message that names the reason when the account has no session other than session 0, when its session is disconnected, or when its screen is locked or Windows does not state whether it is locked (`WTSQuerySessionInformation` with `WTSSessionInfoEx`: the connect state `WTSActive`, and the flags `WTS_SESSIONSTATE_UNLOCK`; `WTS_SESSIONSTATE_LOCK` and `WTS_SESSIONSTATE_UNKNOWN` are refused), so `ci.sh run` fails at once instead of failing in the start check of the package; a start that is refused or fails before the run has written the file `started`, at any step, writes its message to `runner.log` and its exit code to `finished`, stops and removes the task of the run, and removes the bundle, so `ci.sh status` reports the run as failed and `ci.sh forget` removes it; a failure after `started` is written to `task.log` of the run, and the run goes on;
- creates a scheduled task `\junto-ci\<run>` with the logon type Interactive, which runs only while the account is logged on and stores no password, and with the rights of the account without elevation; its program is `start.sh` of the run in the Bash of the setup under `conhost.exe --headless`, so no console window appears;
- starts the task and waits at most 60 seconds for the file `started` of the run; without it the task is stopped and removed and the start fails with the result of the task;
- records the number and the creation time of the console host of the run in the file `process` of the run; the creation time is the value that `GetProcessTimes` returns, in UTC as Windows stores it;
- starts, through the process creation of the management service (`Win32_Process.Create`), a second copy of itself that keeps Windows from sleeping while the process of the run runs (`SetThreadExecutionState` with `ES_SYSTEM_REQUIRED`, a request that ends with that copy; no power setting changes), and then removes the task. The run cannot remove its own task, because Windows requires elevation to remove a task that an elevated process created. The result of the removal is in `task.log` of the run. When the console host was not found, no second copy starts and the task stays, so that its state shows whether the run runs. Each start also removes the tasks of earlier runs that have ended: the folder of the run no longer exists, it has `finished`, or `start-run.ps1 -Ended` states that the run has ended. The task of a start that runs at the same time stays. A task stays until a later start when the SSH connection drops between the creation of the task and the start of the second copy, when the console host was not found, or when Windows restarts while the second copy waits; such a task has no trigger and no stored password and does not run again.

A logoff, a restart or a shutdown of Windows ends the processes of a run before they write `finished`. For a Windows run without `finished`, `ci.sh status` asks `start-run.ps1 -Ended` whether the run still runs: with the file `process`, whether a process with the recorded number and creation time runs; without it, whether a start of the run runs or its task runs. When it does not run, the run is reported as failed ("ended without a result"), and `ci.sh forget` removes it. `ci.sh status` asks this before it reads the files of the run: a run writes its record and `finished` before its processes end, so a run that ends during the question is shown with its result. When the copy of the bundle and the scripts to the machine fails, `ci.sh run` writes the exit status to `finished` of the run and removes the bundle; when the connection ends during the start command, the run can have started, and `ci.sh run` names the run and leaves its state to `ci.sh status`. A run that the machine's sleep stopped continues after the machine wakes. When the screen is locked or the session is disconnected after the start, the run continues; the start check of the package then fails if the window cannot draw its first frame, with the time limit of that check. Whether it can was not tried, because a locked screen cannot be unlocked over SSH.

During step 5 of the package check the window of the installed `junto.exe --check-startup` appears without taking the focus, until its first frame is drawn (51 seconds after its start in the first run). The debug build asks for the DirectX debug layer, which the machine does not have; gpui logs the error `0x887A002D` and continues without it.

On the Linux host, a run has at most 8 processors and 12 GB (11 GiB) of memory over all of its containers, without swap. Jobs run one after the other, so the containers of one job are the containers of the run. Rust on Linux and licences: the build container gets 4 processors as a set (ADR 0750: a quota stops the threads of a test that measures sound in real time) and 8 GiB; PostgreSQL 2.75 processors and 1.5 GiB; LiveKit 1 processor and 768 MiB; the control container 0.25 processor and 128 MiB. Database work dominates the integration tests, so its budget includes the concurrent queries instead of reserving most processors for an idle test driver. Test data is prepared in bounded statements under the normal database limits (ADR 0904). The transcription worker: one container of 8 processors and 11 GiB. The layout page: a Node container of 6 processors and 9 GiB, which shares the host's network to reach the LiveKit container of `tools/with-test-livekit.sh` (2 processors, 2 GiB). A host with fewer than 8 processors gives each job its processor count. The uv program and the Docker command-line program come from their images in `tools/ci/pins.sh`, copied into the CI directory. Every Docker object of CI on the host has a name that starts with `junto-ci-`.

The Linux package startup check uses a headless Wayland display with the Pixman software renderer. Sway may detect a host driver through the process filesystem even though the container has no GPU device, so this private display uses `--unsupported-gpu` to bypass the hardware-driver refusal. The optional document portal can report that its FUSE mount is unavailable; X11 startup and the package checks do not require that mount. The AppImage runs in extraction mode, without a FUSE device or container privileges.

All Linux jobs that execute tests use `tools/linux/run-as-user.sh` to prepare their writable checkout and cache mounts and run the job as user and group 1000. The Rust container uses the same launcher as the transcription worker and the layout page. Before each command, the launcher changes entries with a different owner, including entries inside a volume left by an earlier root job, then drops user, group and supplementary group privileges with `setpriv`. Subsequent writes are owned by the test user. The layout job installs browser system packages as root before entering this launcher; browser installation, build and tests run as the normal user. Its supplementary group grants access to the mounted Docker socket used for its test service.

**Caches.** The caches of the Linux host are named volumes: `junto-ci-cargo` (Cargo registry), `junto-ci-target` (target directory and the installed cargo-deny), `junto-ci-uv` (uv cache and Python), `junto-ci-npm` (npm cache and the Playwright browser). On the macOS machine the caches are the Cargo target directory `cargo-target` of the CI directory and the BuildKit builder `junto-ci-deployment` of the deployment job; on the Windows machine they are that target directory and the Cargo registry `cargo/registry`. Cargo does not remove the files of earlier builds from a target directory, BuildKit keeps the layers and cache mounts of earlier builds, and Docker's local volumes have no size limit, so a cache grows with each run: on the Linux host the target volume grew from 17 GiB to 40 GiB in the 13 runs after it was emptied, and reached 74 GiB in the run before, with a cap of 60 GiB that was applied only after a run; the target directory of the Windows machine had 57 GiB. The disk of the macOS machine is also the disk of the developer's work, and a run that started with too little free space filled it.

`tools/ci/caches.py` keeps the caches within their limits. It runs in `run-jobs.sh` with the run lock held, before the first job of a run and after every process of its last job has ended, so a cache is never measured or removed while a job uses it:

- A cache above its size cap is emptied, before and after a run: such a cache holds the output of earlier builds.
- Before a run, the target cache is emptied when it holds output that this runner did not write. After each run `caches.py` writes a stamp into the target cache (`.junto-ci-runner`, with the version of the runner and the path of the checkout at which the jobs build: `/src` in the containers of the Linux host, `checkout` of the CI directory elsewhere). Before a run the target is emptied when the stamp is absent, names another version or path, or when a fingerprint file of Cargo in it is newer than the stamp. The `run-jobs.sh` of an older commit, or of a branch without the one checkout, builds into the same target directory from a checkout of its own, which it writes before its lock; Cargo would then keep that output in a later run of this runner, compiled from other files and naming another checkout. The runner of the commit under test is the one that runs, so the detection is in this runner, and it does not depend on the older ones. A run of this runner that was ended before its check after the run also leaves output newer than the stamp, and the next run empties the target: a cold build, but no wrong output. The check after a run writes the stamp only when the check before the same run examined the target (the file `cache-examined` of the CI directory names that run), so a run whose check before stopped with an error does not mark output that no check examined. The stamp cannot show output that a process outside the run lock writes during a run, because that output is older than the stamp of the run's end. On the Linux host and on the Windows machine every version of the runner takes the same run lock and ends the processes of a run before the lock is free. On the macOS machine an older runner takes the lock of `JUNTO_HEAVY_LOCK` of its caller and can run beside this one, so there the check before a run stops the run, and the check after a run writes no stamp, while a process whose command line names the target directory runs (the rustc of a build names it).
- Before a run, the free space that the run will use is estimated from the earlier runs of the machine. Each run records the free space at its start, after this check, and at its end, with the size of the target cache at its start, in `cache-history.tsv` of the CI directory; a line that a crash cut or that is not text is left out when the file is read. The use of a run is the drop of the free space during the run, and at least the growth of its target cache: when other work released disk during a run, the free space rose while the run built its target (on the macOS machine two runs without the target cache rose by 7 and 4 GiB while they built 21.5 GiB), and a use of 0 made the estimate 0. The estimate is the median of the uses of the last 5 runs that started in the same state (with the target cache, or without it), with the default of that state added until there are 3 values. The drops include the other use of the disk during those runs, which on the macOS machine is the work of the developer and of other builds; one run during which other work used much of the disk would, as the largest value, decide every later run, and with a free space below that use and the level the caches would be emptied before each of them, so that no later run with the caches is recorded. With the median one or two such runs do not decide; three of the last five do. A run counts as a run with the target cache only when its target at the start is at least half of its target at the end (for the run to come: half of the target at the end of the last recorded run); a run that starts with a small rest of the target builds nearly all of it, and counted as a run with the target it would add a large value to those runs. A run that is recorded without the target cache, because its caches were emptied, does not remove the records of the runs with it.
- When the free space less that use is at least the level, the caches stay. When it is not, and a run without caches would end with that much free space, every cache is emptied. Without a record of a run without caches, such a run is taken to fill the caches again to their present size and to use the space of a run with the target cache besides: emptying a cache that the run then fills again does not leave more free space at the end of the run, so the caches are then not emptied for the free space. Else the run starts no job: `run-jobs.sh` ends with status 1, `runner.log` names the free space, the use and the level, and `ci.sh status` shows the end of `runner.log` for a run that ended before its first job.
- After a run only the caps apply. The free space decides only before a run, at the free space of that time, which the other work of the machine changes.
- A size or a free space that cannot be read, or a setting that is not valid, ends the check with status 2 and a message; before a run the run then starts no job, and no cache is emptied for the free space.

An emptied cache is filled again by the next run, which then compiles from nothing, as a first run does. The limits are in GiB, each with a default, and a line `NAME=VALUE` in the file `settings` of the CI directory of a machine replaces a default; a line end CR LF and leading zeros are read, and an unknown name or a value that is not a whole number stops the check with a message that names the line: `JUNTO_CI_TARGET_CAP_GIB` (60, the target directory), `JUNTO_CI_CARGO_CAP_GIB` (8, the Cargo registry), `JUNTO_CI_UV_CAP_GIB` (4), `JUNTO_CI_NPM_CAP_GIB` (4), `JUNTO_CI_BUILDER_CAP_GIB` (40, the builder of the deployment job), `JUNTO_CI_FREE_GIB` (20, the free space that must remain at the end of a run), `JUNTO_CI_RUN_GIB` (10, the use of a run with the target cache while the machine has no record of one), and `JUNTO_CI_COLD_RUN_GIB` (40, the use of a run without the target cache while the machine has no record of one; a new machine or a removed history then needs the space of a build from nothing). Runs with the target cache used much less than runs without it: on the Linux host a run with a target volume of 40 GiB lowered the free space by 0.7 GiB, and on the Windows machine such a run grew the target directory by 4.1 GB, while on the macOS machine a run without the caches lowered the free space by 29.3 GiB. A default of the size of a run without caches would make a machine with less free space than that use and the level empty its caches before every run, so that it never records a run with them. The file is on the machine because the size of its disk and the other use of that disk differ for each machine. With these defaults the macOS machine keeps its caches while it has at least the level and the largest recorded use free at the start of a run. There the one recorded run that started without the target cache and without other work that released disk lowered the free space by 29.3 GiB, and the free space at the start of the recorded runs was 39.9 to 62.3 GiB; with the earlier rule, a free-space level of 60 GiB at the start of a run that emptied the caches after the run, the target directory was emptied after most runs. The cost of a cache that stays is its size on the disk between runs; the cost of an emptied cache is the time of a build from nothing.

On the Linux host the sizes and the free space are read in a container that mounts the volume, because the volumes are files of the Docker daemon. The builder of the deployment job is read with `docker buildx du --builder junto-ci-deployment` and emptied with `docker buildx prune --builder junto-ci-deployment --all --force`. On the macOS machine and on the Windows machine `caches.py` reads the size of a directory from the listing of each directory with `os.scandir`: `du` of Git for Windows opens each file, and after a build it took 11.5 minutes for 35 GB of new output while the run lock was held; the listing of the same directory took 1.4 seconds. Links and junctions are not followed. A file with several names, as Cargo creates them with hard links, is counted once on macOS. On Windows it is counted once for each name: `os.scandir` reads the listing with `FindFirstFileW`, which gives no file ID. The directory enumeration of `GetFileInformationByHandleEx` with `FileIdBothDirectoryInfo` gives the ID of each entry without opening the file and would count each file once; it is not used, because the double count, 7 % of the target directory on the Windows machine (37.2 GB against 34.7 GB of `du`), only makes the cap act a little earlier. Each measurement and each removal is written to `caches.log` of the run. The tests are `tools/ci/test_caches.py`: the decision with recorded runs, the settings, the size reader, and the script with sparse files and a program in place of `docker` that stands for the volumes and their disk, also through `run-jobs.sh` with a lock program that marks the time it holds the lock.

**The builder of the deployment job.** The images of the deployment job are built by a BuildKit builder of their own, `junto-ci-deployment`, with the driver `docker-container` and the BuildKit image `JUNTO_CI_BUILDKIT_IMAGE` of `tools/ci/pins.sh`; `deployment.sh` creates it when it is absent or has another image, and sets `BUILDX_BUILDER`, which `docker build` and Docker Compose use. `docker build` with this driver keeps its result in the cache of the builder only, so the job's `docker build` commands have `--load`; Compose places the images in the image store of the daemon itself. Its cache (the layers and the cache mounts of the server image, `/usr/local/cargo/registry` and `/src/target`) is a cache of the macOS machine above. The builder of the Docker daemon is shared with the other work of the machine and is never pruned by CI.

**Paths of the checkout in tests.** A test or a build script that reads a file of the checkout takes the directory of its package from the variable `CARGO_MANIFEST_DIR` at run time, which `cargo test` and Cargo's run of a build script set for the current checkout, and not from `env!("CARGO_MANIFEST_DIR")`, which holds the path of the checkout that built the binary. Cargo keeps a built binary when only the path of the checkout differs and the files of the checkout are older than the build, as with the checkout per run of an earlier runner, or a target directory that two worktrees share; the compiled path then names another checkout, which can have been removed. A test that needs a repository makes one in a temporary directory.

The images and deployment job runs on the macOS machine and not on the Linux host. Its image builds compile the workspace. The builder of the Docker daemon gives the RUN steps of a build no processor or memory limit, and a BuildKit builder in a container, which can be limited, needs a privileged container or seccomp and AppArmor off. The Linux build image of ADR 0750 uses no feature of BuildKit, so on the host `tools/linux/run.sh` builds it with the builder of Docker without BuildKit (`JUNTO_LINUX_BUILDER=limited`): each step runs in a container with the processor set and memory of the build container, and the build leaves no BuildKit cache, which Docker cannot remove for one owner only on a host whose disk other projects share. The image carries the label `junto-linux-image=junto-ci`; an image that a new build replaces is removed by that label.

The images that the jobs pull (`tools/ci/pins.sh`) keep the name of their registry and are run by digest; Docker gives a pulled image no other name unless it is tagged, and a tag would not stop a run by digest from pulling it again. `docker rmi` with each image reference of `tools/ci/pins.sh` removes them.

## Consequences

- An error that exists only with PostgreSQL on macOS or Windows is found by CI only when a window test reaches it; the other tests that need PostgreSQL run on Linux only.
- The tier of the call tests against a real LiveKit server, the tier with the real worker and its models, and the mutation tests of the layout page do not run in CI. They need a build of the test participant, the model files, and more time than a commit check has.
- The recording test of the deployment (`deploy/tests/recording.sh`, ADR 0910) does not run in CI. The storage guard starts a recording only with 13 GiB of free disk space (ADR 0605), and a hosted runner states 14 GB of disk, of which the images of the deployment take 5.3 GB without the cache of their builds. The recorder needs up to 3 CPU cores for the composite while the media server, the server and three test participants run, and a hosted runner has 4; a recorder that is short of CPU writes a file with holes (ADR 0602), so the test would fail without a defect. CI lints the scripts of the test.
- The licences of the Python packages and of the packages of the layout page are not checked by a tool in CI. The build of the layout page fails when a bundled package has no licence file, and `THIRD-PARTY.md` of the worker is kept by hand (ADR 0610).
- The Linux packages and the Windows package of each commit are built from debug builds of the client and checked; release builds and their publication are not part of this workflow. The macOS job starts the unsigned bundle of the debug build; the signed bundle of the product is checked by the manual release check of `packaging/check_release.py`.
- On GitHub, the Linux job builds the Linux image in every run; no cache keeps the image or the target directory between runs, so every run compiles the workspace. The runner of a private repository has two processors; the container runner starts one Cargo job for each processor of its set. On the Linux host the image and the volumes stay, and a run compiles what changed.
- A CI result on the project's machines is recorded on those machines only. A pull request shows no result; the person who merges reads `ci.sh status <commit>`.
- The images job on the macOS machine builds images for arm64; the images of the deployment for x86-64 are not built by CI while that job runs there.
- The Windows job runs on one Windows 11 machine with 4 processor cores and 16 GB of memory, not on a virtual machine with limits: a run uses the whole machine while it runs, at a lower priority (`nice`), beside the other programs of the account. The Windows virtual machine on the Linux host that this ADR first planned needs hardware virtualisation, which is off in the host's firmware and cannot be changed remotely.
- The Windows job needs the account to be logged on to the desktop of the machine, with the session connected and the screen unlocked, and during the start check of the package the Junto window appears on the desktop of the account until its first frame is drawn (51 seconds in the first run).
- The Linux image reads its packages from `snapshot.debian.org`. The job fails while that service cannot be reached.
- A new version of an action is a change of its commit hash in the workflow file.
- `cargo deny` is compiled in its job when the cache has no copy.
