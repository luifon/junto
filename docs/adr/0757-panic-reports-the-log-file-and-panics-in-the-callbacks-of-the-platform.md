# 0757. Panic reports, the log file, and panics in the callbacks of the platform

## Status

Accepted

## Context

In the first live test the macOS client ended three times. Each time a Rust panic in a listener of the window (the scroll of the message list) ran inside `handle_view_event` of `gpui-pre-macos`, an Objective-C method that AppKit calls. A Rust function with the `extern "C"` ABI cannot unwind, so the panic became `panic in a function that cannot unwind` and the process aborted. Twice the message of the panic was lost: the client wrote its log only to standard error, which an application that the system starts does not keep, and it recorded no panic.

The places where the platform calls gpui, and so the code of the application, in `gpui-pre` 0.3.8:

- macOS: the Objective-C methods of the window, the view and the delegate of the application (`gpui-pre-macos`), and the functions that the dispatch queues of the system call to run a task, on the main thread and on the background threads. All are `extern "C"`: a panic aborts the process.
- Windows: the window procedures of the windows and of the platform (`extern "system"`); the platform runs the tasks of the main thread from its window procedure and the background tasks from the callbacks of the thread pool (`extern "system"`). A panic aborts the process.
- Linux, X11 and Wayland: the event loop of the platform is Rust code. A panic unwinds to `main` and ends the process with the exit code of a panic. For the person the result is the same: the application ends.

No profile of the workspace sets `panic = "abort"`, and no build or packaging script passes it.

gpui takes values out of the state of the application while it calls the code of the application, and puts them back after the call: the count of the nested updates of the application and the flag of the flush of the effects, the window that an update of a window uses, the entity that an update of an entity uses, the global that an update of a global uses, the subscribers of an entity while their callbacks run, the global action listeners, the mouse listeners of the drawn frame, the layout engine during a layout, and the phase of a draw. The published version does not put them back when a panic unwinds through it. A panic stopped only where the platform calls gpui would leave an application that no longer runs its effects, has lost the window and the entity of the handler that panicked, and skips every later draw.

## Decision

### The report of a panic and the log file

- `junto_client::panics::install` sets the panic hook at the start of `main`, before the arguments are read. The hook runs on the thread that panics, before the unwind, and then calls the hook that was set before it, which writes the panic to standard error as before.
- The hook writes a report file into `panics/` of the data directory: `panic-<UTC time>-<process, 10 digits>-<number, 6 digits>.txt`, so that the names sort in the order of the reports. The file is made with `create_new`; the header (the build label of the version, the time, the system and the architecture, the name and identifier of the thread, the location and the message) is written and synchronized first, then the backtrace: the resolution of its symbols can take long or fail, and the header is on the disk before it. The backtrace is the one of `Backtrace::force_capture`, also in a release build. On Windows it is followed by the address of each frame with the base address of its module and the offset (see the next point); macOS and Linux do not give the base address, and their program holds its symbol table, from which the backtrace has the names.
- A Windows program resolves the names of a backtrace through its PDB. Measured on the Windows machine with a release build: with the release profile of the workspace (no debug information) the PDB holds only the public symbols, and the report named wrong functions (the function that panicked appeared as another function of the same crate); with line tables (`CARGO_PROFILE_RELEASE_DEBUG=line-tables-only`) it named the right ones. The PDB of the release `junto.exe` with line tables is 184 MB (51 MB compressed), against 71 MB for `junto.exe`. In the package it would have grown the ZIP from about 26 MB to 77 MB and each update archive, which is not compressed, from about 71 MB to about 255 MB, and the installation keeps two archives; DbgHelp can also hold the file open while the client replaces its folder in an update. So the package does not carry the PDB. The Windows release build sets `CARGO_PROFILE_RELEASE_DEBUG=line-tables-only` (`packaging/README.md`), `packaging/windows.py` writes the PDB as `Junto-<version>-windows-x86_64.pdb` beside the ZIP and refuses a build without it, and the release publishes that file with the ZIP (`docs/release.md`, ADR 0755). A report of an installed client then names no Junto function (the PDB is not on the machine) and lists for each frame the module base and the offset, which `llvm-symbolizer` resolves with the published PDB beside `junto.exe` under the name `junto.pdb` (`docs/client-windows.md`). Checked with the release test program on the Windows machine: `llvm-symbolizer` 22 on Linux resolved the offsets of its report to the function that panicked and its line. The debug builds and the other systems are unchanged; the line tables do not change the code of the program.
- The hook makes only the directory `panics/`, inside a data directory that exists. A panic before the client has made its data directory writes no file, so that the data directory is not made with the default permissions, which the client refuses (ADR 0710).
- The hook writes on the thread that panics, also on the thread of the window, which otherwise does not wait for the file system (ADR 0730): the report must exist before a panic that is not stopped ends the process, and a panic is not a part of the work of the window.
- The data directory of a report: the thread that opened the state of the application (`AppState::new`, the thread of the windows) uses the data directory of that state; every other thread uses the data directory that `main` names after the client has opened it. Before the data directory is known a panic is written to standard error only.
- Bounds: one process writes at most one report per location of a panic and at most 10 reports into one data directory; a later panic is still counted and shown, without a file. A new report removes the oldest beyond 20 in the directory. The hook still writes every panic to standard error.
- The log: the `tracing` output, without colour codes, goes to `logs/junto.log` of the data directory, at the level of `JUNTO_LOG_LEVEL` for every crate, or, when it is not set, at `info` for the crates of Junto (the targets that start with `junto`) and at `warn` for the other crates, such as the call library and gpui; standard error keeps its default level `warn`. When the file would pass 4 MiB it becomes `junto.log.1`, the earlier `junto.log.1` becomes `junto.log.2`, and the earlier `junto.log.2` is removed, so the log holds at most 12 MiB. A rotation that fails, for example while another program holds an earlier file open on Windows, is tried again after one second; until it works the file stays at its limit, the lines are dropped and counted, and the next line that is written states the count. The bytes per hour of a call were not measured.
- One process writes the log of a data directory. `main` opens it at the start, after `Client::open` has made the data directory, and the thread of the log holds an exclusive lock of `logs/lock` (`File::try_lock`) as long as the process runs. The client core holds no lock of the data directory after `Client::open`, so a second instance on the same directory can run; it does not get the lock and writes no log file, and says so on standard error.
- The lines given before the file opens, at most 256, are kept in memory and written first when it opens. Each start error is written to standard error and to the log at `error`, and `main` waits until the thread of the log has written it before the application quits. When no data directory opens, the error is written to `junto-start-failure.txt`, replacing an earlier one without following a link at its name: in the temporary directory of the account on macOS and Windows, and on Linux, where `/tmp` is shared by the accounts, in the runtime directory of the account (`$XDG_RUNTIME_DIR`), or else its cache directory. A program without a console, as the Windows program becomes, otherwise leaves no record of it. Every failed start (no data directory, the initialization of the application, or a main window that cannot open) goes through one function, `start_failed` of `main.rs`. It writes `junto cannot start: <reason>` to standard error and to the log; on Windows, when standard error has no reader after the attach to the console of the parent (no redirected stream and no console: a start from Explorer or from a pin), it also shows a message box of the system (`MessageBoxW`, error icon, title `Junto`) with the text `Junto cannot start.`, a blank line, the reason, a blank line, and `The reason is also in <path>.`, where the path is that of the start-failure file before a data directory opens and that of `logs/junto.log` after; the program ends when the person closes it. A start with a redirected standard error, as the checks and tests make, shows no box, so that no dialog stays open on the machine (ADR 0915). macOS and Linux show no box: the reason goes to standard error, the log and the file. The test target `start_failure` runs the program with a relative `JUNTO_DATA_DIR` and requires exit code 1, the reason on standard error and in the file.
- The thread that logs gives each event whole to a thread of the log, `junto-log`, which writes and rotates the file, so the thread of the window does not wait for the file system (ADR 0730). At most 4096 events wait for that thread; a later event, and an event that cannot be written, is dropped and counted, and the next written line states the count. Events that wait when the process ends are lost; the report of a panic does not depend on them.
- Nothing of either is sent over the network.
- The tasks of the state that follow a source for its whole life (the calls, the sound levels, the changes of the client core, the clock of one second, the retries of unreached servers and the panic reports) run each update through `update_once`. A panic in the update, such as one in an observer that the update notifies, ends that update only; the task waits one second and then reads its source again (a watch is marked as changed), so the state does not keep a view of the calls from before the panic. Without the stop the scheduler ends the task with the panic, and the window no longer followed the calls. The window test `panics::a_panic_while_the_calls_change_leaves_the_window_following_the_calls` makes the observer of the state panic in the update of a change of the calls and requires that a later change reaches the window.
- The notice: the hook sends each report to the states of the application that watch its data directory, over a channel. The state logs the 1st, 10th, 100th, and so on, report of each location at level `error`, and holds a notice with the count of the panics since the notice was last closed and the latest report. The task that takes the reports takes every waiting report into one update. A panic in that update (for example in an observer of the state that the notice runs) is stopped there, and the task then waits one second before the next reports: the hook sends a new report for that panic, and without the wait the task would update and panic again without returning to the event loop of the system. The shell shows it over the bottom of the main window, "An error happened in Junto, and the action that was running may not have finished. The report is in <path>.", with a button that closes it.

### A panic in a callback of the platform does not end the application

The workspace uses corrected copies of `gpui-pre` 0.3.8 and `gpui-pre-scheduler` 0.3.8 under `vendor/` (`[patch.crates-io]` of `Cargo.toml`; `vendor/README.md` lists each change). Of the platform crates only `gpui-pre-linux` is copied, for the activation of a window with a token (below).

1. **Stops at the entries.** Every callback that gpui gives the platform runs its body through `unwind::catch`, which stops a panic and gives the platform a fixed result: the callbacks of a window (frame request, input, resize, move, activation, visibility, hover, appearance, button layout, visual viewport, insets, close, the hit test of the window controls, the tab callbacks, should-close), of the application (open addresses, reopen, keyboard layout, thermal state, sleep, wake, quit, the response to a system notification) and of the menus. The results after a panic: an input event is not handled; the hit test finds no window control; should-close and quit return true, as when the application is gone; a menu command is not available. The methods of the text input handler, which the platform calls for typing and the input methods of the system, return an error, as for a window that is closed.
2. **Tasks.** The scheduler builds every task with `propagate_panic`. A panic of a task stops in `Runnable::run`, inside the function of the platform that runs the task; the code that awaits the task receives the panic, and the panic of a detached task is dropped. This covers the dispatch queue functions of macOS, the window procedure and the thread pool callbacks of Windows, and the event loop of Linux.
3. **The state of gpui is put back.** Each frame of gpui that takes a value out of the state while it calls other code puts the value back when a panic passes and lets the panic continue: `App::update` (the count of nested updates), `App::finish_update` (the flag of the flush; no effect runs while a panic unwinds), the update of a window (the window returns to the application), the update of an entity (the entity returns), the update of a global, `SubscriberSet::retain`, the global action listeners (in the dispatch of the application and in the dispatch of a window), the mouse listeners of the frame, `Window::compute_layout` (the layout engine), and the prompt and the dragged view of a window during their prepaint. A panic in a draw resets the draw: see below.
4. **Repeated failed draws.** After three draws of a window in a row that panicked, the window draws nothing, also when its views change, until the person presses a mouse button or a key in it, which allows one more draw. A view that panics at every render, the shell that draws the notice included, then makes three panics and not one per frame of the display. The stop of a callback logs the 1st, 10th, 100th, and so on, panic of each callback at level `error`.
5. **A list whose items do not fill it.** A list aligned at its end (`ListAlignment::Bottom`) starts items that do not fill it at its top, where the published version put them at its end; a list that its items fill is aligned at its end as before and follows new items at its end. The message list of the main area uses it (ADR 0740). This correction is not about panics; it is in this copy because gpui has no option for it. Test: `layout::a_short_message_list_starts_at_its_top`.

The stops are in gpui and not in the platform crates, because the platform reaches the code of the application only through the closures that gpui gives it, the input handler and the tasks; one copy covers macOS, Windows, X11 and Wayland, and the restore of the state of gpui is needed wherever the panic stops. A stop in each handler of Junto would miss the code of gpui elements, where the panic of the live test ran, and would need one at each of several hundred handlers. Ending the application and starting it again would end the call of the person and the state of the window.

### What a stopped panic can leave inconsistent, and what the application does

- The handler of the application stopped at the panic. Its entity holds the changes made before the panic and none after it; the application continues with that state. The notice tells the person that the action may not have finished.
- Borrows of a `RefCell` held by the frames that unwound are released by the unwind. In the live test the list held its state mutably during its scroll; that borrow ends with the unwind, and the next scroll borrows it again.
- The effects queued before the panic stay queued and run at the end of the next update; the effect that panicked does not run again.
- A draw that panicked: the frame drawn before stays on the screen with its hitboxes. The element states that the failed draw had moved to the next frame return to the drawn frame; the state of the element that panicked, and the states that its ancestors held while their children were drawn, are lost and start again at their defaults: for example the scroll offset of a scrolled area without a scroll handle goes back to the top, and hover, click and tooltip states start again. The message list keeps its position, which it holds outside the frames. The stacks that elements push and pop during a draw (element ids, text styles, content masks, element offsets, rem sizes, image caches, the opacity) are emptied, and so are the tooltip bounds and the requested scroll; without that, every later draw failed at an assertion of the deferred draws, and a later frame was clipped to the mask and moved by the offset of the element that panicked. The input handler that the failed draw had taken from the platform window goes back to it, so typing keeps working. A listener that the failed draw had moved out of the drawn frame is lost until the next draw; a mouse listener that is missing is skipped. The next draw renders every view again instead of reusing a view of the failed draw, at the next change of the window.
- The callbacks for the next frame of a frame that panicked are lost.
- A panic in a callback that C, C++ or Objective-C code calls in the media crate stops in the callback (`junto_media::callback::stop_panic`), which logs it and returns a fixed value: the sound data callbacks of cpal (CoreAudio on macOS, WASAPI on Windows), after which the stream delivers silence and is reported as failed; the listeners and the timer that PipeWire calls for a share on Linux, after which the other callbacks of that share do nothing and the share ends with the reason "a PipeWire callback of the share panicked" at the next tick of its timer (10 ms); the enumeration callbacks of windows and screens, the frame and close handlers of the screen capture, the source reader of the camera and the completion of the sound activation on Windows (COM); the delegate methods of the camera and of ScreenCaptureKit and the completion blocks on macOS, after which the camera or the share ends. The work that follows a stopped panic (the report of the failed sound stream, the end of the share or of the camera) runs under a stop of its own (`callback::after_a_panic`), because the fallback of `stop_panic` runs outside the stop of the body; a panic in it is logged as well, and the callback returns its fixed value. After a panic the macOS camera delegate drops the later pictures without running their body, as the cpal callbacks do, until the worker stops the session.
- Still aborting or ending the process, each after the report is written:
  - a panic in the start of the application (the closure of `Application::run`), where no window exists yet;
  - a panic in a `Drop` that runs during an unwind, which Rust aborts;
  - a panic in the code of the platform crates of gpui themselves (`gpui-pre-macos`, `gpui-pre-windows`, `gpui-pre-linux`), outside the closures of gpui, for example an `unwrap` in an Objective-C method before it calls the callback: these frames are `extern "C"` or `extern "system"`;
  - a panic in Rust code that the C++ of the call library calls through the bridge of `webrtc-sys` (`extern "Rust"` functions of cxx);
  - `pthread_cond_wait` and `pthread_cond_timedwait` of the media crate on macOS (ADR 0786), which end the process when the functions of the system are missing, by design.
- A panic on a thread that gpui does not run and that no C code called (the tokio threads of the client core and of the media engine) ends its task or thread as before.

### Activation of a window with a token of the system

A Wayland compositor gives the focus to a window only for an activation token that it issued, such as the token that a notification service obtains for a press on a notification. gpui 0.3.8 activates a window on Wayland only with a token that the window asks for itself, with the serial of its last press; without a recent press of the window the compositor does not honour it. The copies add `Window::activate_with_token` and `PlatformWindow::activate_with_token` in `gpui-pre`, whose default activates the window as before, and the Wayland window of the copy of `gpui-pre-linux` 0.3.8 gives the token to `xdg_activation_v1::activate` for its surface, or activates the window as before when the compositor has no activation. X11, macOS, Windows and the test platform keep the default. ADR 0752 states how the client takes the token of a press and the tests.

### Tests

- The panics of the window tests no longer reach the test. The harness of `crates/client/tests/app` counts the panics of the thread of the windows (`panics::panics_on_this_thread`, from the hook) and fails the test when its last window is dropped after more panics than the test expected (`Window::expect_panics`).
- `panics::a_panic_in_the_scroll_of_the_message_list_is_reported_and_the_window_continues` (`tests/app/panics.rs`, the test platform of gpui): the scroll listener of the message list panics, through the test hook `panics::test_support`, while the list holds its state. The test requires that the panic does not reach the test, the report file with the message, the location, the version and a backtrace through `feed_scrolled`, the notice in the window, then that the list scrolls and follows its end again and that the close button of the notice works. Without the copies of gpui the panic reaches the test.
- `native_panics` (`tests/native_panics/main.rs`, without the test runner, `JUNTO_TEST_NATIVE_PANICS=1`): the application on the run loop of the system with the main window of an empty data directory. A task on the thread of the windows panics; on macOS a press of the left button is then posted through `NSApplication postEvent:atStart:` and the handler of the end of the press panics inside the method of the view that AppKit calls, and a second press reaches the handler without a panic. After each panic it requires the report, the notice in the state, and a frame that painted the notice with the count of the panics and ended: a canvas of the notice counts its paints under `test-support`, a first frame callback reads the count before the draw of its frame, and a second callback, which runs before the draw of the next frame and so after the first frame was drawn and presented, requires a larger count and the expected count of panics. A frame callback alone runs before gpui decides whether to draw, so it did not show that a frame was drawn; with every draw after the first panic made to fail, the test fails. The macOS CI job runs it (ADR 0905); before this decision the process aborted at the first panic.
- `panics::a_panic_in_a_render_is_reported_and_the_window_draws_again`: a task arms the render hook of the shell and refreshes the windows; the draw at the end of its update panics. The test requires the notice, a message sent after the panic drawn at the end of the list, and no other panic. With the copies of gpui before the reset of the draw stacks, the next draw failed at the assertion of the deferred draws.
- `panics::a_render_that_panics_at_every_call_does_not_draw_at_every_frame`: the render panics at every call. The test requires three panics over twenty frames of the test platform with the notifications of the reports, then, after the render works again, that a press of the mouse makes the window draw the notice.
- `panics::a_state_observer_that_panics_at_each_change_lets_the_window_rest`: the observer of the state in the shell panics at each change; a task panics once. The test requires that the work of the window comes to rest, that the task of the reports paused exactly once and no task of the state paused twice, that the panics are the one of the test and one per paused task, and that the notice shows all of them once the observer works again. Each task that follows a source names itself when it pauses (`panics::test_support::paused_tasks`, test support only). Another task, such as the one of the changes of the client core, pauses too when its source changes while the observer panics, for example on an event of the server that arrives after the start settled. The test counted exactly two panics before and failed on the Windows machine with five; the failure message now names the tasks that paused. Without the wait of the task of the reports the work never comes to rest.
- `share::linux::connection::panic_tests`: a panic in a PipeWire callback of a share makes the later callbacks do nothing and ends the share with its reason.
- `gpui_panics::` (a view of the test with gpui alone, no draw between two presses): a panic in a mouse listener, in a subscriber of an entity, in a global action listener and in an update of a global; the second press must reach the same listener, subscriber, action listener or global.
- `gpui_panics::the_layout_engine_stays_after_a_panic_in_a_measure`: a leaf whose measure panics inside `compute_layout` during a draw that a task starts; the next draw must measure the view again with no other panic. `gpui_panics::the_text_input_handler_takes_text_again_after_a_panic_in_it`: the test gives text to a `PlatformInputHandler` of the window outside any update, as an input method does; the first replacement panics, and the second must reach the handler.
- The unit tests of `logs` check the rotation and the bound of three files, the limit of the file while a rotation fails and the count of the dropped lines after it works again, that a second log of the same data directory writes no file, and the lines given before the file opens. The unit tests of `panics` check that a report names the functions of its backtrace (run by hand with `--release` and the line tables on Windows; no CI job runs a Windows release build), that a report does not make the data directory, and one report per location.
- The native targets `frames`, `endurance`, `modes`, `rehearsal` and `native_panics` and the tool `junto-screens` fail when the count of the panics of the process (`panics::panics_in_this_process`) is not zero, and the library tests that open a window fail at a panic of their thread.

## Consequences

- The workspace keeps three more corrected copies. A new version of gpui replaces them only after the tests above pass with it; the copies are removed when a pinned upstream version stops a panic in each callback of the platform and puts its state back.
- A panic in a handler no longer ends the application, so a defect can stay unseen; the notice and the report file make it visible to the person, who can send the report to whoever runs the server.
- The paths of the log and of the reports are in `docs/client-macos.md`, `docs/client-linux.md` and `docs/client-windows.md`.
