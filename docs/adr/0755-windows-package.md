# 0755. Windows package

## Status

Accepted

The package is built and checked by the Windows job of CI only (ADR 0753, ADR 0905); no Windows machine outside CI ran it.

## Context

The client runs on Windows 11 on x86-64 (ADR 0705). The project buys no code-signing certificate (`docs/scope.md`, "Not planned"), so Windows treats every file of the package as coming from an unknown publisher. The client updates itself from signed releases (ADR 0724, ADR 0726). The requirements of a Windows package are an installation without administrator rights, the replacement of the program while it runs, a rollback, and a statement of what Windows shows to the person.

Windows lets a running program file be renamed and moved on its volume; it does not let the file be deleted or written. It refuses to rename a folder that holds a running program. Files that a browser downloads carry a mark of their origin ("Mark of the Web"), and Explorer gives the mark to the files that it extracts from a marked ZIP file.

The options:

- An MSI file: it can install for one account, but its upgrade cannot replace a running program without closing it, and its rollback exists only during the installation transaction, not as a later return to the previous version. It would need the WiX tool set in CI.
- An MSIX package: Windows installs it only with a signature from a certificate that the machine trusts. A self-signed certificate must first be installed into the machine's store of trusted people, which needs administrator rights.
- A setup program (NSIS, Inno Setup): it is one more unsigned program, and the update of the client would still be its own; it would only copy files.

## Decision

- The package is a ZIP file `Junto-<version>-windows-x86_64.zip` with one folder `Junto`: `junto.exe`, `junto-recover.exe`, the uninstall program `uninstall.exe` (ADR 0728), the description `junto-package.json` (format 1, version, system `windows`, package `directory`, architecture), and `licences\` with the licence of Junto and the licence file of the package (ADR 0801). The program has the static C runtime (ADR 0753) and no library of its own.
- The symbols of `junto.exe` are not in the package. The release build has the line tables of every crate (`CARGO_PROFILE_RELEASE_DEBUG=line-tables-only`), and `packaging/windows.py` writes its PDB as `Junto-<version>-windows-x86_64.pdb` beside the ZIP, which the release publishes as a file of its own; a panic report of the client is resolved with it (ADR 0757). Measured for a release build: the PDB is 184 MB (51 MB compressed) against 71 MB for `junto.exe`; in the package it would have made the ZIP about 77 MB instead of about 26 MB and each update archive about 255 MB instead of about 71 MB.
- The person extracts the folder into a folder of their account, such as `%LOCALAPPDATA%\Programs`. No step needs administrator rights or installs a service. The data directory is `%LOCALAPPDATA%\Junto` (ADR 0710).
- `junto.exe` is a program of the Windows subsystem (`windows_subsystem = "windows"`): Windows opens no console beside its window. Windows gives a program of the console subsystem a console window of its own when Explorer starts it. The program writes its log and its errors to standard error, which a parent can redirect; a command that writes a text for the person and opens no window (`--help`, `--version`, an argument error, `--rollback-update`, a start that fails before its window) first attaches to the console of the process that started it, when that process gave it neither a standard output nor a standard error. A parent that redirects the streams, such as the checks of the package, reads them unchanged, and the exit codes are those of the console program. `junto-recover.exe` stays a program of the console subsystem: it runs in a terminal.
- The program writes one key of the registry of the account at each start: the identity of its notifications (ADR 0742). `junto-recover.exe unregister` removes it.
- Taskbar: Windows groups a window and the pins of the taskbar by the application user model identifier. The process names `chat.junto.Junto` for its notifications, so its window is not the program file for the taskbar: a pin that Explorer made from `junto.exe` has the identifier that Windows derives from the path, and a start from it shows a second taskbar button. The main window therefore states, through the property store of the window (`SHGetPropertyStoreForWindow`, module `taskbar` of `junto-client-core`), the identifier, the relaunch command (the quoted path of the running `junto.exe`), the name `Junto` and the icon `junto.exe,0`; a pin made from its running taskbar button starts `junto.exe` and stays one button with the window. The window takes the properties away before it closes, at its close and at Quit, as Windows asks. A Start menu shortcut that carries the identifier was the other way: it is an entry that the package does not create, it needs the same interfaces of the shell for its property, and it does not change a pin made from `junto.exe`. Explorer keeps each pin of the taskbar as a shortcut in `%APPDATA%\Microsoft\Internet Explorer\Quick Launch\User Pinned\TaskBar`, and groups a pin with the windows that name the identifier of its shortcut. At each start the program, on a thread of its own in the multithreaded apartment of COM, gives each shortcut of that folder whose target is the running `junto.exe` and which names another identifier or none the identifier of the process (`taskbar::mark_pins`), so that a pin made from `junto.exe` in Explorer, also before an update, becomes one button with the window; shortcuts of other programs are not changed. The Windows test `taskbar::tests::a_pin_of_the_program_file_gets_the_identifier_and_other_pins_stay` writes two shortcuts in a temporary folder and requires the identifier on the one of the program only. Whether Explorer reads a changed pin at once or after it reads the folder again is not tested; `docs/client-windows.md` tells the person to pin the running Junto, and to unpin a pin that still shows a second button.
- The update archive holds the folder `Junto`. The installer replaces the entries of the installed folder one by one: each old entry moves into the staging directory, then each new entry moves into the folder. A failure moves the entries back; a failure of that return is reported, and the staging directory is kept because it holds the application.
- The replaced running program stays in the staging directory until it ends. A mark beside that directory lets the next update or rollback remove it (ADR 0726).
- Rollback: `.Junto.junto-update\record\previous\recover.exe rollback <folder>` beside the folder, with every instance closed.
- What Windows shows: at the first start of a program that was extracted from a downloaded ZIP file, Microsoft Defender SmartScreen states that it protected the computer from an unrecognized app; "More info" shows "Run anyway". Files that the client downloads and writes for an update carry no mark of their origin. With Smart App Control on, Windows does not run the program (ADR 0704).

Checks (`packaging/check_windows.py`, in the Windows job of CI):

- The ZIP of the client build: its entries, no library and no symbols, and the symbols file beside it; a licence file that lists every crate of the programs and holds the WebRTC licence; the icon group 1 of `junto.exe` with the rendering of the icon at each size (ADR 0756); the subsystem of the optional header of each program (Windows for `junto.exe`, console for `junto-recover.exe`); extraction into a folder; `junto.exe --version`; the first frame with `--check-startup`.
- The window of the installed program (ADR 0703), at its first start, so with the dialog of the first start open over the columns: through the messages that Windows sends to a window, with the cursor of the desktop at each tested point (gpui answers the hit test from the last pointer position, and Windows sends the window the position of the cursor when the window appears or changes its size under it; the check puts the cursor back afterwards), the hit test answers the close, maximize and minimize buttons and the caption at the points of the strip, and the client area below it; the top border in the top rows of the strip and over the close button, the top-right corner at the last column; the left, right and bottom borders and the bottom corners just outside the client area; maximized, the client area equals the work area of the monitor and the top row at the close button answers the close button; a double press on the caption maximizes and restores the window, the maximize button maximizes it and then restores it, the minimize button minimizes it, and the close button ends the program with exit code 0. Then the key of the identity of the notifications names `Junto` and the PNG file of the data directory, whose picture equals the rendering of 256 pixels (ADR 0756), and `junto-recover.exe unregister` removes it and succeeds again without a key. The check restores the key of the account as it was before the check, also after a failure.
- With fixture programs: an update from a local source while the installed program runs, the requests of the update, the new program in place, the mark of the staging directory; then the rollback with the recovery program, a changed archive and a second rollback refused, and no staging directory left.

- The real-client lifecycle (`packaging/check_lifecycle.py`, described in ADR 0725): two builds of the checkout with temporary test keys, the workspace version and its next patch version, in their own target directory. The first ZIP is extracted into a folder whose name holds a space and a character outside ASCII. The window of the installed `junto.exe` updates its own folder with `--update-source` and `--check-update` (ADR 0724, ADR 0780) while it runs, and the recovery program of the previous release record rolls the update back. At installation, after the update and after the rollback, the installed folder equals the package folder of the expected version file by file, and the client states its version and draws its first frame with a new empty data directory. The fixture test still covers replacement while another program of the folder runs.
- A start and `--version` have a bound of 120 seconds, the update one of 300 seconds (ADR 0725). Every command starts suspended, is put in a job object that ends its processes when the job closes, and then resumes; the job is ended when the command returns, so no program that it started keeps running. Error dialogs are turned off for the commands. Packages, profiles, keys and update records stay in the temporary folder. A virus scanner can keep a new program file open for a short time after its process ended, so the removal of the folder is tried up to 10 times, 3 seconds apart; a removal that still fails names the files that are left and fails the check.

## Consequences

- The setup program of ADR 0728 creates the Start menu entry and the entry of the installed programs; the ZIP file creates neither, and the person pins the running Junto to the taskbar. A taskbar pin made from Explorer on `junto.exe`, also one of an earlier version, gets the identifier at the next start (above), which changes only that shortcut of the account; a pin that still opens a second taskbar button is removed by the person, who pins the running Junto. That a pin of the running window, and a pin made from `junto.exe` after a start, start Junto and stay one button is checked by a person; a unit test sets and reads the properties on a window and takes them away. The program holds the application icon as its icon group 1 (ADR 0756): Explorer, an entry that the person creates and the windows of the program show it.
- An uninstallation is `uninstall.exe` of the folder (ADR 0728), which removes the registration of the notifications, the folder and `.Junto.junto-update` beside it, and the data directory only when the person chooses it; `junto-recover.exe unregister` still removes the registration alone. A key that stays after a removal of the folder without the first step names a picture of the data directory; `reg delete` removes it (`docs/client-windows.md`).
- Started from a terminal, `junto.exe` returns at once to the prompt of `cmd.exe` and PowerShell, because they do not wait for a program of the Windows subsystem; the text of a command that writes one appears after the prompt. PowerShell waits when the output is piped (`junto.exe --version | Out-String`).
- The replacement of the entries is not one step. Both lists of entries are read before the first move, and every return move is tried after a failure. When a return move also fails, the folder holds entries of both versions and the staging directory, which is kept, holds the rest; the error names it. The recovery program then can refuse, because the folder may have no description or one that differs from the record: the entries are moved back from the staging directory by hand. A crash between two moves leaves the same state.
- The SmartScreen warning appears at the first start of each new download, not after an update by the client.
- New direct dependencies on Windows: `windows` 0.62 in `junto-client-core` (the property store of a window, `taskbar`) and `raw-window-handle` 0.6 in `junto-client` (the handle of the main window). gpui uses both in these versions, so they were in the lock file already.
- The relaunch command is the program without arguments: a pin of a Junto started with `--data-dir` starts the default data directory (`docs/client-windows.md`).
