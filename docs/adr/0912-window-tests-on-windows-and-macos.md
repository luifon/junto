# 0912. Window tests on Windows and macOS and their database

## Status

Accepted

On macOS the steps ran on the macOS machine of ADR 0905 on 2026-10-19 with the macOS build of PostgreSQL 17.11: the 3 window tests without a database and the 132 with PostgreSQL pass (1 ignored, the rehearsal in two windows), without a correction of a test. The program started PostgreSQL in 8 to 11 seconds and, after a SIGTERM, stopped it and left no process.

The steps ran on the Windows machine of ADR 0905 on 2026-10-17: the 3 window tests without a database and the 97 with PostgreSQL pass (1 ignored). The two unit tests of `tools/windows` that had not run before failed there and were corrected: the version test read the PostgreSQL image from the workflow, where it no longer is (it is in `tools/ci/pins.sh`), and the test of a child that keeps the output of `pg_ctl` open left the child holding a file of the test's temporary folder, which Windows does not remove; the test now ends the child and waits for its end. Open: the server built for Windows stores no file, so on Windows no window test uploads, downloads or exports a file, and no window test shows a recording. The tests of `live::` need LiveKit and do not run on Windows.

## Context

The scope items "Client on Windows" and "Client on macOS" require that the client starts on each system and that its window tests pass there. The check of the Windows package (ADR 0755) already starts the installed `junto.exe` with `--check-startup` and requires exit code 0 and the line `Junto first frame rendered`; on macOS `packaging/check_start.py` does the same with a bundle (ADR 0725), and no CI job ran it or the window tests before this change.

The window tests in `crates/client/tests/app` open the window code on the test platform of gpui, whose text system draws no glyphs; they need no display and no GPU. Most of them start the server binary of the workspace on a database of their own, from the PostgreSQL that `JUNTO_TEST_DATABASE_URL` names. On Linux, `tools/with-test-postgres.sh` starts that PostgreSQL as a Linux container. The Docker engine of a Windows runner runs Windows containers only, and service containers of GitHub Actions run on Linux runners only. The macOS runners of GitHub have no Docker: their virtual machines on Apple processors cannot start the virtual machine that Docker needs for Linux containers. The runner image `windows-2025` has a PostgreSQL installed, but its version is that of the image and changes when the image changes. EnterpriseDB publishes a ZIP of PostgreSQL binaries for Windows and one for macOS of each version; the macOS ZIP holds programs for x86-64 and arm64, signed by EnterpriseDB, whose libraries are found relative to the programs, and the ZIP states the permission bits of each file.

The server opens and creates its files below a directory without following links, through `openat` with `O_NOFOLLOW` (`crates/server/src/recordings/files.rs`). On another system than Unix every such operation returns an error. Attachments, exports, backups and recordings use these operations.

## Decision

- The Windows job and the macOS job get their database from `tools/with_native_postgres.py`, one program for both systems; on macOS it replaces the Docker container of `tools/with-test-postgres.sh`, so that the job also runs on a runner without Docker. The program downloads the ZIP of binaries from EnterpriseDB for the system, of the version `JUNTO_CI_POSTGRES_BUILD` of `tools/ci/pins.sh` (the version of `JUNTO_TEST_POSTGRES_IMAGE` with the build number of EnterpriseDB), checks its SHA-256 against `JUNTO_CI_POSTGRES_MACOS_SHA256` or `JUNTO_CI_POSTGRES_WINDOWS_SHA256` of that file, keeps the checked file in `~/.cache/junto-postgres` and removes the ZIPs of other versions there. On GitHub the job saves the folder in its cache in a step before the tests, so that a failed test does not lose the download; the key of the cache is the SHA-256 that `--pin` prints. On the machines of ADR 0905 the folder is `postgres` of the CI directory, through `JUNTO_TEST_POSTGRES_DOWNLOADS`.
- The program extracts only `bin`, `lib` and `share`. It refuses an entry that leaves its folder: a part `..`, a colon, a backslash (Windows reads it as a separator, so `pgsql/bin/..\..\x` would leave the folder there) or a path that is not below the folder after its resolution; and an entry that the ZIP states as a link or another type than a file, and on macOS gives each file the permission bits of the ZIP without write permission for others; Python's `zipfile` would write every program without the permission to run it. For each run it creates a new data directory with `initdb` and starts the program `postgres` itself as a direct child process, on the loopback address, at a free port, without a Unix socket, with the settings of `tools/with-test-postgres.sh` and its output in the log of the server; `pg_ctl` is not used. It waits until `pg_isready` states that the server accepts connections, at most 120 seconds, and fails when the server exits before; a start that fails prints the log of the server. It runs the command with `JUNTO_TEST_DATABASE_URL` and then stops the server, also after a start that failed. The program never reads a process number from `postmaster.pid` and never acts on a number that it did not get from the start of its own child:
  - On Unix the server runs in a session and a process group of its own, whose number is the number of the server. Until the program collects the server, the system gives neither number to another process. The stop sends SIGINT (a fast shutdown) to the server, waits at most 30 seconds, sends SIGKILL to the process group of the server, which holds the server and its child processes, and then collects the server; it signals only while the server is not collected. Whether the server has exited is read with `waitid` and `WNOWAIT`, which does not collect it; `Popen.send_signal` is not used, because it collects an exited child before it signals. macOS refuses a signal to an exited server that is not collected, and to a group with only that server, with EPERM; the program then has no process left to signal. After the collection the program checks with signal 0 that no process of the group runs: a group number stays with its group as long as one member runs.
  - On Windows the server is created suspended, with a restricted token (the privileges removed and the groups Administrators and Power Users only for denial, as `pg_ctl` creates it, because PostgreSQL refuses to run with administrator rights), in a job object of its own with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, and resumed only after it is in the job, so each of its child processes is in the job. The program keeps the handles of the process and of the job. The stop ends the job with `TerminateJobObject` and waits at most 30 seconds until the job has no active process. When this program ends, Windows closes the job and ends its processes.
  - The stop fails when a signal or `TerminateJobObject` fails, or when a process of the group or of the job still runs; its error is printed, and the program then exits with 1, also after a command that passed. The removal of the directory of the run follows every result and every error of the stop.
- On Unix the server is in a session of its own, so the end of the process group of a CI job (ADR 0905) does not reach it. The first SIGTERM, SIGINT or SIGHUP that the program receives before its cleanup ends the command; the cleanup stops the server and removes the data directory, and the program exits with 128 and the number of the first signal. The start of the server and its record are not separated by a signal: a signal during the start is raised after the record. The cleanup first turns the signals into records, so a signal during the stop does not interrupt it. It runs once: when the signal ends the command, the cleanup of the `finally` runs and its result is kept; when a signal comes at the start of that cleanup, before the signals are records, the cleanup runs in the `except`. After the cleanup the program restores the default handling of the three signals and then reads the record, so a signal after that ends the program with the signal as its status.
- `tools/check-pins.sh` fails when the version of `JUNTO_CI_POSTGRES_BUILD` differs from the version of the CI image or when a system has no SHA-256. Unit tests fail when the server settings differ from those of `tools/with-test-postgres.sh`, when a pin is missing or malformed, and for each rule of the download, the extraction, the start, the stop and the signals; the tests of the stop start a Python program with a child process as the server, check that both end, that a server that ignores SIGINT ends with its group, that every signal goes to the number of the own child, and that a process named in `postmaster.pid` is never signalled; they run in the macOS job and the Windows job. `tools/ci/test_job_steps.py` runs `tools/ci/rust-other-systems.sh` with programs in place of `cargo`, `python3` and `uname` that record each command, and fails when the macOS job does not run the window tests with PostgreSQL and the start of the bundle, or when a job leaves out other window tests than those stated here.
- Both jobs run the window tests in two steps: `updates::` without a database, and the other tests with the database. The second step leaves out `live::`, which needs LiveKit. On Windows it also leaves out `recordings::`, and the four tests of `messages::` and the one of `admin_pages::` that store a file on the server. The server reads the free space of its directories on Windows (ADR 0605), so an upload there passes the storage guard and is refused by the file operations. On macOS the server stores files, and these tests run.
- The harness of the window tests sends the log of the client into the output of each test, at the level of `JUNTO_LOG_LEVEL` and `info` without it. The test runner prints that output for a test that fails, on every system.

## Consequences

- The tests on macOS and Windows use the PostgreSQL version of the tests on Linux. A change of the CI image needs a new build number and two new sums in `tools/ci/pins.sh`.
- The first run of a new version downloads 340 MB on Windows and 437 MB on macOS; the next runs read the cache. Each run extracts the programs into a new directory.
- On Unix a SIGKILL of `tools/with_native_postgres.py` alone leaves its PostgreSQL running with its data directory; the CI jobs send SIGTERM first (ADR 0905). On Windows the end of the program closes the job, which ends the server.
- The Windows code of the start and the stop (restricted token, job object) runs only on Windows; its unit tests run in the Windows job.
- Whether the macOS runner of GitHub draws the first frame of the bundle was not tried; GitHub Actions is not used at present (ADR 0905).
- A new window test that stores a file on the server fails on Windows until it is added to the list of left-out tests: `messages::files_attached_before_a_send_are_in_the_message_in_the_order_of_their_drops` failed there with the refused upload before it was added.
- The server is not made to store files on Windows for these tests. A server with file operations for Windows, or a server for Linux that the Windows job can reach, would let the tests of files and recordings run there.
