# 0916. Window tests and the start check on macOS

## Status

Accepted

The macOS job ran these steps on the macOS machine of ADR 0905 on 2026-10-19 and 2026-10-20: the start of the bundle passes, and the 3 window tests without a database and the 132 with PostgreSQL pass (1 ignored, the rehearsal in two windows, which needs LiveKit), without a correction of a test. On the same machine, with PostgreSQL 17.11 for macOS, a run ended by SIGTERM left no process, no directory and no shared memory segment; a postmaster stopped with SIGSTOP was ended by SIGKILL after SIGINT and SIGQUIT had no effect, its child processes ended after it, and its segment was removed.

## Context

The scope item "Client on macOS" requires that the client starts on macOS and that its window tests pass there. Before this decision the macOS job of ADR 0905 ran no window test, and no check started the packaged application. `packaging/check_start.py` starts the executable of a bundle with `--check-startup` (ADR 0725), and Windows runs its window tests against a PostgreSQL build for Windows (ADR 0912).

The window tests in `crates/client/tests/app` open the window code on the test platform of gpui and start the server binary of the workspace on a database of their own, from the PostgreSQL that `JUNTO_TEST_DATABASE_URL` names. The macOS runners of GitHub have no Docker: their virtual machines on Apple processors cannot start the virtual machine that Docker needs for Linux containers, so `tools/with-test-postgres.sh` cannot run there. EnterpriseDB publishes a ZIP of PostgreSQL binaries for macOS of each version, with programs for x86-64 and arm64, signed by EnterpriseDB, whose libraries are found relative to the programs; the ZIP states the permission bits of each file.

PostgreSQL stops in this order: SIGINT to the postmaster is a fast shutdown, in which the postmaster ends its child processes; SIGQUIT is an immediate shutdown; SIGKILL ends the postmaster alone. Each child process of PostgreSQL calls `setsid()` and is in a session and a process group of its own, and ends when it sees that the postmaster has ended. After a SIGKILL the postmaster leaves `postmaster.pid` and its System V shared memory segment, whose key and identifier are line 7 of `postmaster.pid`; PostgreSQL itself decides from the number of processes attached to that segment whether a data directory is in use.

## Decision

- The macOS job runs, after the signing and update checks:
  - the start of the bundle: `packaging/bundle.py` assembles the debug programs `junto`, `junto-recover` and `junto-icon` into an unsigned `Junto.app` in the temporary directory of the job, and `packaging/check_start.py` starts its executable with an empty data directory, `--no-activate` and `--check-startup`, and requires exit code 0 and the line `Junto first frame rendered`. The window appears without taking the focus;
  - the window tests in two steps, as on Windows: `updates::` without a database, then the other tests with PostgreSQL. The second step leaves out only `live::`, which needs LiveKit; the server stores files on macOS, so the tests of files and recordings run.
- The database comes from `tools/with_native_postgres.py`. It downloads the ZIP for macOS of the version `JUNTO_CI_POSTGRES_BUILD` of `tools/ci/pins.sh` (the version of `JUNTO_TEST_POSTGRES_IMAGE` with the build number of EnterpriseDB), checks its SHA-256 against `JUNTO_CI_POSTGRES_MACOS_SHA256` of that file, keeps the checked file in `~/.cache/junto-postgres` and removes the ZIPs of other versions there. On the macOS machine of ADR 0905 the folder is `postgres` of the CI directory, through `JUNTO_TEST_POSTGRES_DOWNLOADS`. On GitHub the job keeps the folder in its cache in a step before the tests, with the SHA-256 that `--pin` prints as the key.
- The program extracts only `bin`, `lib` and `share`, and gives each file the permission bits of the ZIP without write permission for others; Python's `zipfile` would write every program without the permission to run it. It refuses an entry with a part `..`, a colon or a backslash, an entry whose path is not below the folder after its resolution, and an entry that the ZIP states as a link or another type than a file.
- For each run it creates a new data directory with `initdb` and starts the program `postgres` itself as a direct child process, in a session of its own, on the loopback address, at a free port, without a Unix socket, with the settings of `tools/with-test-postgres.sh` and its output in the log of the server; `pg_ctl` is not used. It waits at most 120 seconds until `pg_isready` states that the server accepts connections, and fails when the server exits before; a start that fails prints the log of the server. It runs the command with `JUNTO_TEST_DATABASE_URL`, and then stops the server, also after a start that failed.
- The stop follows the order of PostgreSQL: SIGINT, then SIGQUIT, then SIGKILL, each to the postmaster only, each only while it runs, each followed by a wait of at most 30 seconds. No process group is signalled, and no process number is read from a file. The program collects the postmaster only after its last signal: until then the system gives its number to no other process. Whether it has exited is read with `waitid` and `WNOWAIT`, which does not collect it; on macOS `waitid` with `WEXITED` also reports a stopped child, so only an exit counts. `Popen.send_signal` is not used, because it collects an exited child before it signals. macOS refuses a signal to an exited child that is not collected with EPERM, which then means that the postmaster has ended.
- After the collection the program waits at most 30 seconds until no process uses the data directory: the port refuses connections and no process is attached to the segment that `postmaster.pid` names, as `ipcs -m -o` states it. It then removes that segment when `postmaster.pid` still names it. When a process still uses the directory, or a signal fails, the program prints the error and exits with 1, also after a command that passed. The removal of the directory of the run follows every result and every error of the stop.
- The first SIGTERM, SIGINT or SIGHUP that the program receives before its cleanup ends the command; the cleanup stops the server and removes the data directory, and the program exits with 128 and the number of the first signal. The start of the server and its record are not separated by a signal: a signal during the start is raised after the record. The cleanup first turns the signals into records, so a signal during the stop does not interrupt it. It runs once and keeps its first result; when a signal comes at the start of the cleanup of the `finally`, before the signals are records, the cleanup runs in the `except`. After the cleanup the program restores the default handling of the three signals and then reads the record, so a later signal ends the program with the signal as its status.
- `tools/check-pins.sh` fails when the version of `JUNTO_CI_POSTGRES_BUILD` differs from the version of the CI image, or when the SHA-256 is absent. The unit tests of `tools/with_native_postgres.py` run in the macOS job before the database step. The tests of the stop use a Python program as the postmaster with one child process in a session of its own that ends when the postmaster has ended; they record, at each signal, its number and whether the postmaster was collected, and fail when a group is signalled. `tools/ci/test_job_steps.py` runs `tools/ci/rust-other-systems.sh` with programs in place of `cargo`, `python3` and `uname` that record each command, and fails when the macOS job does not run the window tests with PostgreSQL and the start of the bundle, or when a job leaves out other window tests than ADR 0912 and this decision state.

## Consequences

- The tests on macOS use the PostgreSQL version of the tests on Linux. A change of the CI image needs a new build number and a new sum in `tools/ci/pins.sh`.
- The first run of a new version downloads 437 MB; the next runs read the cache. Each run extracts the programs into a new directory.
- A SIGKILL of `tools/with_native_postgres.py` alone leaves its PostgreSQL running with its data directory; the CI jobs send SIGTERM first (ADR 0905).
- A child process of PostgreSQL that is stopped and does not see the end of the postmaster keeps its segment attached; the program then fails after its wait and leaves that process.
- Whether the macOS runner of GitHub draws the first frame of the bundle was not tried; GitHub Actions is not used at present (ADR 0905).
- The signed product bundle is not started by a check (ADR 0725).
