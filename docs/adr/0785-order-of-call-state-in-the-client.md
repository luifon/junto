# 0785. Order of call state in the client

## Status

Accepted

## Context

Call state reaches the client through snapshots, events, join answers, token renewals and own-call reads. Arrival order does not establish the order of the state they describe. Replaying an included event over a newer HTTP answer can restore an obsolete participant, block or meeting state. A microphone block that a token renewal returned was removed by an older state of the client, a read of the own call rolled blocks back, and a meeting grant was lost when its notice was discarded.

## Decision

Every writer compares the cursor of its observation (ADR 0519) with the last accepted cursor for that call in the same epoch. An older observation cannot replace a newer one. A read of the own call replays only later events; an included event delivered after the answer cannot change the call fields already described by that answer. Effects on other collections and speaking marks, which the call answer does not include, continue to follow their own event history.

A call read may be ahead of the stream without advancing the stream cursor. Membership and pending moves still use the stream cursor; call participants, blocks and meeting state use the call cursor (`ServerModel::call_cursor`). A later call read does not turn older membership into a current observation.

The media session applies the same rule to join answers, renewal answers and the live model. Admission and participant actions require the server to list the current seat in state at least as new as its join answer; until then the microphone and the sound of the call stay closed on the device. Restrictive controls are applied before a renewed media connection can send or play sound. Another epoch is reconciled as another history, not compared by its numeric position: the session asks the client core for a snapshot that is requested after the question (`LiveServer::refresh`) and continues from it.

The answer to a request for a new token (a renewal answer) is a writer like the others, and it carries the state of the person at its cursor. The rule for it:

- An answer with a cursor of the same epoch, for the seat that the session holds, changes no admission. When its position is at or after the last accepted one, its blocks are applied at once, and the state and the events of the stream up to its position do not change the blocks. The end of a microphone block follows the rule for the end of a block below. When its position is before the last accepted one, it changes nothing but the token.
- An answer for another seat, an answer of another epoch, an answer without a cursor, and an answer that does not tell the blocks (ADR 0517) end the admission: the microphone and the sound stay closed until a state lists the seat. The session uses the seat of the answer in each of these cases, also for another epoch: a seat that the server gave and that no device uses would stay. The exception is a seat that the rule for a renewal after an end below voids: the session gives that seat up with a leave request.
- The fields of the renewal answer that this rule depends on, each read in the transaction that reads the cursor (ADR 0519): the microphone block of the person with its reason, which is the block of a moderator or the block of meeting mode (`microphone_block`); the meeting of the call with its presenter (`call.meeting`), from which the session derives a grant when the block that it held is absent; the sound block (`sound_block`); and that the seat of `identity` exists at the cursor, which the server checks before it gives an answer with a cursor.
- An answer for a call that hides who is inside tells none of these until the server has seen the device in the room (ADR 0517). A seat that the state of the client listed was seen, so an answer for an admitted seat tells them.
- An answer of a join or of a renewal with a cursor states that the person is inside with its seat at that cursor. It is the membership of the person at that position: while the stream is live and its state is from before that position, the place is held, and a media connection that fails is followed by a request for a token. A state at or after that position is the membership in its place. An event at or before that position does not end the place; an event after it that ends the place ends it, also when the answer arrives after the event. While the stream is interrupted, an answer decides nothing (ADR 0734). The floor for membership and moves is the position of that answer, not the position of a later read of the call.

The answer of a read of the own call says whether the admission check of the server has seen the seat of the account (`inside`, ADR 0517). The state holds that statement with the identity of the seat (`ServerModel::own_seat`) as an observation at the position of its answer: an event of the call at or before that position does not change it, and an event after it that lists the account in the call ends it. A change of the own call ends it at any position, and the state reads the own call again. An answer that does not say it states nothing, which is not "outside". The media session does not admit a seat that the state lists while the state holds "not inside" for that seat; without the statement it decides by the list of the call, as for a server from before the field.

The hide setting of a call that the state holds is the one that the server stated with the call. The event of the start of a call states the setting that the call keeps (ADR 0517): the state uses it for a call that it does not hold and corrects a call that it holds. For another event of a call that the state does not hold, the setting is the one that the own call of the account states when it is that call, and otherwise the setting of the channel. A server from before these fields states none, and the state uses the setting of the channel as before.

A device that has its account and no session, while the client core logs in again (ADR 0787), keeps its call as while the event stream is interrupted (ADR 0734): the admission and the blocks stay as the last state told them.

Notices that require an action by the person remain observable even when a newer model was published first. In particular, a meeting grant that requires the person to reopen the microphone cannot be discarded by refreshing the model (ADR 0739). The session reads the meeting of its call from the events in their order, and a grant closes the person's microphone setting once: its local mute effect remains until an explicit user action, including when meeting mode ends afterwards, and a grant that arrives after the person has opened the microphone again for the same position does not close it again. A state that shows the end of a block tells the same grant as the event of that end. The session holds the position of the last state that showed the block: when the person was told a grant after that position, or opened the microphone after it, a later state without the block does not close the microphone again.

The end of a microphone block. A state, or an answer, that no longer shows a block that an earlier state or answer showed does not tell how the block ended. When it still shows meeting mode of another presenter, the end is a grant, as above. When it shows no meeting, the block ended in one of two ways, and only the events tell which: the presenter let the person speak and meeting mode ended after that, or the block ended without a grant (meeting mode ended, or a moderator removed the block). A state from after both events is the same in the two cases. The rule:

- The block holds on the device, and the view of the call shows it, until an event after the last state that showed the block shows the seat without the block, or tells the end of meeting mode, which removes every block (ADR 0512). The event of a grant closes the person's setting, and the block ends when that event is read, also while the state of the stream is behind the answer that showed the end. An open that waits is the safe direction; in the usual order the event is read a few milliseconds after the state.
- The session reads the block of the person from the events as the state of the client does: the start of meeting mode by another person blocks the person without an event of the person (ADR 0719), so the end of that block by the presenter is a grant.
- The person was told a grant, or opened the microphone, after the last state that showed the block: nothing is waited for.
- The events of that time were not delivered: the reader of the notices was too slow and missed some, a snapshot replaced the state, or the events lie between the answer that gave the seat and the moment from which the session reads notices. The end of the block is then taken as a grant: the person's setting becomes "closed" once, and the person opens the microphone. After missed notices this holds for a block that ends before the next event is read. It holds also for a block that the events told and that no state showed to the session. The state that shows the end is then what the session knows of the block and of the meeting, so the next event of the person is not read as the same grant again.
- A block that an answer without a cursor told has no position among the events, so its end cannot be put in order with the event of a grant. Its end is taken as a grant too: the setting is closed once.
- Whenever the setting is closed because the end of a block could not be read, the person is told so (`MicrophoneClosed::EndOfBlockNotRead`).

A block that began and ended inside events that the device did not get is not known to the device, and nothing is closed for it. The state of the server does not hold a grant.

A renewal after an end. A request for a new token is a join. When the seat has ended, the server gives a new seat to a person who may enter the channel, whatever ended the earlier seat (ADR 0510). The session continues a call at another seat only when the server ended the earlier seat because no media connection used it. The rule:

- While a request for a place runs, an event that the account is in no call, with the reason `connection_lost` or `never_connected`, decides nothing: the answer can name a new seat. An event with another reason, or without one, ends the call at once (a removal by a moderator, the end of the access, the end of the call). The answer that arrives later is taken by no session, and the seat that it gave is given up.
- A seat of the account on another device ends the call with "elsewhere", also while a request for a place runs: in the state, or in an event after the last sign of the seat of this device, whatever a state shows. An event of another device from before any sign of the seat of this device ends nothing. Another seat on this device is the one of the request and ends nothing. The state and the event name the device of a seat.
- The answer of a renewal that gave another seat holds its position. An event at or before that position that the session reads after the answer, and that tells an end with another reason than the two above, or a seat on another device, voids the seat: the call ends with that reason, and the session gives the seat up with a leave request that names it. This is the exception to "an event at or before that position does not end the place": that sentence orders observations of one seat, and this rule is about a seat that the request should not have made.
- When events were not delivered (missed notices, or a snapshot that replaced the state) after a state last showed the seat and before the answer of the renewal, or before the events have passed the position of that answer, a seat that the renewal gave is void: why the earlier seat ended is not known. The call ends with the reason "not read" (`EndReason::NotRead`), and the person is told that.
- Until the events have passed the position of the answer, the seat is not admitted, also when a state lists it: the microphone and the sound stay closed, and the camera is not published at it (ADR 0794). Events that the session read before the answer count.

The server still makes the seat for the time between the request and the leave, and for a seat on another device the request takes the seat of that device. Only a request that names the seat that it renews avoids both.

An answer without a cursor comes from a server from before ADR 0519, and from a current server when the seat or the call had ended before the second read of the join, or when the server could not complete that read (ADR 0519). The client uses it as before that ADR: the client core applies again every event that arrived during a read of the own call, and the media session takes the answer as read at the position of the state that the client holds when the answer arrives. Such an answer has no order with the events.

## Consequences

A delayed model cannot erase a returned block, and a delayed answer cannot erase a newer block. Deterministic tests deliver answers and events in both orders and check capture, playout, admission and the local setting after a meeting grant: `calls::ordering_tests` in `crates/media`, `stream::tests::refresh` in `crates/client-core`. Snapshot replacement remains recovery for unavailable history, rather than the routine way to order token renewals.

A device shows that the person is entering, with the microphone and the sound closed, while the server says that it has not seen the seat, also when a list of the call names the seat. Tests: `model::tests::what_the_server_says_of_the_own_seat_is_held_until_an_event_lists_the_account`, `model::tests::a_call_takes_the_hide_setting_that_its_start_or_the_own_call_states` and `stream::tests::refresh::what_an_own_call_answer_says_of_the_seat_is_ordered_with_the_events` in `crates/client-core`, `calls::ordering_tests::a_seat_that_the_server_says_is_not_inside_is_not_admitted` in `crates/media`.

A call has no sound on a device while the state of the client does not list its seat, which includes the time in which the event stream of the server is interrupted at the start of a call, and the time after a renewal answer for another seat.

A renewal for the same seat does not interrupt the microphone and the sound beyond the time of the request: the stream of a device moves its cursor without an event of its own only at a checkpoint, 25 seconds apart, and the session does not wait for it.

A microphone whose block ended opens when the event of that end is read, not when a state or an answer shows the end. While the event stream is interrupted the block holds on the device. A person whose device missed notices, or loaded a snapshot, in the time in which a block ended finds the microphone setting closed, with a sentence that says why; so does a person whose block from the answer of a join ended before the session read notices. Tests: `a_grant_stays_closed_before_its_notice`, `the_end_of_meeting_mode_opens_the_microphone_when_its_event_is_read`, `a_block_of_a_moderator_ends_when_its_event_is_read`, `a_block_whose_end_was_not_told_closes_the_setting`, `events_after_a_loss_are_read_as_before`, `a_block_that_ended_before_the_notices_were_read_closes_the_setting` and `the_person_who_opens_the_microphone_ends_the_wait_for_the_end_of_a_block` in `calls::ordering_tests`.

A person whom a moderator removed while a request for a new token was on its way is out of the call on the device, and the device gives up the seat that the request made. The other people can see that seat for a moment. Tests: `a_pending_renewal_cannot_undo_a_removal`, `a_seat_given_by_a_renewal_after_a_removal_is_given_up`, `a_renewal_continues_after_the_server_ended_a_seat_without_media`, `a_renewal_does_not_take_the_call_back_from_another_device` and `a_renewed_seat_is_void_when_events_were_lost` in `calls::ordering_tests`, and `a_renewal_that_waits_does_not_bring_a_removed_person_back` in `crates/media/tests/calls`.

The speaking marks of a call follow the events also when an event is not applied to the call because an answer already holds it: the mark of a person who left is removed.
