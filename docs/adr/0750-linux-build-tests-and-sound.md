# 0750. Linux build, tests and call sound

## Status

Accepted, with the container verification limits below.

The local container checks run on arm64. That is additional build coverage, not evidence for the x86-64 release target of ADR 0705. The Linux job of CI builds and tests the workspace in the same image on x86-64 (ADR 0905). Hardware devices and hardware graphics drivers require separate tests.

## Context

The native client depends on system libraries for its window, text, sound and call implementation. A build of the Rust workspace alone does not exercise a display server or an audio graph. Sound played through the PulseAudio compatibility service cannot reliably be identified by the socket process identifier of the application (ADR 0502).

## Decision

- `tools/linux-container.sh` delegates to the shared build lock and runs commands in a Linux container. The image uses a pinned Rust base image and system packages with exact versions. Each architecture has an explicit Rust linker.
- Every package of the image comes from one dated snapshot of the Debian archives: the release, its updates, its backports and its security archive. A snapshot keeps every version. The archives themselves remove a version when an update replaces it, and a build with exact versions then fails until each version is raised. A new version of a package is taken by a later snapshot date.
- The call library needs clang 21 or later: its build refuses an older one, because the C++ library that it ships needs that compiler. The image installs clang, lld and libclang 22 as Debian builds them for this release in its security archive. Debian builds one version for arm64 and amd64. The package repository of the LLVM project was not kept as the source: it holds one version for each architecture, the versions of the two architectures differ, and it removes a file when it publishes a newer build.
- Cargo's registry and target directory use named volumes. The retained target volume is for the native architecture and debug profile only. An emulated architecture check uses a temporary target volume that is removed after the check. The source is mounted from the checkout. On a Linux host the build user has the caller's user and group identifiers, except that a root caller uses user and group 1000. The shared user launcher prepares ownership of the cache mounts, and of the checkout for a root Linux caller, before dropping privileges; tests always run without root. Build scripts therefore have the same trust as a build on the host.
- The runner uses private PostgreSQL and LiveKit containers without published ports. One set of resource names shares the build lock; a variable replaces the prefix of the names. A leftover container or network stops a new run with an explicit error. The restart test can start and stop only the test LiveKit container through a small control service. The Docker socket path can be supplied for a rootless daemon.
- Each suite repetition uses a fresh runner invocation and a fresh PostgreSQL container, removed with its volume afterwards. Reusing a database container across suites accumulates test databases and statistics. PostgreSQL uses the image selection and database options of `tools/with-test-postgres.sh`, without an extra shared-memory allocation. A failed runner command includes the database’s critical failure diagnostics.
- Test audio uses PipeWire and virtual null devices in a private D-Bus session. No host sound device, display, session bus or home directory is mounted. X11 and Wayland checks use virtual displays. A mapped window is not sufficient: the smoke test also checks that the application painted its surface, and repeats the check for up to 30 seconds, because the time from the mapping to the first picture depends on the load. The image pins Mesa 25.0.7 from Bookworm backports and uses normal renderer selection. It keeps the software Vulkan driver of Mesa 22.3.6 in a directory of its own for the check of the client with an old driver (ADR 0705).
- The X11 display wrapper starts Xvfb with `-noreset`, as it already does for Xorg. It polls `xdpyinfo` until a connection succeeds before starting Openbox, then polls the root window's `_NET_SUPPORTING_WM_CHECK` property before starting the application. Each wait has its existing 30-second failure bound and checks whether the process has exited. Without `-noreset`, the last client disconnecting resets Xvfb: the successful readiness probe can be that last client, so Openbox races a reset and can fail to open the display. A longer wait does not prevent that reset. `tools/linux/test_display.py` checks delayed readiness and retains a property across the probe's disconnection, and starts twenty fresh X11 displays through Openbox. The checks run with real Xvfb and Openbox in the build image.
- The Linux sound host uses CPAL's native PipeWire backend. It reports an error if the native library cannot initialise or PipeWire cannot be reached. It does not silently select an ALSA or PulseAudio route, because that would change how the client excludes its own sound from a share.
- The native call library exports PipeWire stubs that also receive the calls made by CPAL. A small native bridge initialises these symbols before either the audio host or screen capture enters PipeWire. This bridge depends on the pinned call library; its declaration is checked when that dependency changes.
- Device listing refreshes a registry snapshot. Opening devices uses that snapshot, and a retained host keeps CPAL's PipeWire initialisation alive between operations. An explicit device identifier that the host cannot open returns an error. The engine retains the default-device selection and retry policy of ADR 0733.
- The Linux build baseline is PipeWire 0.3.65 or newer. PipeWire has supported paired, repeated initialisation and deinitialisation since 0.3.49. Older library versions are outside the supported baseline. The capture library keeps its own initialisation alive while CPAL retains and releases its guards.
- The sound capture is checked with the address checking of the compiler in a run of its own (`tools/linux/address-check.sh`, `crates/media/README.md`). The PipeWire library frees an object when the capture releases it, and a write into a freed object does not fail a test with the standard allocator.
- The Linux job of CI runs its Rust steps in this image through the same runner (ADR 0905), so the image is the one list of system packages for local checks and for CI.
- The build container gets at most four processors as a processor set and not as a processor quota. With a quota of four processors on a machine with eight, the live tier of the window used up the quota in two of three periods of 100 ms, and every thread of the test process was stopped for the rest of each such period: the tone of a call had gaps of 40 to 200 ms at capture, sending, reception and playback at the same moments, and a test that read the level of one half second failed in 5 of 11 runs. A processor set bounds the use in the same way and stops no thread. Cargo jobs are bounded by both the processor set and the memory budget of ADR 0905; the CPU set remains available to tests even when memory allows fewer compiler jobs.
- Failure statistics of the live media tests are available only with `test-support`. A measured video interval records counters at both boundaries and the age of the share. A deficient interval prints those records even when a later retry recovers. The measurement does not infer a cause from a single cumulative snapshot.

## Consequences

- A container run proves the tested virtual devices and software renderers. It does not prove microphone permissions, physical hotplug, GPU drivers, a desktop notification daemon or a person's portal chooser.
- The Linux host needs the shared lock script's `flock` path; macOS uses its `lockf` path. The container scripts do not implement a second lock and name no lock program. Docker creates a missing mount point as its own user, so the runner creates the one mount point inside the checkout before it starts a container.
- The image and Cargo volumes remain available for subsequent checks. Containers and their private network are removed after each command, including failures. Artifact-copy failures preserve an earlier command failure.
- The Linux sound host and the native bridge are separate from the macOS implementation.
