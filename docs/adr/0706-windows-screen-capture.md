# 0706. Windows screen capture with Windows Graphics Capture and process loopback

## Status

Accepted

The tests of `crates/media/tests/windows_capture` ran on the Windows machine of ADR 0905 (Windows 11, build 26200) against a window of a separate fixture program. The sound tests start both choices of sound and check that the system gives packets to the capture; they play no tone, so the content of a sound capture is not measured on Windows. The window test of the client `live::windows_share` needs LiveKit and does not run in CI (ADR 0912).

## Context

ADR 0502 requires screen share with sound on Windows and left the sound choices of Windows open until a test had run there. ADR 0736 defines the interface of a capture, and ADR 0751 the delivery of pictures and sound for a capture whose pictures arrive in their own form and whose sound arrives in portions of its own size.

Windows 11 offers Windows Graphics Capture for the picture of one screen or one window. It gives each picture as a Direct3D 11 texture, gives a picture only when the content changes, and tells when the captured window was closed. A desktop application that is not packaged needs no permission for it. The system draws a border around the captured screen or window while the capture runs.

The audio session API of Windows has process loopback (since Windows 10 build 20348): a capture of the sound that one process and its child processes play, or of all sound except that of one process and its child processes. The client plays the sound of a call from its own process.

## Decision

Bindings:

- The capture uses the `windows` crate 0.62.2, the version that gpui and cpal already link, with `windows-core` 0.62.2 for the one COM object of the crate. No new crate version is built. The crate `windows-capture`, which the lock file holds for another dependency, is not used: it links `windows` 0.61, a second version of the bindings.

Lists:

- A screen is named by the number of its device (`\\.\DISPLAY2` is screen 2), and its size is the size of the display mode in pixels.
- A window is named by its handle, which has 32 significant bits on 64-bit Windows. A window is listed when the task bar and Alt+Tab would show it: visible, not hidden by the window manager (another virtual desktop, a suspended application of the store), not minimized, with a title, not a window of the shell (desktop and task bars), each side at least 64 pixels, and either asking for the task bar or neither owned, a tool window nor a window that never takes the focus. Its size is the size of its visible frame in pixels.
- The application of a window is the process of its program; for a frame of an application of the store it is the process of the window inside the frame. An application is identified by its process and the path of its program file in lower case, and named by the description in the version information of the file, or by the file name without its extension.
- The client is its own process and every other process of the same program file with the same name (ADR 0736). None of their windows is listed, and none of them is offered for sound. The applications whose sound can be shared alone are the applications of the listed windows, as on macOS. A person who wants the sound of a program without a window chooses all system sound.
- The processes that started the client are read from the process list of the system: the process that created the client, the process that created that one, and so on. Each step requires that the creator is older than every process below it whose creation time is known, the client at least; a younger process with the recorded identifier took the identifier of an ended creator, and the chain ends there. A process whose creation time cannot be read counts as a creator. When the process list cannot be read, or does not hold the client, the creators are unknown: then no application is offered for its sound alone, the dialog states why with "This application" for a window, and a start that asks for the sound of one application fails with `CreatorsUnknown`. An application withheld by mistake costs one choice of sound; an application offered by mistake would carry the sound of the call.
- The sound of one application includes the sound of every process that it started (see Sound), so the sound of an application that started the client includes the sound of the call. Such an application is not offered for its sound alone: the lists name it in `started_the_client`, the list of applications for a share of a screen leaves it out, and a start that asks for its sound fails with `StartedTheClient`. Its windows are listed, because their picture holds no sound. A typical case is File Explorer: a person who starts Junto from the Start menu, the task bar or a folder starts it from the shell process `explorer.exe`, which also draws the windows of File Explorer. With a window of such an application the dialog keeps the choice "This application" and states that Junto was started from that application, so that its sound includes the sound of the call, and that all system sound or no sound can be shared with the window; the share does not start with that choice.
- Every system has both choices of sound: process loopback exists on every Windows 11.

Picture:

- A capture runs on a thread of its own in the multithreaded apartment. It makes a Direct3D 11 device, the capture item of the screen or the window, a free-threaded frame pool of two buffers and a session with the pointer drawn. The border of the system stays.
- The handler of each picture copies the visible part of the picture into a texture of the capture on the graphics card and puts a sign into the slot of ADR 0751. The delivery reads that texture into memory only for a picture that it sends, at the chosen frame rate, and converts it as on Linux. A screen that changes faster than the frame rate costs a copy on the graphics card for each picture and a read into memory only for each sent picture; the last picture of a screen that then stays still is sent.
- A window that changes its size gives pictures of its new size: the pool is made again with that size, and the part of a larger buffer outside the content is not read. An event of the pool can find no picture, for example an event of the buffers that the new pool replaced; the system then answers with no picture, which is not a failure, and the event is ignored.
- A screen has no transparent pixels. A fully transparent pixel of a window, at its rounded corners, is sent black, as on Linux.
- The share of a window ends when the system tells that the window was closed; the share of a screen ends when the screen is removed. The sink is told that the source is gone. The client does not start the share again.
- No thread of a capture waits for a time limit to see the end of the capture. The picture thread waits for messages of its queue, the sound thread waits for the event of the next packet and an event of the end, and the delivery waits for the slot of the pictures. The end of a capture, by a drop of the stream, a closed window or a failure, posts a message to the picture thread, sets the event of the end and wakes the delivery, so a drop of the stream returns as soon as the threads have released their objects. The first end does this once; a later end, such as the drop of a stream whose window had closed, wakes nothing. The message goes to the identifier of the picture thread, and the waker of that thread holds the thread open until it is dropped, so that the system does not give that identifier to another thread before then.
- The size of a share is the size of the capture item at the start, made smaller to the chosen bound (ADR 0736).

Sound:

- One application: process loopback of its process and its child processes. All system sound: process loopback of every process except the tree of the client's process. All system sound leaves out the tree of the client, and an application whose tree holds the client by the creators that the process list records is not offered (see Lists), so the client's own sound is not in a share in these cases. The case of a creator that has ended is open (see Consequences). The sound of a second start of the client is in all system sound, as on macOS.
- The process loopback API takes one process and one mode; it cannot include the tree of one process and leave out the tree of another one inside it. The client therefore refuses the sound of an application that started it, instead of capturing it without the client's sound.
- The tree of the client holds every process that the client starts, and all system sound leaves out their sound too. The applications that the client opens for a link or a file (a browser, a player for a saved recording) are therefore started by the shell: the client asks the window of the desktop, through the shell's automation interface (`IShellWindows`, `IShellDispatch2::ShellExecute`), to open the target, and the shell process starts the application as its own child. The address of a link or the path of a file is the file of that call, and its arguments are empty, so no part of the target becomes an argument of the call; the shell puts the target in the place of `%1` in the command of the application, and the form of a link of ADR 0740 holds no quote or space. The crate exports only this open; the open with arguments that the tests use is in the test build only and takes a list of arguments, which it quotes by the rules of `CommandLineToArgvW`. When no shell answers, for example when `explorer.exe` does not run, the client opens the target itself and writes a warning to its log; the application is then in the client's tree, and its sound is not in all system sound while it runs. A browser that already runs opens the link in its running process, whichever process started that.
- The capture asks for 32-bit floats, two channels at 48 kHz, and the system converts to that form. A packet that the system marks as silent gives silence. A packet of another form ends the capture.
- The capture runs on a thread of its own in the multithreaded apartment and waits for each packet with an event. The samples go into the queue of ADR 0751, and the clock of that ADR delivers 10 ms blocks, with silence while no packet arrives.
- A share whose sound does not start does not run without it (ADR 0502).

Start:

- The start checks the request against the lists of the moment: a window that is not listed any more, a screen that is not there, and an application whose process has ended or now runs another program file give "not available any more". The system has 10 seconds to start the picture and the sound.

Unsafe code:

- The crate `junto-media` allows unsafe code in the modules of the Windows capture that call the system. What decides something is in `share/windows/rules.rs`, without unsafe code, and its tests run on every system.

Tests:

- Ordinary tests on every system: the rule of the list of windows, the number of a screen, the handle of a window from its number, the identity and the name of an application, the client, the processes that started the client (with an unreadable creation time in the chain and an unreadable process list) and the applications that are therefore not offered, the quoting of the arguments of a command line, and the frames of a sound packet. The delivery and the conversion of pictures are the tests of ADR 0751, which now run on every system, with a delivery whose read of a picture fails and the wake of the threads at the end of a capture.
- `crates/media/tests/windows_capture` runs in the Windows job of CI. It starts the fixture program `junto-share-fixture`, a binary target of the media crate for tests, which shows a window of four known colours above the other windows without taking the focus. The tests check that the lists name the screen, the window and its application and not a window that the test program shows itself; that a share of the window shows the four colours, follows a change of them and a change of the size of the window to a larger and a smaller size, and ends with "not available any more" when the window closes, with no picture after the end; that the graphics memory of the test process does not grow over 120 pictures of a window share; that a share of the screen shows the colours at the place of the window and ends without a call of the sink when it is dropped; that a share with the sound of the fixture and a share with all system sound start, that the system gives the capture at least 0.5 s of frames, and that the delivery gives 48 kHz stereo, silent for the fixture; that a closed window, an unknown screen and the application of an ended process do not start; that a test program which the fixture started does not get the fixture's application offered for sound and gets `StartedTheClient` when it asks for it; that a program opened through the shell has `explorer.exe` as its creator, while a program that the test program starts itself has the test program; and that a link of ADR 0740 with quotes, spaces and an argument string, opened through the shell for a scheme that the test registers for the account with the command `"<fixture>" --arguments "<file>" "%1"`, reaches the fixture as one argument equal to the opened form.
- `live::windows_share` of the window tests shares the window of the fixture through the share dialog with the sound of its application, checks the colours that the other person receives, and checks that closing the window ends the share. It needs LiveKit.

## Consequences

- The share dialog warns that sound from other applications may include the call; it makes no unconditional promise to exclude the client.

- A share shows the yellow border of the system around the shared screen or window. The border is not in the pictures.
- The sound of an application includes the sound of its child processes. A program whose sound is played by a process outside its tree, such as an application of the store whose sound a broker plays, has that sound only in all system sound.
- Whether the capture depends on the volume of the speakers or of the session of the application was not tested.
- The sound tests play no tone: CI must play nothing audible on a machine that a person uses. Exclusion of the client's own sound and inclusion of exactly one application are decided by the system from the process tree and are not measured on Windows. A virtual audio device without speakers on the Windows machine would let a test measure them.
- How the audio service builds the tree of a process is not documented. The rule of the lists follows the creators that the process list records. When a creator of the client has ended, the processes above it are not seen; if the audio service still counts the client in their tree, an application above an ended creator (for example File Explorer, when Junto was started through a script whose window has closed) is offered although its sound would include the call, and the client's own sound is then in a share with that application's sound. This was not measured.
- Applications that a person cannot share alone because they started Junto: File Explorer in the usual start of Junto, and a terminal or a launcher with a window from which Junto was started.
- The client test of the share through the window runs only where LiveKit runs; the Windows job has none (ADR 0912).
- The capture costs one Direct3D device per share.
