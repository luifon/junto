# 0706. Windows screen capture with Windows Graphics Capture and process loopback

## Status

Accepted

The tests of `crates/media/tests/windows_capture` ran on the Windows machine of ADR 0905 (Windows 11, build 26200) against a window of a separate fixture program. The sound tests start both choices of sound and check that the system gives packets to the capture; they play no tone, so the content of a sound capture is not measured on Windows. The window test of the client `live::windows_share` needs LiveKit and does not run in CI (ADR 0912).

## Context

ADR 0502 requires screen share with sound on Windows and left the sound choices of Windows open until a test had run there. ADR 0736 defines the interface of a capture, and ADR 0751 the delivery of pictures and sound for a capture whose pictures arrive in their own form and whose sound arrives in portions of its own size.

Windows 11 offers Windows Graphics Capture for the picture of one screen or one window; a share of the windows of one application draws one capture of each window into the picture of one screen (ADR 0738). It gives each picture as a Direct3D 11 texture, gives a picture only when the content changes, and tells when the captured window was closed. A desktop application that is not packaged needs no permission for it. The system draws a border around the captured screen or window while the capture runs.

The audio session API of Windows has process loopback (since Windows 10 build 20348): a capture of the sound that one process and its child processes play, or of all sound except that of one process and its child processes. The client plays the sound of a call from its own process.

## Decision

Bindings:

- The capture uses the `windows` crate 0.62.2, the version that gpui and cpal already link, with `windows-core` 0.62.2 for the one COM object of the crate. No new crate version is built. The crate `windows-capture`, which the lock file holds for another dependency, is not used: it links `windows` 0.61, a second version of the bindings.

Lists:

- A screen is named by the number of its device (`\\.\DISPLAY2` is screen 2), and its size is the size of the display mode in pixels.
- A window is named by its handle, which has 32 significant bits on 64-bit Windows. A window is listed when the task bar and Alt+Tab would show it: visible, not hidden by the window manager (another virtual desktop, a suspended application of the store), not minimized, with a title, not a window of the shell (desktop and task bars), each side at least 64 pixels, and either asking for the task bar or neither owned, a tool window nor a window that never takes the focus. Its size is the size of its visible frame in pixels.
- The application of a window is the process of its program; for a frame of an application of the store it is the process of the window inside the frame. An application is identified by its process and the path of its program file in lower case, and named by the description in the version information of the file, or by the file name without its extension.
- The client is its own process and every other process of the same program file with the same name (ADR 0736). Their windows are listed, and their applications are named in `ShareSources::clients`, for a share of their picture; none of them is offered for sound, and a start that asks for the sound of one of them fails with "the source is gone". A share of such a window or application offers all system sound, which leaves out the tree of this process, or no sound. The capture states at the start whether the picture shows the client, from the application of the window or of the shared application (`capture::resolve`), so that the media engine gives the sharer no preview of it (ADR 0738). The applications whose sound can be shared alone are the applications of the listed windows, as on macOS. A person who wants the sound of a program without a window chooses all system sound.
- The processes that started the client are read from the process list of the system: the process that created the client, the process that created that one, and so on. Each step requires that the creator is older than every process below it whose creation time is known, the client at least; a younger process with the recorded identifier took the identifier of an ended creator, and the chain ends there. A process whose creation time cannot be read counts as a creator. When the process list cannot be read, or does not hold the client, the creators are unknown: then no application is offered for its sound alone, the dialog states why with "This application" for a window, and a start that asks for the sound of one application fails with `CreatorsUnknown`. An application withheld by mistake costs one choice of sound; an application offered by mistake would carry the sound of the call.
- The sound of one application includes the sound of every process that it started (see Sound), so the sound of an application that started the client includes the sound of the call. Such an application is not offered for its sound alone: the lists name it in `started_the_client`, the list of applications for a share of a screen leaves it out, and a start that asks for its sound fails with `StartedTheClient`. Its windows are listed, because their picture holds no sound. A typical case is File Explorer: a person who starts Junto from the Start menu, the task bar or a folder starts it from the shell process `explorer.exe`, which also draws the windows of File Explorer. With a window of such an application the dialog keeps the choice "This application" and states that Junto was started from that application, so that its sound includes the sound of the call, and that all system sound or no sound can be shared with the window; the share does not start with that choice.
- Every system has both choices of sound: process loopback exists on every Windows 11.

Picture:

- A capture runs on a thread of its own in the multithreaded apartment. It makes a Direct3D 11 device, the capture item of the screen or the window, a free-threaded frame pool of two buffers and a session with the pointer drawn. The border of the system stays.
- The handler of each picture copies the visible part of the picture into a texture of the capture on the graphics card and puts a sign into the slot of ADR 0751. The delivery reads that texture into memory only for a picture that it sends, at the chosen frame rate, and converts it as on Linux. A screen that changes faster than the frame rate costs a copy on the graphics card for each picture and a read into memory only for each sent picture; the last picture of a screen that then stays still is sent.
- A window that changes its size gives pictures of its new size: the pool is made again with that size, and the part of a larger buffer outside the content is not read. An event of the pool can find no picture, for example an event of the buffers that the new pool replaced; the system then answers with no picture, which is not a failure, and the event is ignored.
- A screen has no transparent pixels. A fully transparent pixel of a window, at its rounded corners, is sent black, as on Linux.
- The share of a window ends when the system tells that the window was closed; the share of a screen ends when the screen is removed. The sink is told that the source is gone. The client does not start the share again.
- Cancellation posts to the picture thread, sets the sound stop event and wakes delivery. Signal failures are logged, and the picture and sound waits also check cancellation at least every 100 milliseconds. The picture thread handles at most 64 messages before checking cancellation. Dropping the stream requests cancellation without joining a native worker; the bounded supervisor below confirms cleanup or reports its failure. The picture waker retains a thread handle, so the identifier cannot be reused before the waker is dropped.
- The size of a share is the size of the capture item at the start, made smaller to the chosen bound (ADR 0736).

Sound:

- One application: process loopback of its process and its child processes. All system sound: process loopback of every process except the tree of the client's process. All system sound leaves out the tree of the client, and an application whose tree holds the client by the creators that the process list records is not offered (see Lists), so the client's own sound is not in a share in these cases. The case of a creator that has ended is open (see Consequences). The sound of a second start of the client is in all system sound, as on macOS.
- The process loopback API takes one process and one mode; it cannot include the tree of one process and leave out the tree of another one inside it. The client therefore refuses the sound of an application that started it, instead of capturing it without the client's sound.
- The tree of the client holds every process that the client starts, and all system sound leaves out their sound too. The applications that the client opens for a link or a file (a browser, a player for a saved recording) are therefore started by the shell: the client asks the window of the desktop, through the shell's automation interface (`IShellWindows`, `IShellDispatch2::ShellExecute`), to open the target, and the shell process starts the application as its own child. The address of a link or the path of a file is the file of that call, and its arguments are empty, so no part of the target becomes an argument of the call; the shell puts the target in the place of `%1` in the command of the application, and the form of a link of ADR 0740 holds no quote or space. The crate exports only this open; the open with arguments that the tests use is in the test build only and takes a list of arguments, which it quotes by the rules of `CommandLineToArgvW`. When no shell answers, for example when `explorer.exe` does not run, the client opens the target itself and writes a warning to its log; the application is then in the client's tree, and its sound is not in all system sound while it runs. A browser that already runs opens the link in its running process, whichever process started that.
- The capture asks for 32-bit floats, two channels at 48 kHz, and the system converts to that form. A packet that the system marks as silent gives silence. A packet of another form ends the capture.
- The capture runs on a thread of its own in the multithreaded apartment and waits for each packet with an event. The samples go into the queue of ADR 0751, and the clock of that ADR delivers 10 ms blocks, with silence while no packet arrives.
- A share whose sound does not start does not run without it (ADR 0502).

Start:

- The start checks the request against the lists of the moment: a window that is not listed any more, a screen that is not there, and an application whose process has ended or now runs another program file give "not available any more". The system has 10 seconds to start the picture and the sound.

Apartments of COM:

- No code of the media crate leaves a thread that it did not create in an apartment of COM. A thread of the default pool of the system, of the runtime of the client or of the window keeps an apartment for the next code that runs on it, and the activation of the process loopback fails with `RPC_E_CHANGED_MODE` ("Cannot change thread mode after it is set") while threads of the default pool are in the single-threaded apartment, whatever apartment the thread of the sound has. The sound devices of `cpal` did that; the vendored copy no longer does (ADR 0733).
- `com::keep_multithreaded` keeps the multithreaded apartment of the process for the life of the process (`CoIncrementMTAUsage`). The threads of a capture, of the camera (ADR 0770) and of the sound devices use it without entering an apartment, so that objects of the system made on a thread stay usable after that thread has ended.
- A thread that needs the single-threaded apartment is a thread of its own: the open of a link or a file by the shell runs on a new thread, enters the single-threaded apartment there, and leaves it after an entry that succeeded. A failed entry, such as `RPC_E_CHANGED_MODE`, is not left with `CoUninitialize`, as Microsoft's rules state; the call then runs in the apartment that the thread has.

Unsafe code:

- The crate `junto-media` allows unsafe code in the modules of the Windows capture that call the system. What decides something is in `share/windows/rules.rs`, without unsafe code, and its tests run on every system.

Tests:

- Ordinary tests on every system: the rule of the list of windows, the number of a screen, the handle of a window from its number, the identity and the name of an application, the client, the processes that started the client (with an unreadable creation time in the chain and an unreadable process list) and the applications that are therefore not offered, the quoting of the arguments of a command line, and the frames of a sound packet. The delivery and the conversion of pictures are the tests of ADR 0751, which now run on every system, with a delivery whose read of a picture fails and the wake of the threads at the end of a capture.
- `crates/media/tests/windows_capture` runs in the Windows job of CI. It starts the fixture program `junto-share-fixture`, a binary target of the media crate for tests, which shows a window of four known colours above the other windows without taking the focus. The tests check that the lists name the screen, the window and its application, and that a window that the test program shows itself is listed with its application among the clients and not among the applications whose sound can be shared; that a share of that window with the sound of its application fails with "the source is gone", and a share of it without sound states that it shows the client; that a share of the window shows the four colours, follows a change of them and a change of the size of the window to a larger and a smaller size, and ends with "not available any more" when the window closes, with no picture after the end; that the graphics memory of the test process does not grow over 120 pictures of a window share; that a share of the screen shows the colours at the place of the window and ends without a call of the sink when it is dropped; that a share with the sound of the fixture and a share with all system sound start, that the system gives the capture at least 0.5 s of frames, and that the delivery gives 48 kHz stereo, silent for the fixture while it plays nothing; that a share with the sound of the fixture's application gives the tone that the fixture plays on the default output device (`tone <hz>` on its standard input: 900 Hz at -12 dBFS, through the sound host of the media crate) at -20 dBFS or more; that a closed window, an unknown screen and the application of an ended process do not start; that a test program which the fixture started does not get the fixture's application offered for sound and gets `StartedTheClient` when it asks for it; that a program opened through the shell has `explorer.exe` as its creator, while a program that the test program starts itself has the test program; and that a link of ADR 0740 with quotes, spaces and an argument string, opened through the shell for a scheme that the test registers for the account with the command `"<fixture>" --arguments "<file>" "%1"`, reaches the fixture as one argument equal to the opened form. A share of an application (ADR 0738) shows its window at its place in a picture of the screen and black elsewhere, follows a change of colours and of size, and goes on after the window closes; a second test opens a dialog that the window owns and a window of the application after the start of the share, each in one colour, moves the window, and requires each window at its place and black at the place that the window left. For that test the fixture creates its second windows with one more call of `CreateWindowExW` and moves its window with one more call of `SetWindowPos`; they are not activated and take no focus. A further test lists the sound devices of the machine through the sound host in 128 tasks of the default pool of the system, as the window does on its background threads, requires no thread of those tasks to be left in an apartment, and starts a share of the window with all system sound and with the sound of its application.
- `live::windows_share` of the window tests shares the window of the fixture through the share dialog with the sound of its application while the fixture plays its tone, checks the colours that the other person receives, that the other person hears the tone of the application above the level of a received share tone, and that closing the window ends the share. It needs LiveKit, which the Windows job starts (ADR 0905). The two tests with the tone play it on the default output device of the machine for a few seconds; a machine without an output device fails them with the reason that the fixture states (`tone failed`).

## Consequences

- The share dialog keeps a warning after sound is selected. The system-sound description states that another running copy of the client may include the call; both application descriptions, for a screen and for a window, state that their sound may include the call. They make no unconditional promise to exclude the client. The live window tests in `live::sound_help` choose each sound kind and check the description used by the dialog before sharing.

- A share shows the yellow border of the system around the shared screen or window. The border is not in the pictures.
- The sound of an application includes the sound of its child processes. A program whose sound is played by a process outside its tree, such as an application of the store whose sound a broker plays, has that sound only in all system sound.
- Whether the capture depends on the volume of the speakers or of the session of the application was not tested.
- The sound tests play no tone: CI must play nothing audible on a machine that a person uses. Exclusion of the client's own sound and inclusion of exactly one application are decided by the system from the process tree and are not measured on Windows. A virtual audio device without speakers on the Windows machine would let a test measure them.
- How the audio service builds the tree of a process is not documented. The rule of the lists follows the creators that the process list records. When a creator of the client has ended, the processes above it are not seen; if the audio service still counts the client in their tree, an application above an ended creator (for example File Explorer, when Junto was started through a script whose window has closed) is offered although its sound would include the call, and the client's own sound is then in a share with that application's sound. This was not measured.
- Applications that a person cannot share alone because they started Junto: File Explorer in the usual start of Junto, and a terminal or a launcher with a window from which Junto was started.
- The window live tier of the Windows job runs against the LiveKit release for Windows (`tools/with_native_livekit.py`, ADR 0905), with both share tests through the window: a window of the fixture program (`live::windows_share`) and a window of a second start of the program of the tests, which is a window of the client (`live::windows_own_share`).
- The capture costs one Direct3D device per share.

## Screen capture test boundary

The native screen-capture test requires an arriving picture at the enumerated display size and no delivery after stopping. It does not require the pixels of a fixture window at fixed desktop coordinates: the captured source is the composited desktop, and another native window can cover that region. The old fixed-coordinate colour oracle is removed. Window capture retains the four-colour content and change checks against its own source, independently of desktop occlusion. This does not establish the cause of an earlier white or grey desktop picture. Checking a complete desktop image against known pixels requires a controlled desktop session.

## Bounded capture shutdown

Dropping a Windows capture cancels delivery and signals the picture and sound workers synchronously. It does not join a native worker on the thread that drops the stream. A separate supervisor observes worker completion for at most two seconds. Background join observers confirm actual thread termination, including thread-local cleanup; the supervisor never performs a blocking join and reports workers that remain. Each worker retains its own objects until it returns; a timeout does not free objects underneath a driver or terminate a native thread. A timeout states that restarting Junto releases remaining capture resources.

`CaptureStream::stop` also returns a cleanup acknowledgement, with a three-second limit if the supervisor cannot answer. The native capture tests await that acknowledgement before requiring no further completed sink callbacks. The engine stops accepting media from an ended share at once. Cleanup failures reach the sink's separate `stop_failed` callback and the engine's share notice, including cleanup after cancellation while a share was starting; they cannot stop a new share or prevent Leave. The calls retain cleanup failures independently of the engine and of the active call, so a failure that arrives after Leave still appears in the share notice. It stays until the person dismisses it. The capture logs every returned cleanup failure, failed wake, worker panic, timeout, and inability to start its supervisor.

The picture wake checks `PostThreadMessageW`. The picture message wait and sound event wait also return at least every 100 milliseconds to check cancellation if signalling failed; each picture turn dispatches at most 64 messages before checking cancellation. Capture-session, pool, event, sound-client and thread-handle cleanup errors are retained for the cleanup result and logged. The support query has ten seconds to answer and uses no thread join.

The media unit tests `share::workers::tests` use a worker that ignores cancellation until released and a worker that panics. The window live test `live::stopping::a_stalled_capture_reports_stop_failure_and_leave_still_works` injects that same worker supervisor into a generated capture, stops sharing through the window, requires the visible failure and Leave while the worker remains held, then checks Stop Sharing followed by Leave before the cleanup deadline. The worker is explicitly released and acknowledged by the test. These tests require no physical capture. A Windows-only unit test requires the wake of an ended picture thread to return its system error; the Windows native capture target checks real window/display and sound capture cleanup.

A refused wake signal is logged and recovered through the bounded cancellation check. If workers then finish, the stop succeeds; a recovered signal failure does not claim that capture resources remain. Cleanup of an object that reports `RO_E_CLOSED` is also complete and is logged as already closed. Other cleanup failures and unfinished workers produce the cleanup notice.

The same supervisor owns Linux capture and portal-close workers. A join observer may wait on a driver or thread-local destructor; the engine and the supervisor never join that worker themselves. Failure to start a capture thread retains its untransferred native resources and reports the failure instead of dropping those resources on the caller. `share::workers::tests::thread_local_native_cleanup_is_included_in_the_deadline` holds a native-resource stand-in in a thread-local destructor and requires a cleanup timeout.
