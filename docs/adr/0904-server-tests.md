# 0904. Server tests against PostgreSQL

## Status

Accepted

## Context

The server builds its SQL statements at run time (ADR 0008) and relies on constraints, transactions and row locks of PostgreSQL for several rules: atomic counting of invite uses, single use of a challenge, one owner. A test with a replaced database layer would not exercise them. Expiry rules depend on the time, and a test that waits for real time is slow.

## Decision

- The integration tests of the server start the real router on a local port and call it over HTTP.
- They run against a real PostgreSQL. The script `tools/with-test-postgres.sh` starts one in Docker on a free local port, passes its address in `JUNTO_TEST_DATABASE_URL`, runs a command, and removes the container with its volume. The container has the name `junto-dev-postgres`, or the name in `JUNTO_TEST_POSTGRES_CONTAINER`, so that two checkouts on one machine can run their tests at the same time. It is the one script for a temporary PostgreSQL; the tests of the client use it too.
- Each test creates its own database and applies the migrations to it, so tests run in parallel and do not share state.
- A test without `JUNTO_TEST_DATABASE_URL` fails with a message that names the script. It is not skipped.
- A test replaces the clock (ADR 0008) and moves the time forward to test expiry.
- A test that shortens a time limit applies it only to the step that it examines, and prepares under the normal limits. For the time limit of a request and the time limits of the database, the test prepares on one server process and sends the examined step to a second process on the same database that has the short limit. For the time limits of the event stream, the test replaces the limits of the running server after its preparation. Only tests replace limits at run time.
- Fixtures whose bulk preparation exceeds the normal statement time limit are inserted in batches of at most 500 rows under the normal statement time limit. The fixture size and the assertions of the query under test stay unchanged; preparing thousands of rows is not one production request.
- A test waits for a condition and not for a fixed time when it needs something to have happened. For the admission check, the server states whether a check runs or a room waits for one.
- The permission function has table tests for each rule and property tests for the rules that must hold for every combination of roles and overrides.
- A test compares the committed OpenAPI document with the generated one (ADR 0205).
- A test checks that the database itself refuses states that break the invariants.
- A test of a race makes the order of the two requests fixed: it arms the commit gate (ADR 0009) to hold the first request before its commit, starts the second request, waits until PostgreSQL reports a statement that waits for a lock where the case needs it, and then releases the gate.
- One table lists every operation that needs a session, with a caller who lacks the permission and the expected denial. For each row the test checks the response and that no row of any table changed. The table is compared with the operations of the generated OpenAPI document, so a new operation that is not in the table fails a test.
- A test compares the complete responses for an absent object and for an object that the caller may not see.
- The host commands (ADR 0114) are tested by running the server binary.
- On a machine where other work compiles, heavy commands run through `tools/serial.sh`.
- The tests of calls have two tiers. The first tier is part of the integration tests: the server gets a media server in memory that behaves as step 0 measured LiveKit (ADR 0508), the tasks of calls do not run by themselves, and a test runs each admission check itself, so that the order of things is fixed.
- The second tier runs against a real LiveKit server. The script `tools/with-test-livekit.sh` starts one in Docker in development mode with the name `junto-dev-livekit`, runs a command, and removes the container. Real participants are processes of `spikes/test-participant` (ADR 0902). These tests are marked as ignored, so the plain run does not need LiveKit; they wait for the media server with bounded polling.
- Every live test has a time limit. The body of each async live test of the server, the client core and the media engine runs under `limited` of `crates/client-core/tests/e2e/limit.rs`, which the test binaries include. A watch on a thread of its own is armed before the body starts and covers the body and every cleanup of it, whether the body ends, fails or is cancelled. When the body has not ended after 300 seconds, the failure with the last steps that the test noted is written to the standard error of the process, past the capture of the test runner, the body is dropped, which ends its servers and calls and releases what it holds, and the test fails. When the body and its cleanup have not ended after 300 and 60 more seconds, the watch ends the processes that the tests started, reports the test and its last steps, and ends the test process with exit code 124. Each report is written on a thread of its own and is waited for 2 seconds at most, so a standard error that nobody reads does not hold the end. The tests record each process that they start, the call participants, the Docker commands and the helper programs, because these keep a copy of what the test process inherited, such as the lock of the machine, and a forced end runs no drop. A test that is not one future, such as the tests of virtual sound devices and of TURN over TLS on Linux, holds a `watch` with the same limit for its whole run. The wait helpers of every live tier note their steps. A test of the window is not one future: each of its waits on the runtime of the test (`World::run`) has the limit, and its waits for the window have their own limits already. A step that takes longer by design, the writing of the long channel of the native targets, names its own limit.
- The deletion of the database of a server test has its own limit of 30 seconds. The removal of the databases that a test of the upgrade copy leaves on the database server runs on a thread of its own with the same limit, also while the test unwinds after a failure; `upgrades::the_removal_after_a_failed_copy_test_ends_after_its_limit_when_postgres_does_not_answer` runs it against an address that accepts connections and never answers.
- A test server that is dropped ends its tasks, its requests and the connections of its state before its database is deleted. A drop cannot wait on the runtime of a test, so the order comes from what holds the database: each pool of a server process holds it in its settings (`Database::connect_with` builds both pools of the server from given pool settings). A pool keeps its settings until its last connection has ended, and a connection that a dropped task held goes back to its pool on a task of its own that holds the pool, so the deletion cannot start while such a return is still waiting to run, also when the state of the process has already been dropped. The drop aborts the task of `serve_with`, which keeps the tasks that it starts in a set that ends them when its future is dropped; when the last connection of the last pool on the database has ended, the database is deleted. The deletion waits for sessions as PostgreSQL does (5 seconds) and records whether it had to end any; `support::a_dropped_test_server_ends_its_tasks_and_connections_before_its_database_is_deleted` requires that it ended none, with the tasks of calls and of recordings running, and `support::a_task_cancelled_during_its_statement_ends_its_connection_before_the_database_is_deleted` requires it for a task that is cancelled while PostgreSQL runs its statement.
- The tests of the client core and of the window start their servers on databases of the type `TestDatabase` of `crates/client-core/tests/e2e/support.rs`: a database that records no statement statistics and that is deleted when its server is dropped, with the same limit of 30 seconds. The drop of a server process kills the process and waits for it; a server in the process of the test holds its database through its pools, as a server test does, and its drop waits up to 10 seconds until the tasks of its runtime have been dropped; the database is deleted when the state and its connections have ended. `processes::the_database_of_a_test_server_records_no_statistics_and_ends_with_the_server` requires, for both kinds, that the deletion has run when the drop returns and found no session; `recording_server::the_drop_of_a_recording_server_waits_until_its_tasks_are_dropped` holds the drop of one task of the runtime and requires that the drop of the server does not return before it. A test that kills a process that holds a server deletes the database of that server itself, also when the test fails, and kills and reaps the process that it started, also when it fails before it kills that process (`processes::a_holder_is_killed_and_reaped_when_its_test_fails`).
- A test that needs a server process to stop at a chosen statement, or the answer of a statement to be lost, runs the process through the proxy of `crates/server/tests/api/postgres_proxy.rs`. The proxy reads the messages of the protocol of PostgreSQL and passes every byte unchanged otherwise, with two exceptions: it answers a request for TLS or GSS encryption itself with `N`, and it passes no part of an answer that a stop holds. A stop names a text of the statement and, as an option, a text of a statement that the same connection ran before in the same transaction; a statement counts when a `Query` runs it or a `Bind` binds it, so a prepared statement that runs again is found too. The proxy ends the connection before the statement reaches PostgreSQL, or after PostgreSQL has run it and before its answer reaches the process. A stop that no connection reaches within 20 seconds fails the test with the text of the stop. The proxy ends its connections when it is dropped. The product has no hook for it. `TestServer::through` starts a second server process on the database of a test through a proxy.
- The tests of calls share the media server through a fair lock, so one test that waits while it holds the lock also stops every test that waits for the lock after it. A test that waits for the lock notes the tests that hold it. A test that holds the media server alone pauses or stops it; when it releases the media server, by its last step, a failure or its limit, the release unpauses and starts the server and waits until it answers, with a limit on each of these steps, so the tests after it have a media server. The Docker command of the Linux build image accepts the pause and the unpause of the test LiveKit server too. A run of these tests once did not end for hours; the test that held the lock was not found.
- Every test server of LiveKit has the settings of the deployment that do not depend on the host: `room.departure_timeout` (ADR 0020) and the setting of the camera layers (ADR 0609). They are in the one file `deploy/livekit-common.yaml`. `tools/with-test-livekit.sh`, which the server, media, window and layout tiers use, and `tools/linux/run.sh`, which starts the LiveKit server of the Linux container, add the file to their configuration, with no setting that turns it off. The settings that depend on the host stay in each script: the ports, the keys, the address of the notifications, the address that LiveKit announces, and development mode. A Compose form cannot read a second configuration file into `LIVEKIT_CONFIG`, so every form repeats the file; `deploy/tests/check_rendered.py` fails when the `room` or `video` section of a form differs from the file, or when a form has a section that is neither in the file nor one of the sections of the host (`port`, `bind_addresses`, `keys`, `redis`, `rtc`, `turn`, `webhook`, `logging`). The unit tests of the wrapper, of the Linux runner and of the comparison check each part.
- The tests of recordings use a recorder in memory that behaves as step 0 measured the recorder (ADR 0604) and writes the files of its jobs. The files are generated with `ffmpeg`, so that the server reads, joins and checks real media with the programs of the product (ADR 0606). A test runs each pass of the controller, each attempt of the processing and each transcription job itself.
- The transcription worker of these tests is a stand-in script that the server runs as it runs the worker. It keeps the job file that it got and writes the transcript that the test prepared, so a test states both sides of the contract (ADR 0611). One more tier runs the worker of `workers/transcription` with its development model on generated speech; it is ignored in the plain run and fails with a message when the worker is not installed.

## Consequences

- The tests need Docker, and the tests of recordings need `ffmpeg` and `ffprobe` with the encoders `libopus` and `libx264`.
- A rule that depends on a lock or a constraint is tested with the lock or the constraint.
- A test of a time limit takes no real time.
- A machine under load makes a test slower and does not change its result: no preparation step runs under a shortened time limit.
- A live test runs against the media server behaviour of the deployment: a room stays 60 seconds after its last person left, and a camera layer above the lowest is forwarded again after two seconds with packets. A new setting of LiveKit that changes media behaviour goes into `deploy/livekit-common.yaml`; a form that has it alone fails the check of the deployment.
- The CI jobs on macOS and Windows run the window tests against the PostgreSQL build of their system of the same version, without Docker (ADR 0916 on macOS, ADR 0912 on Windows); the other tests that need PostgreSQL run in CI on Linux only.
