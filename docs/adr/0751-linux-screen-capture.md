# 0751. Linux screen capture through the desktop portal and PipeWire

## Status

Accepted. Container checks exercise native shared sound and real portal video with the test backend described below. A person’s portal chooser and an unmodified desktop installation remain unverified.

## Context

A Wayland client cannot enumerate another application's windows or obtain their owning process. The desktop portal chooses and authorises a screen or window and supplies a restricted PipeWire connection. It does not provide the application-sound selection required by ADR 0502. A portal's logical size is not necessarily the size of the captured pixels.

## Decision

- Linux implements the same `ScreenCapture` interface as macOS. The source list represents a request to choose a screen or window with the desktop, rather than inventing a display or window identifier. Only source kinds advertised by the portal are offered.
- Source discovery runs on the client’s existing asynchronous runtime, so the window executor can await its D-Bus and PipeWire work without entering that runtime. The same rule holds for the capture of every system (ADR 0733).
- Permission is requested for each new share, after the person presses Share. Listing choices causes no portal dialog. The Linux permission state means that authorisation takes place at the start; it does not claim that the desktop has granted permanent access.
- Each share owns a portal session and a private D-Bus connection. It selects one source, asks for an embedded pointer when the backend supports it, and uses no persistent restore token. Cancellation, refusal, session revocation and a disappearing source end the request or capture. Dropping a pending request closes its resources as well as dropping an active capture.
- The two portal requests that show no dialog, the creation of the session and the selection of the sources, have a limit of 15 seconds. The request that shows the desktop's dialog has no limit, because a person answers it. During all three the share watches the owner of the portal's bus name: a portal process that ends sends no answer, and the start then fails with that reason.
- The dialog of the desktop shows over the window in which the person pressed Share, so a desktop does not place it behind that window. The request of a capture carries the window as a window identifier of the portal (`CaptureRequest::dialog_parent`), which the start of the ScreenCast session passes to the request that shows the dialog. An X11 window gives `x11:` with its XID in hexadecimal. A Wayland window exports its surface with the xdg-foreign protocol of the compositor (version 2, else version 1) and gives `wayland:` with the handle of the export; the client keeps the export until the next share starts, because the portal reads it while its dialog shows. The client makes the identifier from the window handle of gpui with `ashpd::WindowIdentifier::from_raw_handle`, the code that gpui uses for the dialogs of files; the first step, which reads the surface of the window, runs while the window exists, and only the wait for the compositor follows. A window without a handle of the desktop, such as a window of the tests, and a compositor without xdg-foreign give no identifier, and the dialog shows without a parent window as before. Test: `share::linux::portal::tests::the_portal_keeps_the_explicit_kind_and_receives_an_early_response` (the start passes the identifier to the portal). The placement of the dialog over the window is checked by a person on an X11 and a Wayland desktop.
- Video is read from the remote PipeWire file descriptor supplied by the portal. A stream serial is preferred when the portal supplies it. Legacy node identifiers are used only within the session that supplied them. A removed source is not rebound to another node that reuses its identifier.
- The capture negotiates raw shared-memory pixels, validates buffer boundaries and strides, honours crop metadata, and converts to the call library's video buffer. The negotiated pixel size determines the share dimensions. Resolution and frame rate use the same choices as macOS. An unsupported buffer format fails explicitly.
- The capture asks for the header metadata of a buffer besides the crop metadata, because a producer attaches only what the consumer asks for. A buffer whose header or whose data chunk is marked as corrupted is not sent.
- A failure before the first picture is the answer to the start of the share, so the person reads its reason.
- The sound choice remains independent and explicit: no sound, system sound, or one application. A Linux window selection does not automatically select its owning application's sound. The person chooses an application from the currently playing applications also when sharing a window. A failed or unavailable sound choice never becomes system sound.
- Audio uses a separate direct connection to the local PipeWire graph, following ADR 0502. It creates explicit links from selected playback streams without automatic session-manager linking. Application identity is the sandbox application identifier where available, otherwise the binary and application names together. A reported process identifier or reusable node identifier does not identify an application.
- The sound graph excludes the capture's client, the daemon-verified process identifier of Junto's playback, and forwarding nodes that have a link group. A stream whose client has no daemon-verified process identifier, and a node whose information is incomplete, is never captured: it could be Junto's own. Registry changes update both additions and removals of links.
- System sound is every playback stream that is certainly not Junto's own (ADR 0502). It includes the stream of a program that states no application name; such a program is absent from the list of applications, because it has no identity that a person could choose.
- Each object that the capture binds is held together with its listener, and the listener is released first. The release of a listener writes into its object, and PipeWire frees an object that the daemon has removed as soon as the capture releases it.
- Only the loss of the connection to the daemon ends the capture; the PipeWire library uses the same rule for its streams. An error of the connection with another code leaves the capture running, and a connection that is dead ends with the loss that the library then reports. The daemon reports every error on the connection: a link whose port ended between its announcement and the request is refused in this way, and so is a request for an object that the daemon had already removed. A refused link is released and asked for again at the next change of the graph while the graph still wants it. A stream reports its own error through its state.
- The audio callback writes stereo pairs to a preallocated queue of at most 400 milliseconds, of which the delivery keeps a small part. A ten-millisecond clock on a thread of its own delivers sound and inserts silence when the graph produces no callbacks. A start or restart primes sixty milliseconds of sound to cover the variable graph quantum. The audio callback does not allocate, take a mutex, wait for the sender or perform file or network work.
- The sound graph and the delivery clock are two clocks, and the graph writes in portions of the size that it chose. The level of the queue rises and falls with each portion and moves slowly with the difference of the clocks. The delivery measures the lowest level of each second, which is what remains just before a portion arrives, and holds it between 20 and 80 milliseconds, a band that contains the level that a start leaves: outside that band a block is made from one frame more or one frame less than its length, with linear interpolation. This follows a difference of the clocks of up to 0.2 % and changes the pitch by that much. A lowest level above 120 milliseconds is sound that only waits, which a late delivery thread leaves behind; it is removed in one step down to 50 milliseconds, and that step is audible once. A queue that is nearly full is brought down to 120 milliseconds in one step, because a full queue refuses single frames of the capture.
- The sound capture is ready when its stream has its nine ports. The stream gets its format with its first link, so a share that starts while nothing plays has none yet; a format that arrives later is checked when it arrives, and an unsupported one ends the capture.
- The capture requests nine named input channels: front left and right, centre, subwoofer, rear left and right, side left and right, and mono. The front pair is retained, centre and surround use a factor of one over the square root of two, subwoofer uses one half, and mono goes to both channels. The result is clipped to the sample range. An unsupported channel layout removes the affected application and system-sound choice from the list; a layout that changes to an unsupported one during capture ends the capture.
- The raw video copy is bounded to an 8K frame. One picture waits for the delivery: a newer picture replaces it. A screen sends a picture only when it changes, so the picture that waits is always the newest state of the screen, also when the delivery starts late or is slower than the capture.
- The capture asks the source for no more pictures than the chosen frame rate, with the maximum frame rate of the format. The limit itself is applied by the delivery and not by the capture: every usable picture goes into the slot, and the delivery takes the next one when it is due. A source that sends faster than the limit costs one copy for each of its pictures, and its last picture is still sent. Row padding and pixels outside crop metadata are not sent. A fully transparent pixel is replaced with black so hidden colour bytes cannot be transmitted.
- The slot, the delivery of pictures and sound, the clock of the sound and the conversion of pictures are in `share/delivery.rs`, which the Windows capture uses as well (ADR 0706); its tests run on every system.
- The PipeWire event thread copies the rows of a picture and does nothing for each pixel. The replacement of transparent pixels, the byte order and the conversion happen on the delivery thread. Pictures and sound are delivered on two threads, so the conversion of a large picture does not delay the sound.
- A sandbox with access to the portal but no access to the local audio graph can offer video without sound. It must not offer audio choices it cannot provide.
- The virtual portal test builds the pinned wlr 0.7.1 backend with one shared-memory compatibility patch. That backend otherwise rejects the Pixman compositor because it requires a DMA-BUF format in addition to valid shared-memory pixels. The patch retains shared-memory format validation and changes no chooser, permission, transport or product assertion. The source archive is checked by SHA-256 and the patch must match exactly. This backend is confined to the test image.

## Consequences

- The portal owns its chooser and may include Junto's window. The client cannot filter the desktop's window list through the ScreenCast API. Selecting a whole screen can also include Junto, as on macOS. Own application sound remains excluded.
- A backend that supports only whole screens offers no window choice. Automated virtual-display checks and fake portal tests must state which source kinds they exercise.
- A real person's portal permission dialog, desktop-specific window selection and revocation controls require manual validation. A headless test that selects a virtual output is not evidence that those dialogs were run.
- A successful virtual capture with the patched backend does not establish compatibility with an unmodified desktop backend. Both stock wlr 0.7.0 and 0.8.1 rejected the tested Pixman session: the former at format validation and the latter because the old screencopy protocol path requires a DMA-BUF interface.
- A program that bypasses PipeWire has no playback stream to capture. The share does not change its sound selection to compensate.
- Two programs that state the same binary and the same application name, for example two programs of one runtime, are one entry in the list of applications (ADR 0502). The choice of that entry sends the sound of both, and the list does not show that.
- A desktop whose portal has no screen-cast backend offers no screen share. This is the case for some X11 desktops. There is no second capture route.
