# 0724. Signed release format and source

## Status

Accepted

## Context

ADR 0704 requires one source, authenticated releases and replacement of signing keys. Release authorization and periodic freshness have different custody requirements. Format 1 is settled before the first release; the package field, the release information of each version and the bound on freshness dates were added to it before the first release, when no client could verify a release yet.

## Decision

The update source is the GitHub releases of the public repository `https://github.com/luifon/junto`: every build compiles `JUNTO_UPDATE_SOURCE=https://github.com/luifon/junto/releases/`. The files of a GitHub release carry the signed release information, freshness statements and client archives. Release and freshness verification remain required independently of the host.

- `JUNTO_UPDATE_SOURCE` is one build-time HTTPS base address; HTTP is allowed only for literal loopback addresses. Credentials, queries, fragments, whitespace and control characters are refused by shared build/runtime validation. Without a source or both trust sets, no update request is made. The existing startup and six-hour scheduler applies.
- Release public keys are in `packaging/update-keys.json`; freshness public keys are in `packaging/freshness-keys.json`. Each is a reviewed array of up to 32 base64 Ed25519 keys, initially empty. Release keys authorize code and remain offline between releases. Freshness keys are used before each 30-day expiry, without using release keys. The sets and their private keys are distinct: the build, `TrustedKeys::compiled` and publication refuse a key that is in both files, because its holder would have both roles.
- A release target is the system, the package (`bundle`, `directory` or `appimage`, ADR 0726) and the architecture. `latest-<system>-<package>-<architecture>.json` serves format 1 permanently. A later incompatible format uses a different filename; changing this file's format cannot migrate existing clients. Optional unknown fields are ignored; duplicate known fields are refused. Every used field is inside authenticated bytes.
- The source also keeps `release-<version>-<system>-<package>-<architecture>.json` for every release, with the same bytes as the newest file had, and the archive `junto-<version>-<system>-<package>-<architecture>.junto`. A client uses that file only to keep its installed version for a rollback (ADR 0726): it verifies the release signatures and requires the named version and target; it does not use the freshness part.
- The layout of the source is the layout of the files of GitHub releases (`HttpSource`). The release of version V has the tag `v<V>`. The client reads the latest file at `<source>latest/download/latest-<target>.json`, which GitHub serves from the newest published release that is neither a draft nor a pre-release. It reads every file of version V at `<source>download/v<V>/<file>`: the archive that verified release information names, and, for the rollback, the release information and archive of the installed version. These addresses stay valid after newer releases, so a client never reads an archive through the latest address, and a newer release that is published between its two requests does not change the archive that it receives. The release information names its archive by a file name only; the client takes the tag from the authenticated version, so format 1 is unchanged. A static host serves the same layout with the same paths.
- Every release, also a test release, has the tag `v<version>` of the version that its files state. A test release is published as a pre-release under that tag: the latest address does not serve a pre-release, so clients are offered it only after it is edited into a normal release marked latest. That promotion changes no file, and the per-tag addresses are valid from the start. While no release is published that is not a pre-release, the latest address answers 404, and the check fails ("Could not check for a newer version.", ADR 0780).
- The envelope contains base64 `payload`, named `signatures`, and `freshness`. Release signatures cover exactly the decoded payload bytes, prefixed by `junto-release-metadata-v1` and a zero byte. Parse only those verified bytes. The release payload holds `format` (1), `version`, `system`, `package`, `architecture`, safe `archive` filename, `size`, lower-case hexadecimal `sha256` and named `archive_signatures`. Archive signatures cover `junto-release-archive-sha256-v1`, a zero byte and the binary digest. These signatures do not expire.
- `freshness` contains its own base64 payload and named signatures. Its payload holds `format` (1), `version`, `release_sha256` (the digest of the exact release payload), and `expires` (Unix seconds). Freshness signatures cover `junto-release-freshness-v1`, a zero byte and those exact bytes. Verify with the freshness trust set, then require the stated version and digest to equal the authenticated release information. Missing or expired freshness is refused before even an equal release is described as current. An expiry more than 45 days after the local clock is refused in the same way: the release tool signs 30 days, and the rest allows for a clock that is behind. This bounds a statement that was signed with a wrong clock; it does not bound a party that holds a trusted freshness key. The message names the date and time of the computer rather than assigning fault to the source.
- At least one valid signature from the appropriate trusted set authenticates each object. Each list has at most 32 entries. Sign release information with every release key still needed by supported clients; refresh can likewise carry several freshness signatures. Either role can rotate independently. Shipping an overlap build alone does not reach clients that skipped that build.
- `packaging/renew_freshness.py <release tool> <retained release directory> <freshness secret>... [--upload <tag>]` renews the newest release: it runs `refresh` on the latest file of every target in the directory that `packaging/release_assets.py` wrote (ADR 0727), requires 29 days or more of validity after it, and with `--upload` replaces the latest files of the GitHub release (`gh release upload --clobber`) and reads each one back from the latest address. The operator runs it with the freshness key and the release tool of the release, at most 21 days after the last statement, so that a missed date leaves nine days; each new release starts a new statement. No scheduled job is installed for it. The command refuses a tag that is not `v<version>` of the version in the directory, and checks `gh auth status` before it refreshes. The replacement removes the old file of the release before it uploads the new one, one target after the other; a check in that interval finds no file and keeps its earlier answer (ADR 0780). After an upload that stops between two targets, some targets have no latest file until the command runs again; a repeated run is safe, because `refresh` can repeat. `SHA256SUMS` of a release does not list the latest files, which each renewal replaces.
- `refresh METADATA ARCHIVE VERSION FRESHNESS-SECRET...` first verifies release authorization against trusted release keys, the operator-named version, and the existing archive's size, digest and signature. Only then does it replace the freshness statement, with signatures from trusted freshness keys. It preserves the exact release payload and signatures, writes a new private file and renames it over the old metadata. Operators refresh their retained release files, never files fetched back from the release host.
- A release key alone can authorize arbitrary code, but cannot supply valid freshness for changed release information. A freshness key alone can extend or select an authentic release, but cannot authorize changed release bytes, a different target or unsigned code; clients still refuse versions not newer than themselves. Holding both roles authorizes a new release, subject on macOS to the permanent certificate check. A source alone can withhold files, replay still-fresh authentic releases, or cause verification failures; it cannot change authenticated code or extend freshness. After a newer release, the source can keep clients on the previous release for at most the remaining validity of the last statement of that release, which is 30 days at most; a freshness key removes that limit, because it can sign new statements. No mechanism proves that a still-fresh release is the newest release.
- Unrecognized signatures produce only a Version-settings message: the information is not signed by a trusted key, automatic updating is unavailable, and any newer version must come from a source independently verified with whoever runs the person's server. This state removes the update notice, download address and install control. It does not direct the person to the unauthenticated source.
- Metadata is limited to 64 KiB and a 60-second complete deadline. Archives are limited to 512 MiB, a 60-second idle deadline reset by received bytes, and a total of 60 seconds plus signed size divided by 16 KiB/second, rounded upward. Proxies are disabled; requests contain no account/device identifier. A failed attempt restarts from zero.
- A request follows at most five redirects (`MAX_REDIRECTS`), each to an HTTPS address without a user name or a password, or to an address of the origin of the source, which a loopback test source uses (`redirect_allowed`). A redirect from HTTPS to plain HTTP, to another plain-HTTP origin, or past the bound fails the request. A redirected request carries no `Referer` header. GitHub answers a file at the latest address with two redirects, to the tag and then to its storage host, an HTTPS address with a signed query, and a file of a tag with one redirect to the storage host. The client does not limit redirects to one named storage host, because GitHub has changed that name before, and a client that refuses the new name cannot update to a build that accepts it. From the compiled source only GitHub chooses a redirect target, and the received bytes are verified, so a target on a local address is not refused. The received bytes are verified as before, so the storage host has the power of the source: it can withhold or damage a file, not change authenticated code.
- Downloads create a private file, enforce the signed size while streaming, flush and sync, then verify the held file on a blocking worker. Verification runs once more immediately before extraction. Failure or cancellation removes the temporary file. Fixed public fixtures cover all three signature domains; their private keys are not retained.
- External test key, certificate and version inputs never rewrite tracked files. Any build override records a test-configuration marker, visible in Version and `--version`. The release tool always uses its compiled trust sets. Publication of a test configuration requires the flag `--test-configuration`, and a product build refuses that flag for every command. The public release wrappers refuse overrides.
- A test configuration of the client accepts `--update-source <address>`: the update check and the update action of the window use that source with the compiled trust sets in place of the compiled source. With `--check-update` the window waits for the notice of a newer release, installs it with the update action of the version line, prints the notice, the version line, the installed version and the offered restart, and exits (ADR 0780). The package checks need it because their loopback source has an address that is known only when they run. A product build refuses both flags before it reads the installation.
- The client names `<source>tag/v<version>` as the page of a newer release and `<source>latest` as the download page (ADR 0780); GitHub shows the notes and the files of the release there.
- `publish SYSTEM PACKAGE ARCH SOURCE OUTPUT ...` publishes the package files in SOURCE for that target with the version of the tool, and checks that the package states that version. It creates OUTPUT when it does not exist and removes it again when the publication fails; an existing directory, such as the release directory of the macOS release command, is used, and no file in it is replaced. A macOS bundle is published only on macOS, where its certificate is checked; Linux and Windows packages can be published on any system.

## Consequences

- Timely freshness renewal and a reasonable local clock are required, even when no new code is released. Release-authorizing secrets need not be brought online for renewal.
- An old trusted key remains authoritative for clients that still contain it; rotation does not remotely revoke that authority.
- macOS additionally checks its permanent code-signing certificate. Release commands do not upload files; `renew_freshness.py --upload` uploads only the latest files.
- An installed client keeps its compiled source. The repository address, the tag `v<version>` of every release and the paths of the layout cannot change without leaving installed clients without updates.
- Tests: the unit tests of `redirect_allowed` and of the layout in `releases.rs`; `the_redirects_of_a_github_release_are_followed_to_the_file` and `a_request_follows_at_most_the_bound_of_redirects` in `tests/releases.rs`; the package checks serve their releases with the layout and the two redirects of GitHub (`packaging/release_tools.py`) and require every request of an update in order.
- Validation reuses existing URL, JSON, base64 and Ed25519 packages.
