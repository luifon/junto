# 0740. The message list and the composer in the window

## Status

Accepted

## Context

ADR 0401 and ADR 0408 define what a message holds: a typed document, replies, reactions, files, system lines. ADR 0721 gives the window a timeline per open place, the waiting messages and the unread summaries. gpui has a list element that measures a row when it is drawn, and the component library has a text area with inline tokens.

## Decision

Derivation:

- A function without side effects (ADR 0730) derives the rows of a list from a timeline: day separators, the line of the first unread message, messages, system lines, the waiting messages, and a row at each end that states whether the history goes on.
- Messages of one author on one day form a group while each follows the one before within 5 minutes. A reply, a system line and a deleted message end a group. A message of a group is drawn without the avatar and the name.
- Times and days are shown in the time zone of the system. A moment that the clock of that zone cannot state is shown as the server wrote it (ADR 0747).
- The line of the first unread message stands before the first message after the read position that another person wrote. It stays where it was when the place was opened, until the person leaves the place. No line is drawn when every loaded message is unread.
- A reply shows the author and the start of the message that it answers. A message that the list does not hold is read from the server, at most 8 at one time. It is read again when an event names it and when the state was reloaded, so the reply shows an edit and a deletion. The window keeps the quoted messages that the replies of the shown place name, and no others, up to the weight that ADR 0747 states.

List:

- The list is the `list` element of gpui, aligned to its end. Rows are compared with the rows before by the copy of the message that the state holds; the rows that changed are spliced, so the other rows keep their measured heights and the list keeps its position when a page is added before or after.
- Within 4 rows of an end the next page is read, once for each number of rows: the state of the client core can show a read as ended before its rows reach the window, and a second read then asked for the page after that page. Because the list asks once for each number of rows, a page read that fails with an error that passes (the server is unavailable or limits the reads) is tried again by the client core, as its other reads are: after 2, 4, 8, 16 and 32 seconds, or after the time that the server names, at most five more tries. While a try waits, a new ask of the list for the same page waits for it; a jump or a read of the latest page ends the tries of the pages of that place. After the last try the list asks again when its rows change or the place opens again. The window tells the client core where the list stands, for a reload (ADR 0721): the first message in view, or the end while the list follows it. The window keeps a record of what it told, and sends a position only when it differs from the record. A read of the latest messages makes the client core follow the end, so the record becomes the end too; and a place that the window opens again in the client core gets the recorded position with the open. Reason: the record kept the position from before such a read or such an open, so a list that came back to that position was not told again, and the client core read the end at the next reload. Test: `the_position_of_a_list_is_told_again_after_a_read_of_the_latest_messages` in `crates/client`.
- A list whose messages do not fill it shows them from its top, directly under the title of the place, and not at its end with an empty band above them (finding of the second live test, the chat of a call); once the messages fill the list it stands at its end and follows new messages. gpui puts the items of a list aligned to its end that do not fill it at its end; the copy of gpui starts them at its top (ADR 0757). Test: `layout::a_short_message_list_starts_at_its_top`.
- The list follows new messages while it shows its end. A button leads to the end when the list is elsewhere. A jump to a message (a notice, a search result, a pin) moves the list to the message and stops the following; the list follows new messages again when the person brings it to its end. The jump sets gpui's follow mode to `Normal`, because right after the jump the rows above the message are not measured and gpui's own return to the end would take the list as at its end at once. The check after the layout (next point) sets the follow mode back to `Tail` when the last row is drawn whole in the view and the loaded rows reach the end of the history. While newer messages are not loaded (after a jump, or at the unread line of a long history), the list does not follow: at the bottom of its loaded rows it reads one newer page and takes a row position 1.5 pixels above the bottom, after the layout and again just before the newer page is added to its rows, because a list aligned to its end that stands at its bottom has no row position in gpui and would show rows added after it (a turn of the wheel at the bottom removes the position again). The newer page then arrives below the view, and the person reads it by scrolling. Reason: the list followed the rows of each newer page, the check after the layout read the next page at once, and the whole history to the latest message was read and marked read without an action of the person. Test: `notices::at_the_bottom_of_the_rows_of_a_jump_one_newer_page_arrives_below_the_view`. Reason: no scroll changes the `Normal` mode, so a list brought to its end after a jump did not follow new messages, and its messages stayed unread. Test: `notices::after_a_jump_to_a_notice_the_wheel_to_the_end_reads_the_channel`.
- The page reads, the position told to the client core and the read position are decided in one place, after the layout of the list, for every input: the wheel, the trackpad, the scroll bar, a jump and new rows. An element drawn after the list reads the list after its layout: the rows in view, the number of rows, the follow state, and whether the window is active. When these, or the follow state that the render read, differ from the values that the window acted on last, it defers one function of the window that reads the next page near an end, tells the client core the position, and moves the read position when the list follows its end in an active window. gpui takes up the end of a list only in its layout, after the render read the follow state, so that function also draws the window again when the follow state of the layout differs from the follow state that the render read; the button to the end then follows the layout. gpui keeps no position of the first row while a list aligned to its end stands at its end, so there the first row is known only when all rows fit; the position told is the end in that case, and no position is told there while newer messages are not loaded. gpui calls the scroll listener of a list, and the function that draws its rows, while the list holds its own state. A call into that list from there panics, and in the event callback of the system the panic ends the process. A listener that gpui calls during the work of a list therefore reads only the values of its event and does not call the list; the scroll listener of a message list only takes away the bar of actions of the row under the pointer. Reason: the scroll listener read the follow state of the list, and the client ended at a turn of the wheel or a scroll of the trackpad over any message list of an active window; the window tests used inactive windows, for which the listener returned before that read. gpui calls no listener for a drag of the scroll bar, so the scroll bar did not end the client, but a drag read no page and told the client core no position. The values of the scroll event are those of the layout before the scroll and of the follow state before the next layout, so the position told after a turn of the wheel to the end was a row and not the end. Tests: `scroll::` in `crates/client`: one for each kind of message list (a channel, a direct conversation, a thread and the chat of a call), and `a_drag_of_the_scroll_bar_to_the_top_reads_the_older_page_and_tells_the_position`.
- Each row lies in a block of the width of the list, and its text wraps inside that width. Reason: the list lays out each row as a root of its own, and a flex row as a root takes the width of its content; a system line longer than the list was then cut at the edge of the list, as in the chat panel of a call. The day separator and the line of the first unread message are such flex rows too: their rules now span the width of the list beside the date or the words, where before they had no width. Test: `layout::a_long_system_line_wraps_inside_the_message_list` draws a line longer than the list at window widths of 720, 1000 and 1600 pixels and checks that the line lies inside the list and has more than one line of text in the narrow window, and that the day separator has the bounds of the list across.
- Formatted text is one text layout per block with runs: bold, italic, struck, inline code in the fixed-width face on its ground, links, and mentions on the terracotta ground. The italic faces of the text font are carried in the binary. A link opens in the application of the system for its address. The window draws a link only for an address that the composer accepts: HTTP, HTTPS or mailto, without a user name. A server is not trusted with what this device opens (ADR 0714), so the check of the server (ADR 0408) is not relied on, and another address is drawn as text. The application of the system receives the address in its command line: on Windows the shell puts it in the place of `%1` in the command that the application registered, so a quote or a space in the address would end that argument and add others. The window therefore opens the address in one form only: the URL parser reads it, its serializer writes it with most such characters percent-encoded, and every byte that RFC 3986 does not allow in a URI is then percent-encoded too (the serializer keeps quotes and spaces in the part of a mailto address before `?`, and backslashes after it). The result holds no quote, space, control character, `<`, `>`, `\` or character outside ASCII, starts with its scheme, and is the same address; the tooltip of the link shows that form. Each system receives it as one value and builds no command line: on macOS as a URL object for the workspace, on Linux as one argument of the opening program or as the value of the desktop portal, on Windows as the file of the shell's `ShellExecute`.
- A code block is drawn on basalt with its language. A block that names a language gets syntax colours for five kinds of token: keywords, types, functions, values (strings, numbers, constants) and comments. The tokens come from the library `synoptic`, which works with regular expressions and carries its rules for about thirty languages. The window gives it no block above 32 KiB or above 1,000 lines, takes a panic of the library as "no tokens", and takes no token of a block that the library does not give back as it was written. A pass after the library removes a keyword, a type or a function name that lies inside a longer word, and marks a capitalised name as a type in the languages that write types so. The window holds the tokens of up to 256 blocks that it drew, by the rules of their language and their text. When a further block arrives, the block that was drawn longest ago is dropped. Reason: dropping all 256 made the window compute the tokens of every block in view again on the thread of the window. Test: `a_full_store_of_code_tokens_lets_go_of_the_block_drawn_longest_ago` in `crates/client`.
- A check box takes a click and sends an edit where the message can be edited: an own message that is not permanent (ADR 0402), in a channel that is not archived (ADR 0410). Elsewhere it is drawn without a click, because the server refuses the edit (ADR 0401).
- A file that the server marked as a picture (PNG, JPEG, WebP or GIF within the bounds of ADR 0408: a still picture of at most 33,554,432 pixels, an animation of at most 2,048 frames on a canvas of at most 4,194,304 pixels) is drawn inline. Its card takes the width of its list up to the size that the message states (at most 292 by 220 pixels of the design), and the picture keeps the proportions that the message states in the width that it gets, so the row has its height before the picture has arrived, at every width of a list and every interface scale. Reason: the card had the fixed width of the picture, and a list narrower than that, such as the chat panel of a call, cut the card at its right edge. Tests: `pictures::a_picture_in_the_chat_of_a_call_fits_the_panel_and_keeps_its_proportions` (the panel of the main window, and the call window at widths of 480, 800 and 1200 pixels) and `pictures::a_picture_fits_the_message_list_at_every_window_width_and_interface_scale` (widths of 720, 1000 and 1600 pixels at the scales of 90, 100 and 150 percent). The picture is decoded away from the window, at the size at which a list draws it: the largest picture of a list, 292 by 220 pixels of the design, in pixels of the device at the interface scale and the scale of the display, with its proportions, and never larger than its own size. A window whose scale changes reads a picture again only when it draws it larger than every copy that it holds of it: a smaller size uses the smallest held copy that covers it (`Pictures::covering`). Reason: the size was part of the key of a copy, and no bytes are kept, so a change to a smaller scale downloaded every picture in view again, up to 32 MiB each (review M7). Test: `pictures::a_smaller_scale_draws_the_held_copy_of_a_picture_without_reading_it_again` (no read at 90 %, a read at 150 %). The decoder refuses a picture larger than the size that the server states, whatever its header states, and an animation with more frames than the server states. A still picture is turned by the orientation of its EXIF block after the decoding and before its reduction (ADR 0408 states the size after the turn); a picture sent before the server read the orientation keeps its own proportions in the planned bounds. Reason: a phone stores a portrait photo as 4032 × 3024 pixels with the orientation 6, and the list and the viewer drew it on its side (review H1). Tests: `pictures::a_photo_stored_on_its_side_is_drawn_upright` and `shell::decode::tests::a_photo_is_decoded_upright_by_its_exif_orientation` in `crates/client`. A decoding holds the read file, the picture or one canvas of an animation at its own size, and the reduced copy; the decodings of the process, in every window, hold at most 160 MiB at one time, and a decoding that needs more (a still picture of 33,554,432 pixels needs 128 MiB for its decoded form) starts when no other decoding runs. The decodings wait in their order. A decoding holds its bytes before the read of its file starts (`decode::read_within`), with the length of the file that the server states, so the bound counts the files that are read: three screenshots of 30 MiB of each server read beside a decoding of 8K held about 380 MiB before (review M6). Test: `shell::decode::tests::a_file_is_read_only_when_its_bytes_fit_in_the_bound` in `crates/client`. The window holds at most 128 pictures and 96 MiB of their copies, each for the owner that it was read for, and reads 4 of one owner at one time (ADR 0745). Above 96 MiB the pictures that the last drawing did not ask for are dropped, the oldest first, and released from the GPU (ADR 0774); the pictures of one drawing stay held above the bound. Measured in the window test `pictures::many_large_pictures_are_held_at_the_size_that_the_list_draws`: a list with 40 screenshots of 2560 × 1440 pixels and 10 GIFs of 498 × 280 pixels with 30 frames, in a window of 1280 × 800 at the display scale of 2 of the test platform, scrolled from its first picture to its last, held at most 100,571,968 bytes of pictures (within the 96 MiB, 100,663,296 bytes); the same pictures at their own size take 757,152,000 bytes. A copy of such a screenshot is 584 × 329 pixels, 768,544 bytes, and a copy of such a GIF keeps its size and its 30 frames, 16,732,800 bytes. Before, a list held the screenshot at 1,024 × 576 pixels, 2,359,296 bytes, at every scale, and the GIF was a file row. Reason: the lists held a copy of up to 1,024 pixels per side whatever size they drew, and the server marked no GIF, no animation and no picture above 8 MiB or 16,777,216 pixels, so a GIF and a screenshot of a large screen were rows of files. Discord shows these files inline. Tests in `crates/client`: `shell::decode::tests` (the plan of the size and the frames, the decoding of a still picture, of a GIF, an animated WebP and an animated PNG into reduced frames with their delays, the step between kept frames, the refusal of more frames or a larger canvas than stated, the files that are pictures, and the order and bound of the decodings), `shell::pictures::tests::the_held_pictures_stay_within_their_bytes_except_the_ones_in_use` and `a_picture_is_shown_up_to_the_most_pixels_that_the_window_decodes`. Every other file is a row with its name, its size and the state of its download.
- An animation (a GIF, an animated WebP, an animated PNG) is decoded frame by frame into frames at the size of the list. Its frames hold at most 16 MiB in a list and 64 MiB in the viewer: above that the frames are reduced further, to half of that size at the most, and then only every n-th frame is kept, with the delays of the frames between added to its delay. A GIF of 498 × 280 pixels keeps its size and every frame up to 30 frames at a display scale of 2. A frame with a delay of 10 ms or less is shown for 100 ms, as browsers show it. An animation repeats without end; the repeat count of a file is not read.
- An animation plays only while some part of it is in view of its list or the viewer in the active window. The window is drawn again when the shown frame ends, and not at every frame of the display: the image element of gpui asks for a drawing at every frame of the display while it animates. The animations of a window ask for at most one drawing in 50 ms (`moving::LEAST_INTERVAL`), and a frame that ends within it is shown at the next drawing, so a shorter frame is passed over. Reason: a drawing renders the whole window (gpui renders the view of a notified entity with its ancestors, and the root of gpui-base draws the window without a cache), and a GIF of 20 ms frames asked for 50 drawings a second (review M5). Measured with `JUNTO_SCREENS_ONLY=gif-frames` (release build, headless renderer, two processors of a Linux host, in three runs with other work on the host): one drawing of the window with a GIF in view takes 7.1, 8.4 and 13.4 ms (median of 60), so one drawing in 50 ms is 14, 17 and 27 % of one processor; 50 drawings a second would be 36, 42 and 67 %. Test: `pictures::a_fast_animation_draws_the_window_at_most_once_in_its_least_interval` (one second of a GIF of 20 ms frames draws the window at most 22 times and shows at least 5 of its frames). An animation out of view, and every animation of a window that is not active, ask for no drawing, and an animation continues at its shown frame when it is in view again. With reduced motion an animation shows its frame and plays only while the pointer is over it. Junto has no setting of its own for motion: gpui-base reads the setting of the system into `App::reduce_motion` when the application starts (macOS: Reduce motion; Windows: Animation effects; Linux: the `reduced-motion` key of the desktop portal, which it follows while the application runs). Discord plays GIFs only while its window has the focus, and on hover when it does not play them by itself. Test: `pictures::an_animation_plays_only_in_view_of_the_active_window_without_reduced_motion` (each frame for its delay with one drawing at its end; a window that is not active, reduced motion with and without the pointer over the picture, the picture out of view without a drawing and back in view at its frame, the viewer), and `shell::moving::tests` in `crates/client`.
- Tests: `pictures::a_gif_and_a_screenshot_are_drawn_in_the_list_and_open_in_the_viewer` (the server marks a GIF of 6 frames and a PNG of 2560 × 1440; both are drawn inside the list with their proportions, from copies no larger than the list draws, the GIF with 6 frames; the viewer reads each at the size of its place, at most its own; the download of the GIF saves its bytes). `junto-screens` draws `messages-gif-and-screenshot`.
- A download goes to the download directory of the person under a name that no file has, and the row then offers "Show in folder", behind the setting of ADR 0744 that also covers the opening of a file. While a download runs, the row offers its cancel, and the cancel removes the unfinished file; the test cancels a download before its first byte arrives. No file of a message is opened by the application. Test: `files::the_controls_of_a_file_download_it_cancel_the_download_and_show_the_file`.
- The window takes a change of the stage of a download or an upload of a file of a message, a change of its interruption, and each further hundredth of the file, as for the files of a recording (ADR 0744); a file without a stated length counts parts of 256 KiB. Reason: the window took the progress at each part that arrived or left, and each one derived the view again on the thread of the window. Test: `a_download_is_told_at_each_hundredth_and_at_its_end` in `crates/client`. The clippy rules of the crate refuse the progress watch of a download, an upload and a download of a recording everywhere except in the step reader (`state::progress::Steps`), so no reader of the window takes each part.
- A message whose files the retention of its workspace removed (ADR 0409) keeps its text, and its body states under the remaining files that its files were removed after the retention time of the workspace. The server marks such a message with `files_removed_by_retention`; without the sentence a message that had files would look as if it never had them. Test: `messages::a_message_whose_files_the_retention_removed_says_so`.

Viewer of pictures:

- A press on a picture of a message, or Enter or Space while the picture holds the focus, opens the viewer: a layer over the content of the window, in the main window and in the call window, from every list that draws the files of messages (a channel, a direct conversation, a thread with its root, the chat of a call, the pin list). The search results show the text of a message and no files. The viewer is a dialog for the accessibility tree, named after the file, and holds the keyboard focus. Escape, its close button and a press outside the picture close it, and the focus returns to where it was before. A press on the picture or on the bar of the viewer does not close it. Discord and Slack close their viewers in the same ways.
- The bar above the picture shows the name and the size of the file, "n of m" when the message has several pictures, the download control of the file (the download of the list, with its progress, its cancel and "Show in folder"), and the close button. When the message has several pictures, an arrow on each side and the Left and Right keys show the previous and the next picture of the message; after the last comes the first, and before the first the last.
- The picture is fitted to the place that the window gives it, with its proportions, and is never larger than its own size times the interface scale. The place is measured at each layout; when its size differs from the size that the drawing used, the window is drawn once more.
- A picture whose copy in the lists has its own size and every frame is drawn from that copy. Every other picture is read again while the viewer shows it and decoded at the size of the place of the picture in pixels of the device, at most 8,192 pixels per side and never larger than its own size, an animation with every frame within 64 MiB of frames, through the bound of the decodings above; a place that grows by more than a twentieth reads it again at the new size. Reason: the viewer decoded a picture at its own size, so an 8K picture held 128 MiB and a GPU texture of the same size while it was shown at the size of the window (review M4). Each read of a viewer has its number among the reads of every viewer of the window and names its file: two viewers numbered their first read 1, so the late answer of a closed viewer was shown under the next picture and its GPU copy stayed (review M3). Tests: `pictures::a_picture_larger_than_the_copy_of_the_lists_is_read_at_the_size_of_the_viewer` (5120 × 2880 in a window of 1280 × 800 is held within the window, with the bytes printed; 1600 × 800 in a window of 2600 × 1600 at its own size) and `pictures::the_read_of_a_closed_viewer_is_not_taken_for_the_read_of_the_next_one`; the copy of the lists is shown until it arrives, and stays shown when the read fails. The viewer plays an animation as a list does. The viewer holds one such picture. It is released from the GPU copies of every window (ADR 0774) when the viewer shows another picture or closes, and an answer that arrives after that is released at once. Reason: the server marked no picture with more than 1,024 pixels per side, so a screenshot of a whole screen was a file row that a person had to download to see. Discord and Slack show such a picture reduced in the list and at its own size in their viewers. The server keeps no reduced copies and decodes no picture (ADR 0408), so the client reduces it.
- The viewer closes when its server leaves the server book, and when a list of the window shows its message deleted or without the shown file.
- Tests: `pictures::a_press_on_a_picture_opens_the_viewer_with_its_name_its_size_its_download_and_arrows` (the name, the size, "n of m", the download saves the bytes of the file, the arrows and the keys, the press on the picture, Escape with the return of the focus, a press outside, the close button), `pictures::a_picture_in_the_chat_of_a_call_opens_in_the_viewer_of_both_windows`, `pictures::a_picture_larger_than_the_copy_of_the_lists_is_read_at_the_size_of_the_viewer`, and `pictures::a_gif_and_a_screenshot_are_drawn_in_the_list_and_open_in_the_viewer`. `junto-screens` draws `messages-picture-viewer` and `messages-picture-viewer-several-150`.

Actions of a message:

- React, reply, edit and delete are a bar at the message under the pointer. The same actions are a menu of the message: a right click, and from the keyboard the Menu key, Shift and F10, Enter or Space while the message holds the focus (ADR 0702). Each action is offered only where the server takes it; a message without an action has no menu, and no bar unless the bar states that the message is permanent.
- Edit is offered for an own message, and delete for an own message and with "manage messages". The roles are a prediction; the server decides (ADR 0739).
- A deletion asks first. A reaction, an edit and a deletion change nothing on screen before the server tells the change with its event; the answer to the request is not shown (ADR 0746). A refusal is told in the line under the box of the composer.
- The emoji of the picker are the table that the server uses, by group and by a search of their names. The picker offers only the emoji that the fonts of the system draw whole, and its group tabs are icons with the name of the open group above the grid; a message, a reaction and the reply line show an emoji that the fonts do not draw as its short code (ADR 0758).

Waiting messages:

- A message that the person sent is drawn at the end of the list at once, with its state: sending, uploading its files, no answer, or not sent with the reason. "Send again" and "Discard" are offered for the states that ADR 0721 names.

Composer:

- The composer is a text area that grows to 10 rows. Enter sends, and Shift with Enter adds a line.
- The text is typed with marks, and the sent message shows formatted text: `**bold**`, `*italic*`, `~~struck~~`, `` `code` ``, a block between lines of three backticks with an optional language, `> ` for a quote, `- ` and `1. ` for lists, `- [ ] ` for a check box, `[text](address)` and bare addresses for links, and a backslash before a mark for plain text. The toolbar puts the marks around the selection.
- The work to read a text for its marks grows with its length and not with its square: the runs of backticks of a text are listed once, a kind of mark that has no closing run is not searched for again, the search for the end of a link stops at the longest address, and marks inside marks are read 8 levels deep. A test counts the steps. A text above 64 KiB is not read for marks and is refused for its length.
- A mention is a token of the text area and no mark: `@` opens a list of the members and roles of the workspace, and of "everyone" with its permission; the chosen entry is one unit of the text with the identifier of its account or role. In a direct conversation the server takes a mention of its two participants only (ADR 0408), so the list offers the other participant, once the client holds the name of that account. When a message is edited, the text of the composer writes each mention on one line: a control character of the name, such as a line break, is written as a space, so no prefix of a quoted line and no escape of a line that starts a block is put inside a mention, and its range stays on the bounds of its characters. Test: `compose::tests::a_name_with_a_line_break_is_written_as_one_mention_on_one_line`.
- An edit puts the text of the message into the composer with its marks. The arrow up in an empty composer edits the last own message. Escape ends an edit or a reply.
- The text of the composer cannot state every document that the server accepts: a line break in a list item, white space at the ends of a paragraph, an address in plain text that is no link. So an edit changes only what the person changed. A block at the start or at the end of the text that stands as the composer showed it is sent as the document had it, and so is an unchanged item of a changed list. A check box that the person changes in the text keeps the text of its item. The text between is read as the text of a new message.
- Files are attached with the file dialog, by a drop on the composer, and by pasting a picture. The files of a file dialog are attached only while the composer still writes to the place and for the account that the dialog was opened for (ADR 0746). An upload starts when the file is attached. The composer shows each file with its progress and a control that removes it.
- Before a send the document is checked against the limits of ADR 0408, and a file against the limits of the server. What would be refused is not sent, and the composer states the reason.
- The composer has one line under its box that always has its height: it states a problem of the message, or a refusal, in the colour of an error, and otherwise how to send ("Enter sends · Shift + Enter adds a line", or in a wide composer of a channel with permanent messages that a sent message cannot be edited). A problem that arrives therefore moves no control, and the composer has no empty band where a problem could come. A sentence longer than the line ends with an ellipsis; its whole text is the tooltip and the accessible label of the line (ADR 0730).
- The list asks for the page before and the page after its loaded rows once for each number of rows. A read of such a page that failed and that the client core does not try again counts as a failure of its timeline (`Reading::older_failed`, `newer_failed`); the list asks for that page again at its next move, also at the same number of rows. A move is a scroll of the person (gpui calls the scroll handler of the list at each turn of the wheel, also at the first or the last row) or a change of the first row in view: a change of the height of the list, such as the notice of the failure above it, is none, as the list asked three times for a refused page while that notice took its place. A change of the first row alone was not enough: at its first row the list cannot move further up, the layout after a turn of the wheel shows the same rows, and a page refused there was never read again (a window test with the server under load stayed at the top without its older messages). Before, the list waited for another number of rows, and the history stayed without its next page until the place was opened again (open item RP1). Tests: `scroll::a_page_whose_read_failed_is_read_again_at_the_next_move_of_the_list` and `scroll::a_page_whose_read_failed_is_read_again_at_a_turn_of_the_wheel_at_the_first_row`.
- The text, the reply and the edit of a place stay with that place and with the account that wrote them while the window shows another one. When a server has another account, the texts of the account before are discarded and the uploads of its files are ended.

Unread signs:

- A channel with unread messages has a bold name and a dot, and with mentions the sign "@ n". ADR 0741 makes both follow the notification settings of the person. A workspace of the server book and the icon of a collapsed server carry the same signs for their channels. 100 or more is shown as "99+".
- The read position moves to the last loaded message when the window is active, draws the list, and the list shows its end. The chat of a call is not drawn while the panel shows the members or the settings, and its messages stay unread until the chat tab is shown. "Mark as read" in the header moves the position to the latest one of the channel.

Places:

- A text channel and the chat of a voice channel are the same list and composer. The chat tab of a call (ADR 0735) shows the chat of its voice channel in the panel.
- The window holds the place of the main area open in the client core. ADR 0741 adds the thread of the side panel, with a list and a composer of its own, and direct conversations as places of the main area.

## Consequences

- The composer shows marks while the person types, not formatted text.
- The syntax colours follow regular expressions and no grammar: a name is coloured by its form, not by its meaning. A language that the library does not know, and a block without a language, stay without colours.
- A picture above the bounds of the server for pictures is a file row, and so are HEIC, AVIF and every other format (ADR 0408).
- The name of a channel in a text is plain text: the document of the server has no channel reference.
- The list draws the rows in view and a margin of 800 pixels, so the time of a frame does not grow with the loaded messages: measured with the window code and the renderer without a display in a release build on the development machine, a frame without a change and a frame after a scroll of 40 rows take 2.6 to 2.8 milliseconds with 50 and with 10,000 loaded messages (longest 4.8). A frame after a new message derives the rows again and takes 5.3 milliseconds with 50 messages and 9.1 milliseconds with 10,000 (longest 9.9). A debug build is about ten times slower. `junto-screens` repeats the measurement (`JUNTO_SCREENS_ONLY=frames`).
- A system line of an action that this build does not know is drawn as a line without detail.
- A finished recording is a card in the chat of its voice channel (ADR 0744).
- Direct conversations, threads and pins are in the window as ADR 0741 states.
- New direct dependencies of the desktop client: `chrono` for the time zone of the system, `dirs` for the download directory, `emojis` in the version of the server, and `url` for the check of a link. All four were in the lock file already. The `image` crate of the client has its `gif` feature for the GIF pictures of messages; gpui builds the same decoder, so no crate was added.
