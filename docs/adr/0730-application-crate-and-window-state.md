# 0730. Application crate: the window, its state over the client core, and its tests

## Status

Accepted

## Context

The client core holds storage, keys, the flows, the event stream and the state of each server, and has no interface (ADR 0715). The desktop client is a gpui window (ADR 0701) whose thread must never wait for the network (ADR 0719). The window shows several servers at once (ADR 0703), and every further screen of the product is added to it. A window that reads the client core from its drawing code cannot be tested without a server and cannot be drawn in a state that is hard to reach, such as a ban. The tests of the client must run against the real server (ADR 0902) and must not need a display.

## Decision

Crate:

- The crate `junto-client` holds the desktop application. Its binary is `junto`. It depends on `junto-client-core`, on `junto-media` and on the gpui set of ADR 0701, and holds no rule of joining, of login, of the event stream or of a call.
- Of the component library it uses the unstyled layer `gpui-base`: the root view with the Tab order and the focus trap, the scroll bar, the text input and the slider. The message list is the list element of gpui, and the composer is the text area of the same layer (ADR 0740); the styled layer is not used.
- The arguments of `junto` are `--data-dir`, `--scale` and `--no-activate`. The data directory is the argument, then `JUNTO_DATA_DIR`, then the directory of the user (ADR 0710). A data directory that cannot be opened ends the start with the reason on standard error; nothing in it is changed.

State:

- One entity, the application state, owns the client. It holds what the person selected (a server, a workspace per server, a channel per workspace), the settings of the interface, and the tasks that keep the window current.
- It wakes on `Client::changes` and on the `watch` of each saved server (ADR 0719), and then tells the window to draw. It never asks at an interval for a state.
- A function without side effects derives what the window shows from a copy of what the client core holds of each server, the selection, the names that were read, and what the calls of the client hold (ADR 0734): the call of the device, the levels as lit segments of the meters, the sound settings and the devices. The drawing code takes that data and holds no rule about a server. The function is tested without a window and without a server.
- A selection that the state no longer holds is replaced when the view is derived: the first server, the default workspace, the first text channel.
- The derived view of a server that shows its lists keeps what belongs to the server apart from what belongs to the shown workspace. The server holds its direct conversations, the conversation that the main area shows, the messages and the attached files of the place of the main area, the panel of the call of this device when the main area shows its place (a voice channel or a direct conversation, ADR 0735), and the notices. The workspace holds its channels, its members, the thread, the pin list, the transcript and the search. An account that sees no workspace has a view of the server without a workspace, and keeps the direct conversations, their direct-message calls and the notices (ADR 0741).
- The server that is shown is the selected server of the client core (ADR 0107). The members of the shown workspace are loaded and released as ADR 0719 states.
- A person in a voice channel is named from the members of the workspace. An account that the list does not hold is read from its profile route. A read that gets no answer is repeated with a later change of the state, at most three times for one account; a refusal is final.
- The lists and the name of an account are shown only while the state of the event stream belongs to the account of the session. After a login to another account, a logout, a ban or a removal, the state of the account before is not shown, although the event stream can still hold it for a moment (ADR 0718).
- A login that gave the device another account than the one of its last contact is told by a notice in the notice area of the server (ADR 0712).
- Every write of a file of the data directory that the window starts runs on a background thread: the settings, the name of the preset, the connection mode, the removal of a server, the settings of the separate call window, and a moderation notice that the person put away (ADR 0120). The thread of the window takes no lock of the data directory after the start: another program that uses the directory, such as `junto-cli`, can hold the lock for as long as it wants. A moderation notice that the person put away stays on screen until its write is done. Test: `remaining::an_administrator_removes_a_member_from_one_workspace_and_the_member_keeps_the_server` holds the lock of the member's data directory while the member puts the notice away. A thread of the test holds the lock for at most 60 seconds and fails the test when the window was still waiting at that time. The test failed when the window wrote the book in the click.
- After the start, the thread of the window does not wait for a device, the network, a lock that another thread holds during such work, or a file. The tone of an incoming call opens its output on a thread of its player (ADR 0733). The calls that ask the file system run on a background thread, and their result is used on the thread of the window only where it still applies (ADR 0746): the size of a file that the person attaches; the download directory of the system, which `dirs` reads from a file on Linux and from the account database on macOS, at each save of a file of a message, of a recording or of an export; the check that a saved recording file is still there before it is opened; and the time zone of the system (ADR 0798). gpui's test platform runs the background tasks of the application on the thread of the test, so a check of the thread that takes the lock cannot tell the window from its background work in a test; the tests hold the resource that would make the window wait, and fail when it waits. The attach function of the state takes sizes that were measured (`state::measure`), so the state does not measure a file itself. The `clippy.toml` of the crate refuses the calls of the standard library that ask the file system (the metadata and existence checks of `std::fs` and `std::path::Path`, the reads, writes, opens, renames, copies, removals and directory calls of `std::fs`), `dirs::download_dir`, `iana_time_zone::get_timezone`, `time::UtcOffset::current_local_offset` and `time::OffsetDateTime::now_local` (they exist only with the feature `local-offset` of `time`, which the crate does not enable), the zone functions of the module, `chrono::Local::now` and `chrono::Local::today`, and the type `chrono::Local`. A function that runs them on a background thread, on the runtime of the client or at the start allows them by name; the build script, the screens program of the developers and the test code allow them for their whole target. Clippy does not refuse `chrono::Local` used as a value (`chrono::Local.timestamp_opt(..)`); a test of the `app` target reads the code of the crate and fails on every use of the name `Local`.
- At the start, before the first window is drawn, the thread of the window reads the settings files, the profile, the settings of the call window, the time zone of the system and what the update installer needs; the client core opens its data directory, and the clients of the event streams load the root certificates of the system. At quit it waits for the queue of writes and for the end of the call, with the limits stated below.
- The thread of the window does not copy or convert the pixels of a picture of a call. A small picture of a share is copied into an image of the window, and the picture of the watched share and a camera picture are converted into a pixel buffer of Core Video on macOS or into an image, on a blocking thread of the runtime of the client, before the frame of the display takes it (ADR 0793). A window that does not draw the call converts nothing. gpui copies an image into the atlas of the window when it draws it the first time (ADR 0774); that copy stays on the thread of the window. A change of the levels of a call alone does not derive the view: the window puts the levels into the view that it holds (`ShellView::show_levels`), and a test checks that the result equals the view that a derivation with these levels gives.
- Bound: in the endurance run of ADR 0902 (two windows, three cameras, two shares, the release profile with debug assertions on macOS), after the warming no piece of work of the application holds the thread of the windows for more than 150 ms, and at most one piece in 4000 takes more than 50 ms (three frames of a display of 60 frames a second). A piece is the work of one event with the work that its handlers start, or one frame of the display with the work around it. The test enforces both. The run of the committed code, inside the machine lock with no other test container (load average 3.4 at the start and 4.3 at the end), measured a longest piece of 70.6 ms and 2 pieces above 50 ms of 39 825. Three runs of the same window code while builds of other programs loaded the machine (load average 10 to 29) failed, with a longest piece of 244 ms to 1.04 s: the bound holds for a machine without other work. In a build without optimization the layout of gpui alone holds the thread for up to 568 ms at a scroll, so the bound is not stated for that build.
- These writes are one queue of the application and run in the order in which the person asked for them. The queue does not belong to a window: a write that was accepted is done after its window has closed. When the application quits, it waits for the queue, at most 5 seconds. A write takes that long only while another program holds the lock of the data directory; after 5 seconds the application ends and that write is lost.
- A removal of a server that is asked for while a removal of the same server runs is not started.
- The result of a write is used only where it still applies. A name that was stored marks the name field as saved only when the field still holds that name.
- The argument `--scale` sets the interface scale of one start and is not stored. A scale that the person chooses in the settings is stored and ends the scale of the start.
- What the application does by itself: it contacts every saved server at the start; it checks a join request or a device link that waits every 5 seconds, as `junto-cli --wait` does; and every 20 seconds it contacts a server on which this device has an account and no session. A server on which the person logged out is not contacted until the person logs in (ADR 0712).
- A recovery is acknowledged only by the button of its notice (ADR 0118). A notice that was drawn is not acknowledged.

Window:

- The main window is one view. It holds what belongs to the window: the layer that is open (a dialog or a menu), the text of its fields, and where the keyboard focus returns to.
- A channel list groups the channels without a category by kind, under "Text channels" and "Voice channels", and then lists each category that holds a visible channel, in the order of the server.
- A text channel shows its messages and the composer (ADR 0740). A voice channel shows the chat of the channel, the state of its call, the action that enters it, and the call when the device is in it (ADR 0735). The window draws no control of a function that the build does not have, with one exception: the camera button of the strip of the call is drawn disabled, so that the strip has its final form.
- In the call of the device the level meter of a person shows the level that the media engine measures. In another voice channel it shows three of five segments while the server reports the person as speaking (ADR 0513), and none otherwise.
- The window follows the levels of a call only as far as they change a meter: a level is turned into lit segments before it is compared with what is drawn.
- The call of the device ends with the application: the server is told when the application quits, with a wait of at most 2 seconds.
- The interface text is in one module, with one sentence for every failure of a flow and for the error codes of joining. A test fails when the client core adds a failure without a sentence.
- A device name that the application sends is the name of the product and of the operating system. It holds nothing of the machine or of the person.
- The menu of the selected server has "Log out", which is the logout of the person (ADR 0712). The item is drawn in every state of the server, disabled with its reason as its second line when the state does not accept the logout, so that a change of the state while the menu is open moves no item of the menu. After the logout the main area shows the state "You logged out of this server" with "Log in" and "Remove from this device", and the server book shows "logged out" under the name of the server. Test: `logout::a_person_logs_out_and_the_device_logs_in_again_only_when_the_person_asks` logs out in the menu, sees the server end the session, starts the window again without a login, logs in with the button to the same account, and starts again with a login. The test failed before the menu had the item.

Notice areas:

- A notice, error or bar that arrives after a view is drawn must preserve the bounds of its existing controls. Its region either keeps a fixed height or grows from the edge opposite the content anchor. The notice area scrolls when its contents do not fit; notices are not drawn over controls.
- State panels put notices in the growing part under their actions (ADR 0732).
- A message area reserves a scrolling notice area above the message list, under the controls of a direct call. The list keeps both its bounds and its scroll position when a notice arrives, whether it is at its end or scrolled away. Changing the top edge and compensating the scroll would preserve row coordinates but would clip the rows under the new notice; it would not preserve the control under the pointer.
- A call reserves a scrolling notice area at the end of its stage column, including the meeting bar. The side panel keeps its bounds. This area has a fixed height even when empty: the tiles are centred inside the stage and a shared picture fits its height, so taking height from either edge would move them. The separate call window follows the same rule.
- The channel column places entry notices and connection, sound and update notices below its scrolling list and above the call controls. Its list keeps its top anchor and its call controls keep their bottom anchor.
- The channel column draws the part of the server at its top, with a height that depends on nothing that the server sends: the entry of the notices, the title "Direct messages", "New direct message", and a list of the direct conversations with the height of five rows, which scrolls. The lists of the shown workspace take the rest of the column under it, or the sentence that no workspace is visible to the account. In a short column, such as a window of the least size with the strip of a call and a notice under the lists, the list of the conversations gives up rows down to one, and the list of the channels keeps at least one row; the top of the part of the server stays where it is. Test: `contacts::the_direct_part_shrinks_and_keeps_the_call_controls_in_the_window_of_the_least_size` draws a direct call whose microphone the system refuses in a window of 720 by 480 pixels: every control of the column ends inside the window, and both lists keep at least one row. It failed before the list of the conversations could shrink: the list of the channels had no height. A change of the workspaces of the account, of the channels or of their rows therefore moves no control of the part of the server, and a conversation that arrives moves no channel. The main area keeps its bounds when the last workspace of the account goes or one comes: an open member list stays as a side panel of the same width and states that there is no member list without a workspace, the header keeps "Members", and the place of the search field stays empty while there is no workspace, so the controls before it keep their places. Test: `contacts::the_direct_part_keeps_its_place_when_the_last_workspace_goes_and_comes_back` compares the bounds of the notices entry, "New direct message", the row of the conversation, the title, "Export conversation", "Members", the message list, the composer and the side panel before the last workspace goes, after, and after it comes back. It failed before the part of the server had a place of its own: "New direct message" moved by 76 pixels. `contacts::an_account_without_a_workspace_keeps_its_direct_conversations` compares the bounds of "New direct message" before and after a conversation arrives.
- A form reserves a scrolling status and error slot wherever a result can arrive before another control. Pending requests and explanations of an absent value share that reserved geometry with their completed state. The slot keeps its height when empty and when its text wraps. This also keeps the height and position of a centred dialog. A request result may instead follow all controls in a region whose top position is fixed.
- A form or a question that is drawn in a row in place of the content of that row closes when the server did its request, at a time that the person does not choose, and the row without it has less height. While the form or question is open, the window measures the height of its row. When the answer closes it, the row keeps that height at least, with its content at the top, so a press that starts on a control under the row before the answer and ends after it reaches that control. A form or question that a change of the state puts away keeps the height of its row in the same way. A result that the answer carries for the person, such as the code of a new invite or the secret of a new access token, is drawn in the row of its form, in the place of the form.
- The row keeps that height until one of these, and nothing else: the person opens a form or a question of the same page, the person puts one away, the page changes, or the layer closes, also when it closes because its account changed. A switch, a choice, a scroll, a drag, the expansion of a row and a change of the size or the scale of the window keep it, because a press on a control under the row can follow the answer at any time, and a release at that press would move the control under the pointer. The kept height is a minimum: at another width the row is still as tall as its content, so the kept height hides nothing. A page keeps the height of one row at a time.
- The rule holds for every row of the administration with a form or a question (ADR 0761), for the rows of the roles (ADR 0791) and for the rows of the devices of the account layer (ADR 0781). A row that the request of the person's own form adds at the top of a list whose newest rows are first, such as the row of a new invite or a new access token, is not drawn in the list from the send of the request until the list is drawn after a release of the space of the form with the row in it: the state of the server can bring the row before or after the answer and before or after the release, and at the top it would move every row under it. The code or secret that the answer carries is drawn in the row of the form in its place. The Done button of the code or secret also releases the space, because it puts the result of the form away. The row therefore joins the list at an action of the person: at the first release at which the state holds it. A row that the state brings after the release waits for the next release, also when the person sends the form again in the meantime: each row of the person's own requests is held in this way until a release at which the state holds it. A release counts only for the rows made before it, so a form opened while the list is read does not let a later row join the list at the read. A row that joins the list at a release, such as at the Done button of its result while a further request is sent, stays in the list when that request is answered. The answer of the request ends the wait for it also when a change of the state put the form away while the request was sent, such as the loss of the permission to create an access token. While the state holds only that row, the list draws neither the row nor the sentence that the list has no row, and keeps the place of that sentence. A row that arrives while the request is sent and is not the person's own joins the list with the answer.
- While the request of such a form is sent, the page offers no release: the Cancel button of the form and the actions of the rows of its list are disabled. A click on the page that the list of pages shows as open does nothing, at any time, because it changes no page. The page change and the closing of the layer remain; they drop the answer with its code or secret (ADR 0761). The list of a page is read again when the page opens, so a row that the request made before is drawn with that read. When the page opens again before the server did the request, its row arrives later with the state, as a row that another person adds. A row that the server removes from a list, such as the row of a removed member or export, and a row that another person adds, move the rows under it when the state of the server arrives.
- Changes that replace the whole body, such as a server state panel becoming channel content after its snapshot, are separate view transitions. Controls may change position at that transition, including the recovery acknowledgement. The notice remains until acknowledged; drawing or replacing a view never acknowledges it. Preserving a control across unrelated bodies would require a permanent shared location for that control, which this layout does not provide.

Tests:

- The tests of the window run the real window code on gpui's test platform against the server binary of this checkout. A test puts text into a field, clicks an element by its name, presses keys, and reads the data that the window drew last. It does not read the state of the client core in place of the window: the client core can be ahead of the window for a moment. A second client without a window acts as the administrator.
- An element has a fixed name for the tests. The row of a channel and the row of a member are named by the identifier of the channel and of the account, because a server can hold two channels or two members with one name.
- A test that needs a request to be on its way at a known moment holds it at the proxy of the test and releases it. It does not rely on a wait of a fixed length.
- A test clicks an action that depends on a permission or on a state of the server only after the window has drawn it as allowed. A change that the administrator client made before reaches the window through the event stream at a later time, and a click on an action that is drawn disabled does nothing and is not repeated. Test: `admin_pages::a_member_who_manages_channels_deletes_none_with_permanent_messages` waits until the page of the channel states that the member manages it.
- The client core answers from its own threads at real times. A test allows that in gpui's scheduler and waits for a state with a bound of 60 seconds per step.
- The application state can be given fixed data of servers in place of the client core, and a fixed state of the calls. Only the build with the feature `test-support` has this. The tool of ADR 0731 uses it.
- A test gives the application sound devices that exist only in the program: a tone as the microphone and a sink that measures (ADR 0733). The test with a call needs a media server and is ignored in the plain run.

## Consequences

- A further screen is a part of the one window and reads the same derived data.
- A state of a server that is hard to produce is drawn from fixed data, and its derivation is tested as a function.
- The window follows the event stream without a reload: a change of a channel, a member or a call is in the next drawn frame.
- At the background level the workspaces of a server that is not selected are as old as its last snapshot (ADR 0107). The server book lists them from that state.
- The name of an account that is in a voice channel and is not a member of the workspace costs one request, and at most three when the server does not answer.
- A test that starts the application a second time on one data directory closes the first window before, and checks that the state of the application ended with it.
- The tests of the window need the server binary and PostgreSQL, as the tests of the client core do.
- The crate has code for one system in two places: the height of the strip for the window controls of macOS, and the options of the title bar. Windows-specific code is not written; nothing in the crate prevents a Windows build of the same code.
