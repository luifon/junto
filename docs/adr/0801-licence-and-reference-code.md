# 0801. Licence and the reference-code process

## Status

Accepted

## Context

The project is public and depends on gpui and LiveKit, which are licensed under Apache-2.0. The Zed editor is built with gpui, and its application crates are licensed under GPL-3.0-or-later. Code derived from GPL code cannot be distributed under Apache-2.0. Code that is written with a language model may reproduce code that the model saw in training, whatever the model was given to read.

## Decision

Licence:

- The project is public under Apache-2.0, the licence of gpui and of LiveKit.
- CI checks the licence of every dependency.
- A copy of a dependency in `vendor/` keeps the copyright and licence notices of its files. Each changed source file states in its header that it differs from the published version, each change carries a `Modified:` comment (in a manifest, at the changed dependency), and a new file states that it is not in the published crate. Apache-2.0 section 4(b) requires a prominent notice of change in each changed file of a redistributed work.

The licence files of the client packages and of the server image:

- A client package and the server image carry the licence and notice texts of the third-party code in their programs. The MIT, BSD, ISC and Zlib licences require their copyright and permission notices in binary copies, Apache-2.0 section 4 requires the licence and the attribution notices of a `NOTICE` file, the SIL Open Font License requires its text with the fonts, and LGPL-2.1 section 6 requires its text and a notice with a work that contains the library.
- Each client package (the macOS bundle, the Windows ZIP, the Linux tarball and the AppImage) has a directory `licences` (`Contents/Resources/licences` in the bundle) with `Junto-LICENSE.txt`, the licence of Junto, and `third-party-licences.txt`. `packaging/licences.py` writes the second file when `bundle.py`, `windows.py` or `linux.py` assembles the package, from the checkout and from the directory of the programs of the build.
- The server image has the same two files in `/usr/share/licenses/junto-server`. The build stage of the server runs `packaging/licences.py` after `cargo build`, with Python from the Debian snapshot of the image, for the package `junto-server` and the Rust target of the image. Its file names the licence texts of ffmpeg in `/usr/share/licenses/ffmpeg` and of the recording layout page in the files of the page, and the copyright files of the Debian base image in `/usr/share/doc`.
- The crates are those that `cargo tree` gives for the packages of the programs, for the Rust target of the package: `junto-client` (`junto`) and `junto-client-core` (`junto-recover`) for a client package, `junto-server` for the image. This is the feature resolution of Cargo for these packages, so crates that only another program or the tests use are not listed. Build dependencies and procedural macros are listed: their code is not in the programs, but they produce parts of the programs, such as the generated protocol code and the download of the WebRTC library. Cargo resolves build dependencies for the machine that runs it; each package is assembled on its own system. `cargo metadata` gives the licence, the authors, the repository and the directory of each crate.
- The texts of a crate are the files of its package whose names start with `LICENSE`, `LICENCE`, `COPYING` or `UNLICENSE`, the files of a directory `LICENSES`, the file that its manifest names in `license-file`, and its notice files (`COPYRIGHT`, `NOTICE`).
- The file compares the licence files of each crate with the licence expression of its manifest. It identifies the licences whose texts a file holds by phrases of their standard texts (`LICENCE_PHRASES` in `licences.py`, from the SPDX License List 3.27.0); variants such as MIT and MIT-0, ISC and 0BSD, BSD-2-Clause and BSD-3-Clause are told apart by the phrases that one has and the other lacks. The expression is read as an SPDX expression (`OR`, `AND`, `WITH`, parentheses, and `/` as `OR`). The texts satisfy it when they give one alternative of each `OR`, each part of each `AND`, and a licence with its exception.
- When the licence files do not satisfy the expression, or the package holds no licence file, the file adds the standard text of each declared licence whose text the files lack: Apache-2.0 is the `LICENSE` of the repository, the others are in `packaging/licence-texts/`, from the SPDX License List 3.27.0. The line of the crate states it plainly: that the package holds no licence file, or that its licence files hold no text of the named licences; that the added texts are the standard texts of the licences that the manifest declares; and that the copyright holders are the authors that the manifest declares, or, without authors, the authors of the crate in the repository that the manifest names. A crate whose declared licence has no standard text stops the assembly.
- When the licence files hold the text of a licence that the expression does not declare, the line of the crate says so; the texts are in the file in any case.
- What the comparison found in the crates of the programs in October 2026: the four `sqlx` crates of the server (0.9.0) hold files `LICENSE-APACHE` and `LICENSE-MIT` whose content is only a path (`../LICENSE-APACHE`), and `bmrng` 0.5.2 holds a file with only the expression; these get the standard texts. `libm`, `minimal-lexical`, `ring` and `sha1_smol` hold texts of Apache-2.0, BSD-3-Clause or MIT that their manifests do not declare. From 23 to 80 crates per target hold no licence file.
- The file states for each crate its version, its licence expression, its source (crates.io, a git repository, Junto, or a changed copy in `vendor/`) and the numbers of its texts. Each distinct text is printed once, after the list, with every component that it applies to; two texts that differ only in line endings and trailing spaces are one text.
- The crates of the workspace are listed as part of Junto. The copies in `vendor/` are listed as changed copies, with the notice file of `webrtc-sys`.
- The WebRTC library of the client: the file `LICENSE.md` of the prebuilt library that `webrtc-sys-build` downloaded into the build directory, for the release named by `WEBRTC_TAG` in the vendored `webrtc-sys-build`, or of the library that `LK_CUSTOM_WEBRTC` names. It names WebRTC and each project that it contains, with its licence. A build directory without it stops the assembly.
- The Rust standard library of the compiler that builds the workspace (`rustc --version` in the workspace: the version of `rust-toolchain.toml`, or the compiler of the server build image), which is compiled into each program, with the MIT and Apache-2.0 texts.
- The fonts compiled into the client, with the OFL text beside each family in `crates/client/assets/fonts/`. The icons and the other pictures of the client are part of Junto.
- The Linux packages add the copyright files of the Debian packages of the libraries in `lib`, and the AppImage the licences of its runtime (below).
- No other tool is installed for this. A licence tool such as `cargo-about` identifies a licence text by its content; it would be one more pinned tool on the three CI machines, in the Linux build image and in the server image. The phrases of `licences.py` identify the licences of the crates that Junto uses; a licence file with a licence that they do not know counts as holding no text, and gets the standard text of the declared licence. `cargo deny` checks the licence of every crate in CI.

The AppImage runtime:

- An AppImage of type 2 starts with a runtime, a program that mounts the SquashFS image that follows it and starts the application. The runtime of the AppImage project (`AppImage/type2-runtime`, MIT) is linked statically with libfuse 3.15.0, squashfuse 0.5.2, zstd, zlib, mimalloc and the musl C library. The library of libfuse (`lib/`, `include/`) is under LGPL-2.1; the AppImage project changes one of its files (`patches/libfuse/mount.c.diff`).
- The release 20251108 of the project publishes the runtime and its debug files. It is built in an Alpine Linux 3.21 chroot whose packages (zstd, zlib, mimalloc, musl) are installed at build time without fixed versions, and the logs of that build are no longer kept. Its `LICENSE` and `--appimage-help` name the libraries with links to their licences; the release has no source of the libraries. The strings of the binary show zstd 1.5.6 and zlib 1.3.1; the Alpine package revisions and their changes cannot be recovered.
- LGPL-2.1 section 6: an executable that contains parts of the library, such as a static link, may be distributed under terms of choice that permit modification for one's own use and reverse engineering to debug such modifications, with a prominent notice that the library is used and is under the LGPL, a copy of the LGPL, and one of: (a) the complete machine-readable source of the library with its changes, and the work that uses the library as object code or source, so that a user can change the library and link the executable again; (b) a shared library, which a static runtime is not; (c) a written offer, valid for at least three years, to give these materials; (d) access to them from the same place as the executable; (e) proof that the user already has them. The materials need not include parts that are normally distributed with the major components of the operating system, unless that part accompanies the executable, as the static libraries of the runtime do.
- Other projects, from a search in October 2026: the projects found that use the runtime of the release carry neither its source nor an offer. One project builds the runtime from source archives with fixed checksums and publishes an archive with the sources, the static libraries, the object file of the runtime and a link script beside its AppImage. Another publishes the unchanged source archives of the components of the release 20251108 beside its downloads, with versions taken from the release.
- Decision: option (a), in the AppImage itself. The Linux build image builds the runtime from the source archives of the components, each checked by its SHA-256: the runtime at commit `dd6cebedcbddde9c82f89b011e8e1d40b6e43868` (release 20251108), libfuse 3.15.0 with the change of the project, squashfuse 0.5.2, zstd 1.5.6, zlib 1.3.1 and mimalloc 2.1.7, the versions of the release, with musl 1.2.3 and GCC 12 of the Debian snapshot of the image (ADR 0750). The steps of `tools/linux/appimage-runtime/build.sh` follow the release build of the project: libfuse built with Meson as a static library, zlib, zstd and squashfuse with their own build files, mimalloc from its one-file source `src/static.c` with the definitions and flags of its CMake file (which would also need a C++ compiler), and the runtime with the command of its Makefile (with `-static-pie`). On arm64 the build adds `-mno-outline-atomics`: the outline atomic functions of the libgcc of Debian read the processor features with `__getauxval` of the GNU C library, which musl does not have. The Makefile of the runtime names clang and `-Werror`; the build uses `musl-gcc`, whose GCC 12 reports that a `sprintf` of `runtime.c` can write past its buffer of `PATH_MAX` bytes, and only that report stays a warning (`-Wno-error=format-overflow`).
- The AppImage carries `licences/appimage-runtime`: the source archives, `SHA256SUMS`, `build.sh` and a `README.md` with the components, their licences, the versions of the build tools, and the steps to build the runtime with a changed libfuse and to put it before the SquashFS image of the AppImage (`--appimage-offset`). With the tools of the image, `build.sh` gives the same runtime, byte for byte. The licence file of the AppImage holds the licence texts of each component from its archive (with the LGPL-2.1 text of libfuse) and the Debian copyright file of musl, and states where the source is.
- Option (c) needs a postal or mail address in the packages and a commitment of three years; the repository holds no personal address (ADR 0901). Option (d) depends on the place from which a copy is downloaded; a server operator who gives the AppImage to the members of a server is such a place too. Option (a) holds in every copy of the file. The AppImage grows by the source archives, about 10 MB.
- The program `junto` in the SquashFS image is a separate program that does not link libfuse; the runtime only starts it. The runtime is under the MIT licence, which permits modification and reverse engineering. libgcc is under the GCC Runtime Library Exception, which sets no condition on the runtime.

Checks:

- The packaging unit tests generate the file for the three targets of the packages and require that its list equals the crates of `cargo tree` for the two programs, and that the texts of each crate satisfy its licence expression. A small workspace of path crates checks normal, build, target and test dependencies, files and standard texts, texts printed once, the statements of a crate without a licence file and of licence files without a required text (with authors, and without authors with a repository), the report of an undeclared licence, and the refusal of a crate without a text and of a path crate outside the workspace and `vendor/`. Each standard text and font licence is identified as its own licence only; variants are told apart. A build directory without the WebRTC licence and two different WebRTC licences are refused; the WebRTC licence of the build of the checkout is found.
- The bundle and ZIP tests require both files in the package and the list of every crate. `packaging/check_linux.py` and `packaging/check_windows.py` check the same in the packages of a real build, with the WebRTC licence of that build, and on Linux the copyright files of the bundled libraries. For the AppImage, `check_linux.py` requires the source directory of the runtime equal to that of the build image, the licence texts of each component in the licence file, the AppImage to start with the runtime of the image, and `build.sh` from the AppImage to build that runtime again, byte for byte. A unit test reads the licence texts of the runtime section from source archives and requires that the Dockerfile, `build.sh` and `README.md` name the archive of each component.
- `deploy/tests/check_licences.py` checks the server image: both files, the licence of Junto, the list of every crate of `junto-server` for the system of the image, the texts of each crate against its expression, and the licence texts of ffmpeg. The deployment job of CI runs it.

Reference code:

- The default is not to read GPL code. The Apache-2.0 sources (gpui, the LiveKit SDK, the component libraries) cover most needs.
- Where they do not, the GPL-3.0-or-later application crates of the Zed editor are a reference only, through three separate sessions:
  1. A reader reads the code and writes a description of its behaviour in plain language, with no code and no copied identifiers.
  2. A writer implements from that description and from the gpui and LiveKit documentation, without the reference source.
  3. A checker reads both and passes or fails each file. The checker's feedback names only the project's file and the kind of similarity, and never describes the reference code. Similarity that a library API forces is not a failure. After three failed rounds on one file, the loop stops and the description is rewritten.
- A record is kept of each use of the three-session process.

Similarity check:

- The similarity check covers more than the three-session process. A code-similarity tool compares every client file that implements text editing, lists and windows against a local copy of the GPL crates.

## Consequences

- A dependency with a licence that is not compatible fails CI.
- A correction of a vendored file adds its notice in the same change; `vendor/README.md` names each changed and new file.
- A new dependency whose licence files do not hold the text of its declared licence, and whose licence has no standard text, stops the assembly of a package until its text is added to `packaging/licence-texts/`. A licence that `LICENCE_PHRASES` does not know is added there with its phrases.
- The assembly of a package needs Cargo, the sources of the crates and the build directory of the programs. The file is about 1 MB. The build of the server image needs Python in its build stage.
- A new version of a component of the AppImage runtime changes the SHA-256 in `tools/linux/Dockerfile`, the version in `build.sh`, `RUNTIME_COMPONENTS` in `linux.py` and the table of `README.md`; the unit test fails while they differ. The Linux build image takes a few minutes longer to build.
- A function that only the GPL crates show how to build costs three sessions and at least one comparison round.
- The writer never has the reference source, and the checker's feedback cannot carry the reference code to the writer.
- Client files for text editing, lists and windows are compared against the GPL crates even when no reference was read for them.
- A local copy of the GPL crates is kept for the comparison only and is not part of the repository.
- The process reduces the risk of copying. It is not a legal guarantee.
